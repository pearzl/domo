# DOMO 技术设计

> 本文说明 DOMO 的实现模型、持久化约束、运行协议与扩展边界。产品目标和用户行为以 [DESIGN](DESIGN.md) 为准。

## 0. 文档边界

本文面向持续开发与维护，规定以下技术内容：

- 逻辑组件及其职责边界；
- 核心数据、事务、幂等与恢复约束；
- 工作区、Git 分支和归档引用的操作规则；
- Agent 池快照、调度事件与作业运行协议；
- 当前数据结构与初始化；
- 界面状态、异常 DAG 和审计数据的技术约束；
- 扩展能力时必须维持的技术不变量。

产品流程、状态名称、人工操作策略和界面行为不在本文重复定义。实现与产品语义存在冲突时，先澄清并统一两份文档，不以代码行为隐式替代产品决策。

## 1. 技术原则与系统不变量

### 1.1 技术原则

1. **本地权威数据**：项目、任务、作业、事件、配置和产物索引以本机数据为权威来源。模型供应商只接收作业所需上下文，不承担 DOMO 的状态存储职责。
2. **显式持久化**：调度、人工操作和 Git 操作的关键结果必须可持久化、可审计，不能只存在于进程内存或 Agent 会话中。
3. **能力隔离**：普通目录交付不使用 Git；内部共享信息仓库依赖本地 Git。交付分支能力通过工作区适配层提供，不能渗入通用任务完成条件。
4. **协议解耦**：角色协议与具体 Agent 进程、模型和会话能力分离。调度器只依赖统一作业结果，不依赖供应商私有响应格式。
5. **失败可恢复**：外部进程、模型调用和 Git 操作均可失败。每个跨资源操作都需要明确的中间状态、重入规则和恢复路径。
6. **审计不可丢失**：自动调度、人工干预、失败处置和归档操作都要形成事件，审计记录不能用当前实体状态代替。

### 1.2 系统不变量

- 一个项目在同一时刻只有一个当前阶段和一个当前状态，任务同理。
- 任务 DAG 必须无环；待启动任务的所有前置任务完成后才具备执行条件。
- 项目、任务、作业和产物始终引用明确的交付契约版本。
- 一个作业在一次派发中只绑定一个 Agent；换人会留下独立派发记录，不改写原派发信息。
- 普通工作区同一项目同一时刻只推进一个任务。
- 任务池一经初始化，项目池的排序与启停编辑不会直接改写该快照；项目池启停约束仍在派发时生效。
- Git 合入失败不能留下目标分支或项目分支的部分推进结果。
- 归档、取消和重规划不能抹除审计所需的旧任务、作业与事件。

## 2. 逻辑架构

### 2.1 组件职责

| 组件 | 职责 | 不应承担的职责 |
| --- | --- | --- |
| 项目服务 | 项目创建、目标与契约、阶段状态、重规划和归档 | Agent 进程协议、Git 命令细节 |
| 任务服务 | DAG、任务派生、任务阶段状态、验收与依赖推进 | 项目级 Agent 调度决策 |
| 作业服务 | 作业生命周期、输入输出、会话、重试、超时和结果解析 | 项目方案与验收业务判断 |
| 调度器 | 队列、Agent 可用性、优先级、让位、冷却和换人 | 修改任务验收结果 |
| Agent 适配器 | 进程调用、会话映射、运行输出、结果文件和用量归一化 | DOMO 项目状态持久化 |
| 工作区适配器 | 普通目录与 Git 工作区能力、产物访问和资源回收 | 项目报告与人工裁决 |
| Git 服务 | worktree、任务分支、交付分支、合入和归档引用 | 通用任务流程判断 |
| 事件与审计服务 | 状态事件、作业事件、人工操作、异常和恢复记录 | 以日志代替实体状态 |
| Web/API 层 | 产品视图、操作入口、输入校验和实时状态呈现 | 在客户端复制调度权威逻辑 |

### 2.2 调用边界

- 项目分析和项目总结调用规划者项目作业；执行者与验收者调用任务作业。
- 调度器接收已经明确的角色、项目、任务和作业上下文，不负责生成任务目标。
- Agent 适配器返回统一的进程状态、会话标识、运行输出、结果状态和用量数据。
- Agent 类型清单、配置校验、执行、会话与用量结算分发由同一注册表生成，不逐入口维护类型清单。
- 工作区适配器向任务服务暴露交付结果提交能力。普通工作区直接确认交付结果，Git 工作区执行分支合入。
- Web/API 层提交命令并读取投影；复杂状态推进由服务端完成。

## 3. 核心数据与持久化

### 3.1 逻辑实体

| 实体 | 关键技术内容 |
| --- | --- |
| 项目 | 目标、当前契约版本、工作区描述、阶段状态、确认方式、项目池、重规划代际、合入与归档信息 |
| 契约版本 | 目标、范围、假设、验收标准、约束、来源、对任务与产物的影响 |
| 任务 | 标题、目标、验收标准、依赖、父任务、派生标记、里程碑、阶段状态、任务池快照 |
| 产物 | 路径、类型、格式、来源任务、版本、验收方式、输入/中间/交付分类 |
| 作业 | 角色、项目或任务关联、Agent、会话、派发、队列位置、起止时间、输入输出、结果、失败分类和用量 |
| Agent | 角色、模型、进程配置、并发、启停、可用性计划、限额、冷却和让位配置 |
| 角色池条目 | 所属池、角色、Agent、优先级、启停、排序信息 |
| 事件 | 事件类型、主体、时间、关联作业、原因、上下文和操作结果 |
| 人工裁决 | 请求类型、阻塞主体、上下文、可选动作、处理结果和操作人输入 |

实体之间的关系需要稳定标识。界面标题、Agent 名称和文件路径不能替代实体 ID 作为关联依据。

### 3.2 事务边界

以下操作必须在同一持久化事务中提交其状态写入：

1. **方案确认**：写入已确认契约与方案、创建任务及任务池快照、建立 DAG、切换项目阶段状态、记录事件。
2. **重规划应用**：使旧任务与相关待派发作业失效、创建任务及依赖、保存重规划代际、切换项目状态、记录事件。
3. **任务池初始化**：写入执行者与验收者快照，并保证并发初始化只产生一份有效配置。
4. **验收结果提交**：保存验收证据与结果、更新任务阶段状态、记录事件。Git 合入作为后续外部操作处理，不与数据库事务混为一个资源事务。
5. **归档状态提交**：写入归档状态、停止派发标记和归档事件；进程终止与 Git 资源回收通过可恢复步骤执行。

外部进程和 Git 无法参与本地数据库事务。跨资源流程必须保存操作阶段、操作前引用或状态、错误结果和恢复信息，禁止以单一布尔值代表整个流程。

### 3.3 幂等与恢复

SQLite 的 `delivery` 模块保存交付契约、派发次数、重试历史、消耗边界与合入操作阶段。项目、任务和作业的 `contract_id` 指向不可变的 `contracts` 快照。数据库直接初始化当前结构，不提供历史结构迁移、旧字段转换或数据补录；非当前结构的数据库启动时拒绝打开，使用新的空数据目录运行，不自动清空已有文件。重规划请求、草稿及应用/放弃状态保存在 `replan_history`，不以当前项目上的单份草稿替代历史记录。

任务与作业通过数据库触发器绑定契约；方案应用事务将同轮创建的任务绑定到确认后的契约。作业提示词使用其保存的契约，而不是后来确认的项目方案。阶段、状态和契约事件由数据库触发器在实体写入事务内生成，事件带版本化 JSON `payload`；广播只负责通知，不承担持久化责任。

作业原地重试前把输入、结果、输出、错误和费用保存到 `job_runs`。用量聚合读取 `accounting_jobs`，包含当前作业与历史运行；`dispatches` 记录每次初始派发及原地继续，任务累计执行尝试从执行者派发记录核对，不使用可被人工重试清零的失败计数。

`project_limits` 保存用户明确设置的费用预算、任务累计执行尝试上限及项目重规划次数上限。常规派发和重试入口均检查限制，限制不取消在途作业。`PUT /api/projects/{id}/limits` 是人工设置或提高限制的入口；费用未知保持未知，不计为完整账单成本。未设置限制不限制累计消耗。

- 项目恢复期间保持阻塞，所有项目、任务、作业、队列和外部资源核对完成后才恢复自动推进。
- 每个异步操作使用稳定操作标识。重复提交方案确认、验收、合入、归档或人工裁决时，返回当前结果或冲突状态，不重复产生副作用。
- 作业派发记录先于外部进程启动持久化；进程退出结果与作业记录通过标识关联。
- 进程重启后，运行中作业必须能够归类为仍在运行、已结束待收集、需要终止或需要人工处理。
- 队列顺序和一次性跳过状态必须持久化，不能因进程重启变成不同的调度决策。
- 重规划草稿、已应用代际和清理记录按代际保存，恢复逻辑据此判断继续应用、回滚到草稿前状态或等待人工处理。

## 4. 工作区与 Git 技术设计

### 4.1 工作区能力模型

通用任务流程只依赖以下能力：

- 读取项目上下文与任务输入；
- 写入和枚举任务产物；
- 标识任务交付结果；
- 保存作业与审计信息；
- 回收任务执行资源；
- 归档并保留审计资产。

普通工作区以本地目录实现交付能力，不对用户产物调用 Git。项目共享信息保存在独立的内部 Git 仓库，因此运行服务仍需要 Git。Git 工作区额外提供仓库、worktree、任务分支、项目交付分支、base 分支与合入能力。

### 4.2 Git 工作区结构

- 项目记录创建时的 base 分支和项目交付分支。
- 并发任务使用独立 worktree 和任务分支，验收通过后的任务分支合入项目交付分支。
- 任务合入冲突返回执行阶段。冲突解决后重新验收，冲突本身不累计验收失败次数。
- 任务完成或项目归档后回收相应 worktree 与分支；任务记录保留原 worktree 路径和回收时间。
- 工作区存在未提交改动且用户确认保留时，归档回收流程跳过该 worktree，并记录保留结果。

### 4.3 项目合入算法

`merge_operations` 在 Git 操作前保存项目和目标引用，并以 `rebasing`、`fast_forwarding`、`completed`、`rolled_back`、`recovery_required` 表达操作状态。服务重启时核对两端引用：已完成快进则补记成功；能够证明未推进目标且工作区干净时恢复项目引用；存在意外引用变化或文件现场时要求人工检查，禁止后续合入覆盖现场。合入错误及操作前引用由项目详情的交付区域展示。

项目合入由服务端串行执行，避免 DOMO 内部的并发合入同时修改相同分支。

1. 读取项目分支、目标 base 分支及其检出 worktree，记录双方操作前提交。
2. 目标分支已包含项目分支提交时直接返回“已是最新”，不创建提交、不更新引用。
3. 目标分支已在某个 worktree 检出时，检查该 worktree 没有未提交改动；存在改动则拒绝操作，双方引用保持操作前提交。
4. 在项目 worktree 中对项目分支执行 rebase，目标为项目记录的 base 分支。
5. rebase 冲突或失败时执行 `rebase --abort`。项目分支与目标分支必须保持或恢复到操作前提交，错误结果列出冲突文件。
6. rebase 成功后验证目标分支能够快进到项目分支提交。
7. 目标分支未在任何 worktree 检出时，通过引用更新完成快进；目标分支已检出时，在其 worktree 执行 fast-forward 合并。
8. 合入成功后记录目标分支、合入时间、项目分支提交和操作事件。重复查询或外部合入通过提交包含关系识别。

DOMO 不自动解决项目合入冲突，不强制推送，不创建 merge commit。任何失败返回都要区分校验失败、rebase 冲突、引用更新失败和恢复失败；恢复失败必须阻塞后续重试并保留操作前引用信息。

### 4.4 归档引用与文件资产

- 任务和项目分支的提交保存在 `refs/domo-archive` 命名空间。
- `refs/domo-archive` 不进入普通分支列表，分支回收前必须确保归档引用能够解析到所需提交。
- 归档项目保留 `jobs` 目录，作为作业输入输出和相关审计资产。
- 归档记录需要能够关联项目、任务、原分支、原 worktree、归档提交和回收结果。
- 普通工作区归档保留产物与作业记录，不执行任何 Git 引用操作。

## 5. 项目分析与重规划持久化

### 5.1 分析结果

规划者输出必须解析为提问、项目方案或直接完成中的一种有效结果。结果至少经过以下校验：

- 输出类型与当前项目活动匹配；
- 项目方案引用当前目标，不采用其他草稿目标；
- DAG 无环，依赖引用存在，任务具有独立目标与验收标准；
- 直接完成结果包含实现、自检和总结所需数据；
- 需要人工输入时生成明确的阻塞原因，回答或确认与对应请求关联。

无效结果按作业协议失败处理，不能部分写入项目方案。

### 5.2 重规划代际

每轮重规划保存：

- 发起来源与具体问题；
- 本轮最初目标、契约版本、旧计划和对应报告；
- 暂停派发与在途作业结算状态；
- 独立草稿及其取消任务、保留任务、范围与验收差异；
- 放弃、应用或中断恢复状态；
- 旧任务与作业的取消结果、新任务与 DAG、清理记录和审计事件。

只有当前代际可以应用。用户放弃重规划或出现更新代际后，旧草稿保持可审计但不能提交状态推进。应用入口需要验证项目仍处于该代际，避免重复点击或并发请求重复创建任务。

## 6. 任务、派生与验收技术约束

### 6.1 DAG 与依赖推进

- 依赖写入前检查引用完整性和环。
- 父任务派生时，父任务回到待启动，所有子任务成为父任务的前置任务。
- 子任务之间不建立相互依赖；普通工作区仍按串行能力逐个推进。
- 子任务沿用普通任务状态机，执行后必须由验收者核验；里程碑继续等待人工验收。Git 子任务合入项目交付分支后完成，父任务恢复执行时接收交付分支上的子任务成果并核验整合结果。
- 子任务的失败、取消和完成通过统一依赖推进逻辑影响父任务，不为父任务建立另一套完成判断。
- 下游任务读取的是持久化依赖状态，不依赖 DAG 图或界面拓扑结果。

### 6.2 验收证据

角色结果解析提取 `pass/reason/issues` 等结论字段，任务交付前单独校验必填 `evidence`：`contract_id`、Git 项目的 `artifact_version`、`artifacts`、`risks`、`human_checks`，以及按任务验收标准原文和顺序填写的 `criteria`。每项包含 `criterion`、`passed` 和非空 `checks`；检查必须包含 `method` 与 `result`。通过结论不能包含未通过条目。项目验收必须引用本轮契约与提交、完整覆盖当前标准，并为满足条目提供检查证据。协议错误与缺少结果均在同一作业内最多追加五轮修正提示，次数用尽后阻塞。

验收记录与具体一轮执行结果、契约版本和产物版本关联。至少保存：

- 逐项验收标准及通过情况；
- 检查过的产物标识与版本；
- 检查命令或方法、结果摘要和必要输出；
- 未覆盖假设、风险与人工检查项；
- 通过或拒绝、拒绝原因、指导意见和验收者类型。

里程碑人工验收与 Agent 验收使用相同的任务退回机制。两类验收后的 Git 合并冲突共用持有调度锁的退回流程：保留冲突现场、清除当前人工 gate、回到执行阶段且不增加拒绝计数；修复后重新进行 Agent 验收与适用的里程碑人工验收。Git 合入是验收通过后的独立交付步骤，不能用合入成功反推验收证据有效。

## 7. Agent 池与调度实现

### 7.1 配置存储

- `allow_priority_fallback` 是 Agent 级字段，默认值为 `false`。
- 默认团队、项目池和任务池读取同一个 Agent 级值，池条目只读展示“可让位”，不保存池级副本。
- Agent 角色决定其可进入的角色分组。默认团队随 Agent 注册和角色编辑自动同步。
- 角色内优先级保存为连续且不重复的 `0..n-1`，`0` 为最高优先级。
- 拖动排序通过目标位置计算完整顺序；上移、下移通过相邻交换计算完整顺序。服务端统一校验目标位置、角色成员和排序结果。

### 7.2 任务池快照

任务创建时，在方案或任务创建事务内复制项目池执行者与验收者条目的 Agent、优先级和启停状态。项目池后续排序和启停编辑不回写任务池快照。

空角色池也是有效快照。读取与调度路径只读取任务池，不执行懒初始化或从项目池补齐。任务只保留角色池的排序与启停入口，不提供单 Agent 覆盖字段、覆盖接口或重置快照入口。人工裁决的一次性指定使用独立的派发状态，不改写任务池。

### 7.3 调度状态与事件

调度器需要区分：

- 全局、项目池和任务池启停；
- 角色能力、删除状态、冷却、可用时段和用量限额；
- 当前并发与最大并发；
- 让位扫描、停止扫描和等待原因；
- 一次性失败跳过状态与人工指定。

让位发生时，在 `job_queued` 事件末尾附加让位说明，例如“（A 并发已满，按让位配置调度）”。人工指定事件标注“由人工指定”。等待原因使用结构化 Agent 占用数据生成，界面可展示“等待 Agent X 释放（并发 1/1）”或全部让位 Agent 的并发占用。

人工指定不经过常规可用性过滤，但仍需持久化操作者选择、风险提示确认、目标 Agent 和派发结果。指定 Agent 满额时保留排队关系，不触发让位。

### 7.4 失败跳过与冷却

并发、冷却、周期用量和可用时段属于可自动恢复等待；人为停用、无角色成员和任务池空配置属于人工配置阻塞。配置阻塞记录独立原因，用户编辑相关全局 Agent、项目池或任务池后解除配置阻塞；验收 gate、协议失败、预算限制和任务自身暂停不会因此解除。任务失败换人判断读取任务池及项目池启停约束，不以项目池替代任务快照。

- 需要换人时，在项目或任务上记录一次性跳过失败 Agent 的状态。
- 下一次成功派发后清除该状态；项目分析、直接完成和项目总结共用项目规划者角色的跳过状态。
- 阻塞后保留 Agent 冷却，不由调度器自动重派。
- 作业重试在派发成功后清除实际目标 Agent 在对应角色下的冷却与失败计数，不影响其他 Agent。
- 任务作业和项目作业分别保存跳过状态，避免不同角色或不同项目互相清除退避信息。

## 8. 作业运行与 Agent 协议

### 8.1 进程与会话

- 作业每轮运行上限为 10 小时；超时后最多在同一会话内继续 2 轮。
- 连续 30 分钟没有 stdout/stderr 输出时判定卡死。
- 作业记录保存 Agent 进程标识、适配器会话标识、轮次、起止时间和退出状态。
- OpenCode 复用同一会话；其他支持会话的 Agent 优先复用会话。无会话能力的适配器通过完整上下文继续作业，并在作业记录中标识能力差异。
- 普通暂停允许在途进程自然结束并接收合法结果；强制暂停与归档终止进程，未保存输出可以丢弃，终止结果必须写入事件。

### 8.2 结果文件与角色协议

Agent 适配器通过约定结果文件向 DOMO 提交结构化结果。校验至少包括：

- 文件存在且可解析；
- 结果类型与规划者、执行者或验收者角色匹配；
- 必填字段、枚举值和引用标识有效；
- 项目或任务标识与当前作业匹配；
- 结果不会修改超出当前角色权限的状态。

进程正常结束但没有结果文件，或结果文件不符合角色协议，归类为协议失败。缺少结果文件时，同一作业最多追加 5 轮继续提示；提示执行者时可以包含派生子任务指引。5 轮后仍无有效结果则阻塞，不切换 Agent。

### 8.3 失败分类的技术处理

| 分类 | 技术动作 |
| --- | --- |
| 限流 | 读取 Agent 返回的重试信息设置冷却；缺少重试信息时使用默认值 |
| 供应商波动 | 在同一 Agent 上执行有限重试，次数耗尽后冷却并触发换人 |
| 永久错误 | 不在该 Agent 上重试，直接触发换人 |
| 协议失败 | 按结果文件与角色协议规则补充提示，最终阻塞 |
| 任务失败 | 保存执行失败或验收拒绝的业务结果，不触发 Agent 换人 |

作业失败记录原始错误、归一化分类、适配器信息、重试次数、冷却和后续处置。分类逻辑不能把验收拒绝误判为供应商故障。

### 8.4 用量归一化

统一用量记录包含输入 token、输出 token、费用和时长。Agent 无法提供的字段使用未知状态，不以零值填充。聚合结果的 `known_metrics` 分别记录输入、输出、缓存读写、推理 token 和费用的已知作业数量；明确上报的零值计为已知，任一 token 字段已知不代表费用已知。汇总数值只累加对应指标的已知值；前端在该指标全未知时显示“—”，部分覆盖时标注其覆盖比例。`known_jobs/unknown_jobs` 仅表达至少提供一个 token 或费用字段的作业覆盖，不替代单指标覆盖率。原始作业记录作为核对依据。

## 9. 事件、审计与备份

### 共享信息、产物和队列数据

`resources.rs` 在每个项目工作区的 `shared/` 中维护独立 Git 仓库。`shared_records` 保存待提交意图，每条记录写到 `records/<id>.json`；提交后保存 commit，重启先恢复未结算提交。已有记录不覆盖，修正通过 `supersedes` 引用，分歧通过 `conflicts` 和理由显式保留。每条记录包含适用任务范围与证据。作业只加载相关且未被替代的记录，`job_shared_versions` 固定输入版本；Agent 可通过结果 `shared_updates` 提交记录，格式或提交冲突由同作业修正，不经过规划者逐条审批。只读共享 API 支持主题与历史提交查询。

`artifacts` 登记原始输入、中间产物和最终交付，保存来源任务、作业、契约、格式与验收方式；Git 文件版本保存在 `artifact_versions`，预览只允许已登记提交。手工登记 Git 产物先校验路径在项目分支提交中存在，再在同一数据库事务中写入产物与版本索引；重复登记不重复写入同一版本。普通目录预览当前 UTF-8 文件，不提供历史恢复；预览上限为 1MiB，大文件与二进制通过所在目录查看。路径必须在工作区内，拒绝 `..`、绝对路径、`.git` 和符号链接逃逸。

普通工作区创建时登记已有文件为输入；写作业启动前比对 SHA-256 并设置未完成写入标记。成功结算检查跨任务覆盖是否有 `file_permissions` 中精确路径授权，再登记产物与更新指纹。外部变化、未授权覆盖和中断阻塞后续推进，不自动回滚文件。用户在暂停或阻塞且无在途作业时记录检查结论，重新确认指纹后才能重试。这是检测与人工检查机制，不是文件系统沙箱；外部进程仍可能写入，用户应避免并发编辑。

`queue.rs` 的 `dispatch_queue` 保存跨项目、按 Agent 的派发意图与人工顺序。等待项不是运行作业，暂停保留顺序但移除派发资格，派发或失效后保留记录。任务重试与指导裁决仅在当前角色的最新作业失败时，通过 `retry_requests` 等待相同 Agent 的队列和并发槽，真正派发时才恢复原 job/session；该角色已有后续作业时不复用历史失败，返工创建新作业，验收关联本轮执行。项目任务调序同步其等待执行项的全局位置。队列 API 提供运行项、等待原因、影响后继与里程碑信息，不自动按关键路径重排。

`merge_requests` 保存用户显式选择 Agent 的项目合入作业。人工确认风险后绕过角色、启停和周期可用性，仍检查项目预算、全局队列及并发。`runner/merge.rs` 在 `jobs/<job>/resolution` 隔离 worktree 中 rebase，核对输入引用未变化、结果线性后直接发布；不创建普通任务或验收者作业。成功和失败的 Agent 运行均调用统一适配器结算：OpenCode 从会话账本汇总主会话及子会话用量，其他适配器保留运行输出或结果中的用量；结算记录纳入累计费用与后续预算检查。失败、停止和服务中断保留现场，项目仍为已完成。脏合入工作区进入归档预览并包含在备份中。

配置建议为只读统计：包含全角色调用及重试费用、费用未知数量、关联完成任务、拒绝、失败与重规划。少于五个执行任务提示样本不足，不根据 Agent 名称推断模型档位，不自动修改角色池。多人参与任务存在重复关联，建议不是因果归因或可直接相加的独占成本。

### 9.1 事件要求

事件至少覆盖：

- 项目和任务阶段状态变化；
- 作业排队、派发、输出、结束、失败、重试和换人；
- Agent 启停、冷却、让位和人工指定；
- 契约、方案、重规划代际与产物版本；
- 验收证据、人工指导、裁决和归档；
- Git 合入、冲突、恢复、资源回收和保留结果。

事件使用稳定类型和结构化 payload。展示文案可以由事件生成，不能只保存拼接后的文本而丢失主体、原因和关联 ID。实时输出与审计事件可以采用不同存储方式，但作业必须能关联二者。

### 9.2 归档备份

`backup.rs` 提供离线命令 `--backup <新目录>`、`--verify-backup <备份目录>` 和 `--restore <备份目录> <新目录>`。服务和备份持有数据目录 `runtime.lock` 的操作系统文件锁；停服且没有未结算运行作业时才能备份。目录必须不存在，不覆盖已有文件。备份目录不得与源目录重叠。

备份使用 SQLite `VACUUM INTO` 保存一致数据库，复制项目工作区、共享仓库、jobs、用户产物目录、Git common-dir 及外部 worktree，清单保存文件与符号链接 SHA-256。校验检查文件集合、数据库完整性与作业契约关联、Git 对象和归档引用、共享仓库及审计目录可访问性。外部工具不受 DOMO 锁约束；备份期间必须停止外部修改，校验和不代替系统级原子快照。备份包含提示词、产物及仓库内容，应按敏感数据保管；外部 CLI 凭据和模型服务不在备份范围。

恢复将资源映射到新目录，并重写数据库中的工作目录与 Git 管理指针，不改写历史提示词和上下文。原来运行或正在暂停的项目以暂停状态恢复。恢复命令输出启动所需的 `DOMO_DATA_ROOT` 与 `DOMO_WORKSPACE_ROOT`；使用输出值启动服务，核对产物与作业后再继续。指向复制树以外的符号链接仍是外部依赖，不承诺复制其目标。

普通 Git 分支备份不足以覆盖 `refs/domo-archive`。完整备份采用以下方式之一：

```bash
git bundle create <file> --all
```

或者显式推送全部归档引用：

```bash
git push <remote> 'refs/domo-archive/*:refs/domo-archive/*'
```

备份范围还需包含归档项目的 `jobs` 目录、DOMO 数据库和普通工作区产物。恢复校验至少覆盖数据库关联、归档提交可读、作业资产存在和普通工作区产物可访问。

## 10. Web/API 技术约束

### 10.1 状态与操作

项目暂停只限制项目派发，不批量改写任务暂停意图；强制暂停终止运行作业，将被中断且没有独立暂停意图的任务留在待派发状态，项目恢复后继续。任务依赖等待阶段的状态为空，依赖满足后进入执行阶段并排队。

人工待办由服务端统一以事项为单位返回，列表、详情、导航与待办页使用同一来源；前端不根据项目阶段重新分类待办。任务人工 gate 与项目是否仍可推进分别表达。等待起点读取 gate 状态事件，不以项目最近更新时间代替。任务待办包含受影响后继数量及里程碑影响，导航数量按事项累计。界面确认方案时携带完整已审查草稿，服务端比较当前草稿并拒绝过期确认。

验收作业保存 `execution_job_id`，派发时引用本任务的执行作业，原地重试保留关联。作业摘要与验收接口返回该引用，前端直接据此分组，不按时间或截断偏移猜测归属。事件分类由公共表现层定义，时间线与执行摘要共用。数字直接展示格式化结果，不维护跨组件的动效缓存。

浏览器共享一个 SSE 连接，按项目筛选事件，短时突发事件合并刷新。项目详情请求串行并合并重复请求，在途读取期间发生的刷新请求保留一次后续读取；SSE 正常时使用低频轮询兜底，断线时恢复常规轮询。

- 服务端是项目、任务、作业和队列状态的权威来源。
- 页面过滤、任务列表/DAG 视图选择属于临时页面状态，不作为长期偏好持久化。
- 长时间操作提交后禁用重复入口，并通过服务端状态或事件呈现执行中、成功、幂等成功和失败。
- 阻塞操作必须携带当前请求或代际标识，避免回答旧问题、确认旧方案或处理已失效裁决。
- 强制暂停、归档、人工指定 Agent 和 Git 合入需要明确确认输入，服务端仍执行权限与状态校验。

### 10.2 DAG 投影

DAG 视图由依赖数据计算拓扑层级，同层任务并列，边由前置任务指向后继任务，派生关系使用独立边类型供界面显示虚线。

布局算法必须处理：

- 依赖目标缺失；
- 自依赖或循环依赖；
- 已取消任务过滤后的孤立关系；
- 无法完成拓扑排序的异常数据。

异常时输出可诊断信息并终止布局计算，界面保留列表访问能力。键盘 Enter/Space 与点击使用同一任务打开命令。

### 10.3 接口边界

客户端与服务端使用当前接口契约，不提供旧客户端降级分支。领域事实只由服务端计算，前端负责文案、布局与交互状态。

### 10.4 界面呈现与可访问性

- `web/src/styles.css` 集中定义颜色、控件圆角与动效变量；浅色背景上的成功、警告和错误文字使用对应的深色语义色，不直接使用亮色状态点颜色作为正文颜色。
- 页面首屏优先呈现目标、进展与操作；辅助使用说明通过原生 `details/summary` 按需展开。项目检索在当前快照上匹配名称、目标、路径和分支，分词取交集，并与阶段、状态、待办筛选组合；默认按最近更新时间排序，不修改原始快照。
- 导航提供当前页语义与跳转到主内容的键盘入口，交互控件保持可见焦点。任务进度提供 `progressbar` 数值与可读说明，尚无任务不显示为已完成。
- 任务抽屉与 Agent 编辑面板打开时锁定背景滚动，Tab 在面板内循环（包含折叠标题），Escape 关闭并恢复触发位置的焦点；关闭后还原背景滚动样式。
- 表单与 Agent 网格的最小列宽受容器宽度约束；窄屏导航使用独立横行，不依赖隐藏页面溢出来容纳控件。用量明细的横向滚动区可键盘聚焦，名称列固定在滚动区左侧。
- 首次读取失败展示错误与重试入口，不展示代表真实空数据的成功空状态；操作错误在对应操作区域内呈现，不被后台读取成功覆盖。
- 概览的当前进展与下一步先于契约、共享信息及产物；参考内容默认折叠，工作区中断警告仍常显。项目列表的高级筛选与默认团队配置按需展开，不以控制区挤占内容首屏。
- 方案待确认徽标只在分析阶段出现；任务运行、排队以服务端 `status` 为准，`pending` 依赖等待不冒充 Agent 排队。作业数与自动尝试、拒绝计数分别标注，后者不等于历史执行轮次。
- 任务打开按钮与队列调整按钮是同级独立控件，不在按钮语义内部嵌套可聚焦操作。任务历史最新在前，默认最近三轮；历史反馈默认折叠并明确不代表当前问题，抽屉提供区块定位入口。
- 关键事件过滤机械状态同步事件，摘要只保留可读结论，不混入 Agent JSON 输出；原始消息按需读取，事件列表每次展示二十条并保留更早记录入口。
- 用量覆盖按指标保留，部分合计使用可聚焦标记提供完整覆盖说明，不在每个数值后重复长文本。费用始终表示 Agent 上报值，不作为实际账单或免费使用的结论。

## 11. 持续扩展约束

### 11.1 扩展角色或 Agent 类型

需要同时明确：

- 项目作业或任务作业归属；
- 角色结果文件协议与校验；
- 默认团队、项目池和任务池成员规则；
- 调度、失败分类、会话和用量适配；
- 界面展示、事件和审计关联。

### 11.2 扩展工作区类型

工作区适配器必须实现通用交付与审计能力。任务状态机不得直接假设分支、worktree 或 Git 引用存在。类型专属信息通过能力描述驱动界面展示。

### 11.3 扩展任务或项目流程

- 保持阶段与状态正交，不用额外阶段表达排队、冷却或等待人工。
- 所有状态入口和出口都需要事件、恢复规则和人工可理解的阻塞原因。
- 影响 DAG 的操作必须验证无环与依赖完整性。
- 影响交付契约的操作必须明确版本引用和任务、产物影响。
- 跨数据库、进程和 Git 的操作必须具备幂等键、中间状态和恢复路径。

### 11.4 扩展存储与接口

- 数据结构以当前版本为准，不维护历史数据或旧客户端兼容层。
- 事件 payload 和结果文件协议需要版本化校验，解析失败不能静默接受。
- 实体删除优先评估审计引用、任务池快照和归档关联，不能破坏回溯链路。

## 12. 技术验收清单

每次涉及核心流程的开发，至少覆盖与改动相关的以下验证：

- 方案确认和重规划应用的并发提交、重复提交与中断恢复；
- 普通工作区交付文件不使用 Git，内部共享仓库可用；
- DAG 缺边、自环、成环和派生依赖处理；
- 任务池创建时快照、空池保持与排序启停独立性；
- Agent 优先级、让位、人工指定、冷却与一次性跳过；
- 超时、卡死、缺少结果文件、协议错误和会话能力差异；
- Git 合入成功、已是最新、脏工作区、冲突、引用更新失败与恢复失败；
- 归档进程终止、未提交改动保留、归档引用与 `jobs` 资产完整；
- 备份恢复后的数据库关联、提交、产物和作业审计可访问；
- 未知用量、事件关联和界面异常 DAG 的可诊断性。
