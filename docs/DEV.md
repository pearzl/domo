# DOMO 开发契约

> 本文约定仓库整体层面的规范：目录用途、文档职责、可入库内容、测试与验收、变更与合并要求。

## 1. 目录结构与使用规范

- server/：后端代码，按 Rust 社区规范执行。
- web/：前端代码，按 React 社区规范执行。
- tests/：测试脚本，只放可执行脚本，用例说明写脚本头部注释，不建子目录，不放运行产物。
- docs/：参考 [README.md](../README.md#文档) 的说明。
- 根目录：只存放工程运行和展示的必要内容，不得新增临时文件、笔记、一次性脚本等。


**docs 目录的边界**

- `DESIGN.md` 是唯一的产品设计文档；`DEV.md` 是唯一的仓库级开发规范。
- `docs/notes/` 保存所有值得长期保留的思考，包括但不限于已采纳、已否决、未决与被取代的方案；它不是当前行为说明，也不承担路线图。
- **禁止**在 `docs/` 新建测试用例说明、验收标准说明、冒烟报告、阶段总结、截图、过程记录。这些内容：
  - 用例与验收标准 → 写进 `tests/test_*.sh` 的头部注释；
  - 运行结果、日志、快照 → 放 `data/`（已忽略）或 `${TMPDIR:-/tmp}`；
  - 模块级约定 → 写进对应源码文件头。
- 需要新增一篇文档（例如 API 契约）时，先确认它会被长期维护，再在本文的第一节登记；否则不建。

**通用规则**

- 新建目录前，先确认现有目录能否承载；**不允许“随手建一个目录放文件”**。确需新增目录，必须在本文登记用途。
- 一次性产物（临时脚本、备份、截图、导出、实验代码）一律进 `data/` 或 `/tmp`，不留在源码树里。

## 2. 文档职责与写作约束

1. **DESIGN.md**：只写核心产品能力和设计思路。不写技术实现。
2. **README 只做入口**：说明产品是什么、核心体验、如何启动、文档在哪；不维护“当前状态”、路线图或变更记录。
3. **规划中的内容始终放在最后一节**：`DESIGN.md` 的未实现产品能力放在“未来能力”；不得在正文其他位置混入规划项。
4. **文档和注释只写现状**：必须始终描述**完整现状**，不得进行迭代过程式说明和解释。
5. **notes 是唯一例外**：`docs/notes/` 按话题组织文档，每个文档讨论一个话题。按时间顺序追加；更正事实错误时追加更正说明，不删除原记录。

## 3. 可入库内容约束

**可以入库**

- 源代码与测试代码（Rust `#[test]`、前端源码）。
- 构建与依赖配置、锁文件：`Cargo.toml` / `Cargo.lock`、`package.json` / `package-lock.json`、`tsconfig`、`vite` 配置。
- 值得维护的文档：`README.md`、`docs/DESIGN.md`、`docs/DEV.md`、`docs/notes/`。
- 测试脚本：`tests/test_*.sh`。

**不得入库**

| 类别 | 例子 |
|---|---|
| 构建产物与依赖 | `server/target/`、`web/dist/`、`web/node_modules/` |
| 运行时数据 | `server/data/`、`*.db` / `*.db-wal` / `*.db-shm`、`*.log`、`*.out` |
| 工作区与隔离目录 | `~/.domo/workspace/`、任何项目或任务工作区目录 |
| 归档与一次性产物 | 冒烟存档、验收快照、报告导出、日志包、截图、视频、压缩包 |
| 凭据与个人环境 | token、API key、私钥、含本机绝对路径的配置；需要说明时用占位符或环境变量 |
| 编辑器 / 系统垃圾 | `.DS_Store`、`Thumbs.db`、`.idea/`、`.vscode/`、`*.swp`、`*~` |
| AI 辅助文档 | `AGENT.md`、`CLAUDE.md`、`GEMINI.md`、`.cursorrules`、`.windsurfrules`、Copilot 指令文件等本地辅助说明 |

**执行要求**

- 提交前先看 `git status`：每个改动都能解释来源，不夹带无关文件；新文件先确认归属目录。
- 不通过修改 `.gitignore`、`git add -f` 等方式绕过上述约束；确需例外时必须在提交信息里写明。
- 仓库保持轻量，任何改动都不应让它显著膨胀。

## 4. 测试与验收标准

改动的最低验证门槛：

```bash
# 在 server/ 下
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
```

```bash
# 在 web/ 下
npm run build    # tsc + vite，类型错误即失败
```

- 冒烟脚本放 `tests/test_*.sh`（Windows 原生冒烟脚本放 `tests/test_*.ps1`），**默认使用 mock agent**，不依赖真实模型与外网；真实模型用例通过环境变量传模型（如 `DOMO_RT_MODEL`），**不把模型名写死在脚本里**。
- 临时目录统一用 `${TMPDIR:-/tmp}`（PowerShell 用系统临时目录）；端口通过 `DOMO_*_PORT` 覆盖；脚本退出码 `0` = 全部通过，结束必须清理自己启动的进程与临时文件。
- Windows 改动必须额外运行 `powershell -NoProfile -ExecutionPolicy Bypass -File tests/test_windows.ps1`；`.sh` 用例可在 Git Bash 中运行，依赖 `python3` 与 `curl`。依赖 Unix 信号或 shebang 脚本的用例（如 `test_shutdown.sh`、`test_agent_adapters.sh`）仍需在 Linux/WSL 中运行。
- **修缺陷必须带回归用例**：Rust 单测（纯逻辑 / 解析 / 数据）或冒烟断言（流程 / 接口 / 事件），至少其一。
- 涉及并发、锁、调度、恢复的改动，必须验证错误路径：进程被杀、Agent 超时、限流熔断、数据库锁竞争。
- 验收以“能实际使用”为准：改完后服务要能启动、视图要能刷出数据，不以“编译通过”作为完成标准。

## 5. 合并要求

- 长期分支只有 `main`；所有改动在短生命周期的特性分支或本地分支上完成，**不在 `main` 上直接开发**。
- 合并进 `main` 一律**先 rebase、再压缩为单个提交**，禁止对 `main` 强推。
- `main` 必须保持**线性历史**：禁止 merge commit（`--no-ff`）、禁止交叉合并、禁止把多个不相关改动塞进同一次合并。
- 提交信息按 Conventional Commits 1.0.0：首行 type(scope): 做了什么，正文写“为什么 / 影响面”。
- 合并前必须通过第 4 节的验证门槛；合并后再本地启动一次，确认服务可用。

## 6. 其他要求

1. **文档同步**：docs 内容必须与实际情况一致，同步更新 `README.md`（核心体验与文档索引）。
    - 产品功能有变化先改 `docs/DESIGN.md`。
    - 开发约定有变化先改 `docs/DEV.md`。
