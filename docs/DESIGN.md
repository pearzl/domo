# DOMO 产品设计

> 本文详细说明 DOMO 的产品功能和设计思路，技术实现约束见 [TECH](TECH.md)。（本文由人工维护，AI不得擅自修改）

## 0. 产品目标

DOMO 是一个面向个人用户使用的，单机部署的产品。通过多个 Agent 的分工与协作，在交付效果与总成本之间取得平衡，实现目标的可靠交付。

不同 Agent 产品的定价、能力和适用场景各不相同，同一个 Agent 也不一定适合承担所有工作。DOMO 的产品理念是让不同复杂度和能力要求的任务交给合适的 Agent：明确、简单的工作可以使用低成本 Agent，复杂或关键的工作使用能力更匹配的 Agent，避免所有工作都使用高成本 Agent，也避免只追求低价而因反复失败和返工增加成本。

这种平衡以满足交付契约为前提，关注完成一个合格目标的总成本，而不是单次调用的最低价格。总成本既包括规划、执行、验收和返工产生的调用费用，也包括用户监督、判断和收尾的时间投入。多 Agent 协作、任务拆分和验收是实现这一目标的手段，不以 Agent 数量、任务数量或并行度本身作为产品价值。

**面向个人**意味着不需要现实中的协作与沟通，DOMO 实现一个人就是一支团队的现实目标。任何想法都可以由 AI 帮助你实施落地。

**本地**意味着除了你提供的大语言模型调用，所有数据都保留在你的电脑上，没有云端接入和账号体系，你拥有全部的控制权。Git 为软件交付提供隔离与合入能力，不构成其他交付场景的使用前提。

**单机**意味着它可以直接部署在你的笔记本上，不需要昂贵的硬件成本。


## 1. 领域模型

### 1.1 项目

项目是为了达成一个明确目标，在有限资源和范围内，组织起来的一次性交付单元。它承载：

- 最终的交付目标
- 项目分析与方案
- 任务DAG（含里程碑任务）
- 独立的运行时配置
- 整体进度与状态
- 总结报告

### 1.2 任务

任务是项目内的可独立执行、验收的最小单元。它承载：

- 局部的细节设计、执行和验收
- 由项目继承的独立运行时配置
- 阶段性产物、结论与里程碑

*里程碑是任务的一个特殊标记，被标记的任务需要人工进行二次验收。*

### 1.3 Agent 角色

Agent 将扮演多种角色，分别是：
- 规划者：持有项目整体信息，负责与人讨论项目目标、给出项目方案并拆解任务，最终交付验收。
- 执行者：持有简略的项目信息和任务目标，对任务目标进行设计和实现。
- 验收者：持有简略的项目信息和任务目标，对执行者的工作进行核验。

角色的划分不仅用于设置不同提示词，也用于按工作职责配置不同的 Agent 和模型。结合任务专用 Agent 池，用户可以根据任务复杂度、能力要求和验收风险分配合适的 Agent，不要求规划、执行和验收使用相同成本档位的能力。

不同角色可以分配给不同的 Agent 和模型，一个 Agent 也可同时扮演多个不同的角色。角色分离本身不保证交付质量，成本与效果的判断以实际产物、验收证据和返工情况为依据。

### 1.4 作业

一次 Agent 调用被称作一次作业。作业分两类：由任务推进的作业称为任务作业，执行者与验收者的调用属于此类；由项目阶段推进的作业称为项目作业，规划者的项目分析、直接完成与总结调用属于此类。

### 1.5 工作区

每个项目拥有一个由 DOMO 维护和管理的工作区，用于存放项目运行中的所有相关信息。如任务产物、作业输出……

工作区分为普通工作区和 Git 工作区，分别对应非 Git 仓库项目和 Git 仓库项目。

- 普通工作区：选择或创建本地目录，用于不依赖 Git 的交付目标。项目分析、任务执行、验收和审计不调用 Git，产物与作业记录在归档后保留。
- Git 工作区：沿用仓库、worktree、任务分支、项目交付分支与合入能力。

普通工作区采用串行调度，同一项目同一时刻只推进一个任务。DAG 用于表达依赖与执行顺序，任务派生的子任务也依次执行。普通工作区不提供任务并发和隔离能力。

项目列表与详情按工作区类型展示对应信息。普通工作区不展示 base 分支、交付分支、合入状态和 Git 恢复命令。

Git 项目利用 worktree 对不同任务进行并发隔离。任务完成或项目归档后，DOMO 回收任务执行资源，同时保留任务原工作区位置、回收时间和审计所需产物。工作区有未提交改动时，归档需要用户确认，确认后保留该工作区。

### 1.6 交付契约与产物

交付契约是项目目标、验收和执行约束的版本化载体，包含：

- 要解决的问题与预期交付物
- 验收标准与关键假设
- 其他约束和说明

规划、执行、验收和报告引用同一份契约。目标或约束需要调整时形成可审查的版本，并说明对任务与产物的影响。

任务与项目可以声明预期产物。产物清单记录文件或目录、产物类型、格式、来源任务、版本与验收方式。项目详情提供产物查看、预览、打开所在目录和版本回溯入口。原始输入、任务中间产物与最终交付物具有明确区分。


## 2. 核心流程

我们的目标是：用户输入 -> AI 执行 -> 结果产出。

这个模型描绘的场景令人兴奋，但现实中受限于自然语言的表达能力和 AI 的智能水平，最终的表现并不总是令人满意。事实上即便是由人组成的团队来负责执行，也很难做到一次达成。因此需要设计一套通用的流程和信息交换方式来帮助 AI 准确执行人的输入。

### 2.1 项目分析

输入的项目目标几乎总是模糊的，如前所述这种模糊来自自然语言的限制、不同的上下文信息和理解能力的不同。项目分析阶段同时完成目标确认和项目规划：规划者阅读仓库、澄清目标，并给出可执行的项目方案。

项目分析由规划者角色完成，输出三类结果：
- 提问：只有缺少会改变任务拆分的关键信息时才向用户提问，用户回答后继续分析。
- 项目方案：给出确认后的目标、关键假设、项目级验收口径、范围边界和任务 DAG。任务必须可独立执行、独立验收，任务之间用依赖表示且无环。
- 直接完成：目标简单到不需要拆分任务时，由 AI 一次性完成实现、自检和总结。

项目分析包含两个可以独立跳过的步骤： AI 向用户提问澄清，以及用户对方案做最终确认。项目可以设置确认方式：
- 人工确认（默认）： AI 给出方案后，必须等待用户确认，DOMO 才创建任务并进入执行，或开始直接完成。
- 自动确认： AI 可以在结果中声明方案已明确，DOMO 直接开始执行； AI 认为仍有歧义时，仍应提问或等待确认。

任务只在方案被确认后创建。直接完成不经过独立验收者，自检结果作为项目报告的一部分；项目报告仍必须经过人工验收，项目才进入完成阶段。

自动确认只影响项目分析阶段，不跳过项目报告的人工验收。

重规划同样经过项目分析阶段。已确认目标是重规划不可修改的边界，只有用户主动修改目标的入口可以写入新目标。偏离当前目标的规划或直接完成草稿一律无效。

重规划请求暂停后续任务派发，等待在途作业结算后生成独立草稿；旧任务、报告、目标与验收口径在分析期间保持可恢复。用户可以放弃重规划并恢复本轮最初目标、旧计划与对应报告。草稿标明取消任务、保留任务、范围扩大与验收变化。草稿生成后无需人工确认，不受项目的方案确认方式影响；DOMO 应用草稿时取消旧任务与作业、创建新任务并切换项目状态。应用过程具备原子性，进程中断后可以恢复，每轮重规划的记录均可审计。

### 2.2 任务执行

按任务描述进行具体执行。任务执行由执行者完成。

根据执行的实际情况 AI 可以请求对项目重新规划。例如原规划中存在明确的事实错误导致当前任务无法达成。
此时执行者应当把当前的具体问题提交给规划者，请求规划者重新进行[项目分析](#21-项目分析)。

AI 也可以对当前任务进行再次拆分，[派生](#24-任务派生)更多子任务。

### 2.3 任务验收

按任务验收标准对执行阶段的结果进行核查。任务验收由验收者完成。

验收结果只有通过或者拒绝两种。验收记录必须列出对照的验收标准、检查的产物及版本、实际执行的检查与结果，以及未覆盖的假设、风险和人工检查项。验收被拒绝时退回执行者再次执行，并附上拒绝原因。

普通工作区的任务在所需验收全部通过后完成。Git 工作区还需由 DOMO 把任务分支合并到项目交付分支，合并成功任务才完成；合并冲突时任务退回执行者解决冲突，解决后重新验收，该流程与验收拒绝相同，但不计入验收失败次数。

里程碑任务在验收者验收通过后等待人工二次验收。人工验收通过才满足任务的验收条件；人工验收拒绝时退回执行者再次执行，并附上拒绝原因和指导意见。里程碑人工验收未通过计入验收失败次数，未通过前任务不能完成，依赖该任务的后继任务不能启动。

如果多次验收都未通过，则应该交由规划者判断，规划者可选择修改验收标准重新验收，或保持现状交由[人工裁决](#5-人工裁决)。

### 2.4 任务派生

任务派生是将一个复杂的，工作量巨大的任务拆分成多个小的、可并行的任务。这个过程很像项目规划的任务拆分，区别是：
- 任务派生由执行者决定，而项目规划由规划者决定
- 派生任务不调用验收者，其验收结果直接视为通过，等同于由始终返回通过的验收者处理
- 派生任务不能再继续派生新的子任务，以避免无限递归的情况
- 派生的所有子任务之间没有相互依赖关系

任务派生后[任务阶段](#33-任务阶段)变更为待启动，同时所有派生的子任务在 DAG 中自动成为该任务前置任务。
父任务在某一轮作业结束时提交派生请求，之后等待所有子任务完成后将他们的输出作为自己新一轮作业的输入，继续自己的任务阶段流转流程。

派生任务仍然是任务，除验收者调用外，其阶段、状态、完成条件与工作区合入规则均与普通任务相同。派生任务失败、取消或完成时对父任务的影响，与普通前置任务对其依赖任务的影响相同。

### 2.5 人类干预

在项目完成前，人可以随时对项目进行干预。干预的目的是对 AI 的工作进行指导和纠偏。干预的手段包括：
- 要求重新进行[项目分析](#21-项目分析)
- 将任意未完成的任务标记为里程碑
- 对任意未完成的任务进行指导，指导的内容将在下一次作业时生效
- 修改[项目和任务状态](#3-阶段和状态)：暂停、强制暂停、归档/取消、继续等
- 增加新任务并添加到 DAG。增加新任务可能导致已完成/总结阶段的项目重新回到执行阶段，原项目报告需要重新撰写。

### 2.6 项目验收和总结

所有任务完成后，项目进入总结阶段，由规划者根据交付契约进行项目验收。项目验收记录与任务验收一样，必须列出验收标准、产物及版本、检查与结果，以及未覆盖的假设、风险和人工检查项。

项目验收通过后，规划者撰写项目报告并交给人工验收，项目保持在总结阶段。项目验收不通过时，规划者根据实际情况请求重新进行项目分析，或者请求人工裁决。

### 2.7 人工验收

流程与验收者相同，都是通过或拒绝两种，同时附上拒绝原因。但根据不同的场景，人工验收还有额外的处理策略：

- 里程碑验收：可要求重新规划或重新执行，附带指导意见；任务流转遵循[任务验收](#23-任务验收)的规则。
- 项目总结：可针对报告内容进行多轮讨论，并要求重新撰写、重新规划执行或增加新任务。

### 2.8 项目合入

项目进入完成阶段后，人工可以把项目交付分支合入目标分支。合入是 Git 项目的可选后续操作，不属于项目完成条件，也不延伸到发布或上线流程：

- 合入前将项目分支整理到项目创建时记录的 base 分支之上，随后快进目标分支。历史保持线性，不产生 merge commit。
- 目标分支在某个工作区检出时，合入要求该工作区没有未提交改动；有改动时拒绝合入，项目分支与目标分支都保持操作前状态。
- 整理项目分支时发生冲突或失败，合入终止，项目分支与目标分支都保持操作前状态，错误信息列出冲突文件。DOMO 不自动解决冲突，不强推。
- 无论目标分支是否已检出，合入结果都必须保持线性历史，目标分支只能快进到项目分支提交。
- 合入成功记录合入时间与项目分支提交。目标分支已包含项目分支提交时，再次合入返回“已是最新”，不产生新的提交、不改变分支状态。

## 3. 阶段和状态

阶段描述进行到哪一个步骤，状态描述是运行的状态。

很多时候他们容易被混淆，例如，一个任务因为前置任务未完成，和在 Agent 队列中排队，给用户的感受都是它没有在执行。

我们使用两个正交的维度来描述，希望能准确的表达这种差异。

### 3.1 项目阶段

项目阶段包括：
1. 项目分析：项目创建后自动处于该阶段，即项目的初始阶段。规划者在此阶段完成目标澄清、方案确认和任务规划。
2. 执行：方案确认后创建任务并进入该阶段；任务发起的重规划请求被同意也会将项目重置到项目分析阶段。
3. 总结：项目中所有任务完成后，规划者进行项目验收并撰写项目报告，随后等待人工确认和验收；项目验收不通过时可请求重规划或人工裁决。
4. 完成：项目报告和最终结果被人工确认验收后就进入完成阶段，标识整个项目成功结束。

### 3.2 项目状态

普通暂停和强制暂停对项目与任务采用相同的在途作业处理规则：普通暂停只停止后续作业派发，在途作业不受影响，仍可产生流程允许的任何结果；强制暂停终止在途作业进程，未保存输出直接丢弃。

项目状态包括：
1. 阻塞中：项目无法自动流转，需要外部驱动。项目创建后因为还没有输入目标，因此自动处于该状态。等待用户回答澄清问题、确认方案、验收里程碑或项目报告，以及等待人工裁决，且没有其他可自动推进的项目作业或任务作业时，项目也处于该状态。
    - 进程重启后的恢复过程中，项目也处于阻塞状态，当状态全部恢复后自动解除阻塞进入运行中。
2. 运行中：只要项目中有任何项目作业或任务作业可以无需人工干预地继续执行，项目就处于该状态，包括项目分析、直接完成和项目总结作业。
3. 暂停中：用户命令项目暂停后进入该状态。项目中所有任务同时暂停；恢复时所有任务同时恢复，不保留任务在项目暂停前的单独暂停状态。
4. 已暂停：用户命令项目暂停后，项目中所有作业都已经停止，自动进入该状态。
5. 已归档：由用户触发的不再关注的项目，无论项目处于哪种阶段都可以进行归档操作。
    - 已归档的项目立刻停止所有 Agent 作业派发，在途作业的终止方式与强制暂停相同。
    - 已归档后的项目无法恢复重新执行，但依然可对执行情况进行[回溯和审计](#7-审计与回溯)

*项目可以被取消，取消也视为归档操作*

### 3.3 任务阶段

任务阶段包括：
1. 待启动：前置任务未完成时。
2. 执行：全部前置任务完成时。
3. 验收：执行阶段结束时。验收未通过或 Git 工作区合并冲突时回到执行阶段；派生任务按[任务派生](#24-任务派生)的规则处理验收。
4. 完成：满足[任务验收](#23-任务验收)规定的验收与工作区交付条件时。

### 3.4 任务状态

任务状态包括：
1. 阻塞中：任务无法自动流转，需要外部驱动。如存在尚未被答复的人工裁决请求。
2. 运行中：Agent 正在执行对应阶段的作业。
3. 队列中：对应角色的 Agent 尚未被释放。
4. 暂停中：用户命令任务暂停后进入该状态，在途作业按上述统一暂停规则处理。
5. 已暂停：用户命令任务暂停后，且所有作业都已停止，自动进入该状态。
6. 已取消：不再继续推进的任务，可能处于任意未完成阶段。如被项目重规划后丢弃的旧任务。

## 4. Agent 池

Agent 池就是一支等待调度的 AI 团队。

Agent 池承载用户对能力与成本的配置策略：角色池用于区分规划、执行和验收的能力投入，任务专用 Agent 池用于区分不同任务的能力投入。用户可以按任务复杂度和能力要求调整候选 Agent、优先级与启停状态；调度器按这些配置选择 Agent，不自动根据任务复杂度判断能力档位或升级 Agent。

项目和任务会使用已配置的 Agent 池，按池的调度策略自动使用。
项目的 Agent 池继承自系统已配置模板，任务的角色池继承自项目，但均可独立修改优先级和启用规则。

### 4.1 配置

Agent 由用户提供，对项目和任务提供相同的能力，包括：
- 模型选择
- 负载队列，如：可并行的最大数量
- 异常检测，如：进程卡死检测
- 可用性计划，如：按时间规划、按用量规划
- 角色选择优先级
- 并发已满时让位，如：达到最大并发后允许同角色池中后续优先级的 Agent 接手

并发已满时让位是 Agent 级开关，默认关闭。项目池、任务池与默认团队共用这一个值，不提供池级覆盖；开关在 Agent 团队页的 Agent 编辑表单中设置，角色池面板只读展示“可让位”徽标。

默认团队覆盖全部已注册 Agent：每个 Agent 按其角色自动出现在对应的角色分组中，注册 Agent 或修改其角色后自动同步。角色池的成员由全局 Agent 的角色决定，用户只调整角色内的顺序与启停。

### 4.2 队列

当多个任务同时调度到同一个 Agent，且任务数量超过 Agent 的最大负载时，任务就会按调度的先后顺序开始排队。此时用户可以选择：

- 不做干涉，等待 Agent 顺序执行
- 暂停/强制暂停执行中的任务，提前释放 Agent
- 调整队列中未开始的任务的排队顺序

Agent 队列是系统全局的，同一个 Agent 的所有作业共用一个队列。

### 4.3 可用性计划

可用性计划帮助用户自动启停 Agent，合理规划来自不同供应商的账单成本。支持的计划维度有：
- 按时间：针对限时免费和折扣活动，最大化利用优惠政策。
- 按使用量：当 Agent 达到设定阈值后自动禁用。使用量的说明参考[成本与用量](#6-成本与用量)

### 4.4 优先级与调度

每个 Agent 在每个角色下都有一个优先级，同一角色的优先级编号连续且不重复，数字越小优先级越高，0为最高优先级。

当需要对应角色的 Agent 时，按优先级升序检查角色池。可用指：全局启用、项目 Agent 池对应角色启用、任务 Agent 池启用、具备该角色、未被删除、不在冷却中、处于可用时段且未达到用量限额。执行者与验收者使用任务 Agent 池，同时受项目 Agent 池对应角色的启停约束；规划者使用项目 Agent 池。

并发满额时的派发由 Agent 的“并发已满时让位”开关决定：

- 关闭：第一个可用且未满的 Agent 独占该次派发。该 Agent 满额时派发等待它释放，等待原因展示该 Agent 名称与并发占用，不检查后续优先级。
- 开启：满额 Agent 让位，调度按同角色池继续扫描下一优先级，可以连续让位多个满额 Agent。遇到关闭开关且满额的 Agent 时扫描停止，由该 Agent 承担等待，等待原因展示它的名称与并发占用。全部让位的 Agent 之后仍无 Agent 接手时，展示所有让位 Agent 及其并发占用。

让位只作用于并发满额：不可用判定、冷却、可用时段、用量限额与失败换人的处理都按同一规则执行，不因开关改变。发生让位时，排队信息说明被让位的 Agent；人工指定的派发明确标注“由人工指定”。

人工指定 Agent 的派发遵循[人工裁决](#5-人工裁决)中的例外规则。

除让位外，只有高优先级 Agent 不可用时才检查下一优先级；没有发生让位且全部 Agent 不可用时，阻塞信息逐个列出每个 Agent 及其不可用原因。

正常调度不使用上次执行者做轮转，同一任务重新执行时仍从最高优先级的可用 Agent 开始。

作业每轮运行上限为 10 小时；超时后最多继续 2 轮。连续 30 分钟没有运行输出时判定卡死。

作业失败后的处置对任务作业和项目作业一致：

- 作业失败时按失败原因分类，记录在作业与 Agent 上。原因分为限流、供应商波动、永久错误、协议失败和任务失败。
- 限流：立即让该 Agent 冷却，冷却时长取 Agent 返回的重试信息，没有信息时使用默认值。
- 供应商波动：同一 Agent 先按有限次数重试，次数用尽后让该 Agent 冷却并换人。
- 永久错误：不在该 Agent 上重试，直接换人。
- 协议失败：Agent 正常结束但没有产出符合角色协议的结果。缺少结果时，在同一作业内最多追加 5 轮继续提示，并提示执行者可以派生子任务。5 轮后仍无有效结果则阻塞，不切换 Agent。
- 任务失败：如执行者报告失败、验收未通过，属于任务自身的问题，不更换 Agent。

需要换人时，本次派发记录一次性跳过失败 Agent 的状态：下一次派发跳过它，派发成功后清除。项目作业的跳过状态记在项目上，规划者的分析、直接完成和总结作业共用同一份记录。

换人后作业按原阶段重新派发：

- 任务作业：任务保持队列中，重新派发前按任务池优先级选人。
- 项目作业：项目保持运行中，由调度器重新派发，按项目池优先级选人。

只有任务作业或项目作业在本角色下已经没有可用 Agent 时才进入阻塞，等待[人工裁决](#5-人工裁决)。阻塞原因记录失败原因；阻塞后不清理 Agent 冷却，也不由调度器自动重派，重新派发需要人工重试或裁决。

### 4.5 启停与角色池修改

启停分为三层，任一层停用都不再向该 Agent 派发新作业：

- 全局开关：Agent 团队页的 Agent 级开关，影响所有项目与任务。
- 项目池开关：项目 Agent 池与默认团队中按角色的启停。项目 Agent 池的角色启停只影响当前项目，并屏蔽该项目已有任务的同角色派发；任务池快照不被改写。
- 任务池开关：任务 Agent 池按角色的启停，只影响该任务。

用户可以修改 Agent 的优先级和启用状态。角色池成员由全局 Agent 的角色决定。

角色内优先级支持拖动条目到目标位置，也支持上移、下移按钮。拖动可直接跨越多个位置；上移和下移与相邻条目交换位置，已在边界时无变化。每次操作保存后，该角色内全部条目按展示顺序连续重排为 0..n-1。

启停状态只有开关两种状态。启停状态不影响优先级的设置。全局开关只屏蔽派发，不改写项目与任务配置。

### 4.6 任务专用 Agent 池

任务专用 Agent 池由项目 Agent 池派生，只包含执行者与验收者两个角色分组。任务创建时把项目池对应角色的全部条目、优先级与启停状态快照到任务池，项目池后续变化不会改写既有任务池。

任务池支持与项目池相同的排序与启停操作，改动只作用于该任务。任务池成员由项目池快照确定，只调整顺序与启停。

执行者与验收者按[优先级与调度](#44-优先级与调度)使用任务池，并受[启停与角色池修改](#45-启停与角色池修改)中的项目池约束。项目池中缺少该条目时不阻塞任务池，历史快照保持可用。任务池为空或全部不可用时，任务保持等待并给出原因，不回退到项目池。规划者仍使用项目池。

## 5. 人工裁决

当系统遇到无法恢复的错误，或 AI 遇到无法解决的问题时，则需要人工裁决。
此时会提供必要信息，包括事件类型、关联项目和任务、其他必要上下文，供人类做出合适的判断。

根据类型的不同可能由不同的处置策略：
- Agent 作业失败：重试、更换 Agent
- 无可用 Agent： 更换 Agent
- 任务核验多次被退回：指导规划者重规划、指导执行者重试、更换 Agent（执行者）、更换 Agent (验收者)

*更换 Agent 的含义是：临时使用指定的 Agent 执行本次任务，可以绕过调度策略、启停状态、角色能力、冷却、可用时段、用量限额和其他可用性限制。人工指定不遵循让位，即使该 Agent 已满额并开启让位开关，派发仍等待它释放。选择界面必须显示风险提示，说明此次调用可能产生额外费用、使用不具备目标角色的 Agent，或在 Agent 正常不可用期间执行。*

作业重试是用户在作业层面解除阻塞的手段，界面上的重试按钮落在具体作业上。任务作业重试复用原作业与原 Agent 会话，以“继续”提示和派生提示重新执行；项目分析、直接完成或总结阶段的作业失败使项目停住时，作业重试让该阶段的作业重新排队，项目随之从阻塞回到运行中。其他原因造成的项目阻塞由对应机制解除，不通过作业重试处理。

作业重试只在派发成功以后才清除冷却与失败计数，并按角色清除，只清除本次重试实际派发到的单个 Agent：项目作业重试作用于规划者，清除项目池规划角色中该 Agent 的冷却；任务作业重试与人工裁决作用于该任务的执行者与验收者，清除任务池对应角色中该 Agent 的冷却。其余 Agent 保持原有退避。


## 6. 成本和用量

DOMO 将记录每次 Agent 调用的成本，包括输入与输出 token 数量，费用与时长。这些记录的信息用于：
- 支持[可用性计划](#43-可用性计划)的实施。
- 对用户提供多种维度的聚合的统计信息。
- 结合验收结果与返工记录，评估不同 Agent 配置完成合格交付的实际成本，避免只按单次调用价格判断性价比。

项目成本包含规划、执行、验收、失败尝试、返工和重规划的调用消耗，不因某次作业未产出合格结果而排除其成本。调用费用与时长用于衡量可记录的投入，不能替代对交付效果和人工监督负担的判断。

统计数据由 Agent 自身提供，无法提供的 Agent 信息也会被明确记录为未知，并在聚合展示时特殊标记。


## 7. 审计与回溯

DOMO 详细记录项目中的所有信息，用户可以在任意时刻对已发生的行为进行详细的分析和溯源。
记录的内容包括：
- 项目的阶段和状态变更
- 任务的阶段和状态变更
- 人工裁决结果
- 异常与恢复情况
- 作业记录，包括起止时间和输入输出

归档项目保留完整的作业审计资产。Git 项目的任务和项目分支提交在归档后仍可追溯，但不进入普通分支列表。备份与恢复必须覆盖这些归档提交、作业记录和普通工作区产物，确保归档项目能够完整审计。

# 用户界面设计

## 1. 全局导航与待我处理

全局导航包含项目、待我处理、Agent 团队和成本用量。待我处理集中展示所有需要人工驱动的项目，包括：

- 待回答的项目澄清问题与待确认的项目方案；
- 待验收的里程碑任务与项目报告；
- 待处理的人工裁决、阻塞作业和无可用 Agent 的项目或任务。

每个待办展示事项类型、关联项目与任务、摘要、当前阻塞原因和等待时长，默认按等待时长倒序排列。点击后打开对应项目、任务或作业的处理位置，用户可以在该位置回答问题、确认方案、验收或裁决。处理完成后事项离开待办列表，导航中的数量同步反映当前待办总数。已归档项目不产生待办。

## 2. 项目列表

项目列表以卡片展示项目名称、目标、工作区类型、阶段、状态、当前阻塞摘要和任务进度。已合入的项目在卡片上显示“已合入”与短提交号。顶部提供创建项目入口，以及阶段与状态两组分类标签：

- 阶段标签取项目分析、执行、总结、完成；状态标签取运行中、阻塞中、暂停中、已暂停、已归档。
- 同组多选为“或”，两组之间为“且”；组内不选表示该维度不过滤。
- 标签显示当前已加载项目中的数量；任一标签选中时提供一键重置。
- 过滤结果为空时显示空状态与重置入口；项目集合为空时显示“还没有项目”。

## 3. 创建项目

创建项目表单包含：

- 项目名称与目标；目标可以稍后补充，未输入目标的项目创建后处于项目分析阶段和阻塞状态。
- 工作区类型与本地目录；普通工作区支持选择已有目录或创建目录，Git 工作区支持选择已有仓库。
- Git 项目的 base 分支，默认使用仓库当前分支，并允许在创建时选择其他分支。
- 方案确认方式，默认人工确认。
- Agent 池与独立运行时配置，默认继承系统模板，创建时可以展开调整。

创建后进入项目详情。项目分析产出的交付契约、验收标准与预期产物在方案区域展示，不以创建表单中的简短目标替代完整契约。

## 4. 项目视图

项目视图包含基本信息、目标与交付契约、任务、产物、项目报告、作业、事件、成本用量和 Agent 池。页头展示阶段、状态、当前推进事项或阻塞原因，并提供暂停、强制暂停、继续、重规划、归档等适用操作。强制暂停与归档需要确认；Git 工作区存在未提交改动时，归档确认还需说明 worktree 保留结果。

交付契约按版本展示目标、范围、关键假设、验收标准和约束，支持查看版本差异及其对任务与产物的影响。产物区域区分原始输入、任务中间产物与最终交付物，支持按任务和类型过滤，并提供查看、预览、打开所在目录与版本回溯入口。

任务面板支持列表与 DAG 两种视图，默认列表，视图选择不作为长期偏好保存。列表支持按阶段、状态和里程碑标记过滤，展示前置依赖、当前 Agent、等待原因和验收结果。

DAG 视图按任务依赖计算拓扑层级：同层任务并列，依赖边由前置任务指向后继任务，派生任务与父任务的关系用虚线表示。节点展示任务 key、标题、阶段与状态徽标、里程碑与派生标记；取消的任务不进入图。节点可以点击或用键盘 Enter/Space 打开任务抽屉。依赖缺失或存在环时给出提示，并保留列表视图作为任务访问入口。

项目详情展示完成横幅。项目处于完成阶段且目标分支尚未包含项目分支提交时，横幅提供“合入到 base 分支”按钮；点击前需要确认，执行期间按钮禁用。成功、已是最新和失败结果都显示在横幅内。目标分支已包含项目分支提交时（包括在 DOMO 之外完成的合入），横幅不再显示合入按钮；DOMO 记录的合入显示目标分支、合入时间与短提交号，刷新后保持。普通工作区不展示该合入横幅。

## 5. 项目分析与重规划

项目分析区域按当前活动展示澄清问题、分析进度或项目方案。澄清问题支持逐项回答和统一提交；项目方案展示确认后的目标、关键假设、范围边界、项目级验收口径、预期产物和任务 DAG。人工确认模式下提供确认入口，确认前可以要求规划者继续调整；自动确认模式展示方案内容与自动执行状态。

重规划区域展示分析进度和草稿，包括取消任务、保留任务、范围扩大与验收变化，以及各任务和产物受到的影响。草稿生成后自动应用，不提供确认入口；应用前可以放弃重规划并恢复本轮最初目标、旧计划与对应报告。应用后保留该代际草稿、差异和结果供审计查看。

直接完成在项目分析区域展示实现、自检和总结结果，不展示空任务列表作为主要内容。

## 6. 人工裁决与验收

人工裁决展示事件类型、关联项目和任务、阻塞原因、相关作业及必要上下文，并根据事件类型提供重试、更换 Agent、指导规划者、指导执行者等操作。更换 Agent 时按[人工裁决](#5-人工裁决)的规则展示风险提示，确认本次选择后才允许派发。

任务与项目验收采用一致的证据布局，展示交付契约版本、逐项验收标准、产物及版本、检查与结果、未覆盖的假设和风险。用户可以在同一视图查看相关产物与作业输出，并通过或拒绝验收；拒绝时必须填写原因。

里程碑与项目报告验收提供[人工验收](#27-人工验收)规定的操作入口。验收期间的对话、意见、证据和结果都进入审计记录。

## 7. 任务视图

任务视图包含任务目标、验收标准、阶段与状态、前置与后继依赖、父子派生关系、里程碑标记、运行时配置、Agent 池、产物、验收记录、作业列表和事件时间线。

用户可以对未完成任务添加指导下一次作业的内容、设置里程碑、调整任务 Agent 池，以及执行暂停、强制暂停或继续。验收区域区分验收者验收与里程碑人工验收，展示每轮拒绝原因、检查证据和退回记录。派生任务展示派生标记和验收状态，不展示验收者作业。

## 8. 作业视图

作业视图展示关联项目与任务、项目阶段或任务阶段、角色、Agent、模型、会话、排队与运行状态、起止时间、等待原因、输入输出和 Agent 实时输出。用量区域展示输入与输出 token、费用、时长以及未知数据标记。

失败作业展示失败分类、重试与换人记录、结果或协议错误、卡死与超时信息。符合重试条件的阻塞作业提供重试入口，重试后仍保留原作业输入输出和完整处置记录。

## 9. Agent 团队与队列

Agent 团队页展示全部 Agent 的启用状态、角色、模型、并发占用、冷却、可用时段和用量限额。编辑表单提供模型、最大并发、异常检测、可用性计划、角色和“并发已满时让位”等配置。

默认团队、项目池和任务池使用一致的角色分组面板，支持启停、拖动排序以及上移、下移。任务池标明其快照来源，项目池对既有任务的约束在对应条目中说明。

全局队列按 Agent 展示运行中和排队中的作业及其所属项目、任务、角色与等待原因。排队中的作业支持调整顺序；运行中的作业支持暂停或强制暂停。人工指定 Agent 时在等待原因和作业事件中保留明确标识。

## 10. 成本用量与审计回溯

成本用量页支持按时间、项目、任务、角色、Agent 和模型聚合，展示 token、费用、作业时长与调用次数。无法由 Agent 提供的数据明确标为未知，不以零值参与汇总；提供原始作业记录入口以核对聚合结果。

项目审计视图以统一时间线呈现项目、任务和作业的阶段与状态变化、人工干预、裁决结果、验收证据、契约与产物版本、异常及恢复情况。用户可以按对象和事件类型过滤，并从事件跳转到相关作业或产物。归档项目保留只读审计入口，Git 项目同时展示归档提交引用和保留的 worktree 信息。
