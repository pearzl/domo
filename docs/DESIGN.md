# DOMO 产品设计文档

版本：v0.2（M1 实施基线）
状态：核心功能定义已定稿，随迭代演进。

---

## 1. 产品定位

- **一句话**：把一群 BYO 的 AI Agent 组织成协作团队，用户作为团队负责人管理项目交付的工作台。
- **开源个人项目**，不考虑商业化。本地优先，数据不出本机。
- **场景边界**：当前需求是 coding 工作台，但**设计目标是通用任务**——所有核心概念（任务、验收标准、产物）不预设为代码。
- **单用户**：一个部署对应一个负责人（后续多用户为非目标）。

## 2. 名词表

| 名词 | 定义 |
|---|---|
| 项目 Project | 一次完整交付，含任务 DAG、里程碑、规划、事件日志 |
| 任务 Task | 最小工作单元，默认含「执行 + 验收」两步 |
| 里程碑 Milestone | 阶段性目标及其效果定义，是人工确认 gate 的锚点；项目可以没有里程碑 |
| 角色 Role | 团队职能标签：`planner`（规划者）/ `executor`（执行者）/ `acceptor`（验收者）/ `decision_maker`（决策者）。**角色是标签不是绑定**，一个 agent 实例可持多角色，但同一任务禁止同一实例既执行又验收 |
| Agent（成员） | BYO 的 agent 实例，登记进团队池，带能力档案 |
| 决策者 Decision Maker | 常设角色，**人类在团队中的代理**：复核所有「更新项目内容/计划」的请求 |
| 决策收件箱 Inbox | 所有需要人拍板的事项的统一入口（升级、gate、重大变更） |
| 验收标准 Acceptance Criteria | 执行者与验收者协商一致的可检验条目，一致后才允许执行 |
| 事件 Event | 不可变审计记录，全系统状态变化的唯一事实来源（事件溯源） |
| 会话 Session | 某 agent 处理某任务某次尝试的执行上下文 |

## 3. 项目生命周期

```
INITIALIZING ──(规划产出)──▶ PENDING_CONFIRM ──(人确认规划)──▶ RUNNING ──(全部任务终态)──▶ COMPLETED
                                 │                          │ │                     │
                                 │                          │ └─── PAUSED ⇄ ───────┘
                                 └──(人不确认，可修改)◀──────┘(里程碑 gate 只挂起下游分支)
                                                            └──(用户取消)──▶ ARCHIVED（=归档，成果全保留）
```

- **INITIALIZING**：由规划 agent 完成调研分析、任务拆解、里程碑与角色分配（M1 阶段为人工/手工建项）。
- **PENDING_CONFIRM**：规划提案提交负责人确认；可修改后确认。
- **RUNNING**：调度器自动推进；里程碑 gate 处人介入确认（见 §8）。
- **PAUSED**：项目级暂停，冻结一切在途流程（**含验收**）；其他项目不受影响。
- **ARCHIVED**：取消即归档——成果、日志、会话记录全量保留，只读。
- **COMPLETED**：产出项目总结报告（M3+）。
- 项目可**没有里程碑**：此时全程无需人工介入（除异常升级）。

## 4. 数据模型

```
Project   { id, name, brief, status, plan(confirmed_at, content), created_at }
Milestone { id, project_id, name, goal, effect, task_ids[], status: pending|awaiting_confirm|passed|failed }
Task      { id, project_id, milestone_id?, title, description,
            depends_on: [task_id],
            assignee_role, executor_agent_id, acceptor_agent_id,
            acceptance_required: bool,          // 豁免=false（由决策者裁定）
            acceptance_criteria: string|null,   // 协商一致后写入
            negotiation_status: pending|agreed|failed,
            status, attempt: int, rejection_count: int, failure_count: int,
            artifacts: [path], created_at }
Agent     { id, name, adapter: mock|opencode|..., roles: [role],
            capabilities: { supports_resume: bool, max_parallel: int },
            status: idle|busy, current_task_ids: [] }
InboxItem { id, project_id, type: escalation|milestone_gate|replan|negotiation_failed|decision_maker_down,
            payload, status: open|resolved, resolution?, created_at }
Event     { id, ts, project_id, task_id?, type, payload }   // append-only
Guidance  { id, task_id, text, created_at }                 // 人工指导，作用于单次任务（M1）
```

## 5. 任务状态机

```
                 ┌────────────(豁免)───────────────────────┐
PLANNED ──(标准协商一致/豁免裁定)──▶ READY ──(依赖满足)──▶ EXECUTING
   │                                ▲                      │
   │(协商失败→决策者裁决)             │(验收退回，重做)        ├─(产物提交)─▶ AWAITING_ACCEPTANCE
   ▼                                │                      │                  │
NEGOTIATION_BLOCKED ────────────────┘                      │        ┌─(通过)──┴─▶ DONE
                                                          │        └─(退回，attempt+1)
                                                          │              └▶ 退回≥2轮 ─▶ ESCALATED(升级待人裁决)
                                                          │
                                          (执行失败)      │
                                          attempt+1 ──────┤── 失败≥3次 ─▶ SUSPENDED(挂起，通知人，
                                                          │                 不阻塞无依赖分支)
任意非终态 ──(项目取消)──▶ CANCELLED
```

要点：
- **PLANNED**：验收标准协商中（M1 无协商，直接视为 agreed）。
- **重做**：验收退回后回到 EXECUTING，携带退回意见；同一任务退回 ≥2 轮 → ESCALATED，交决策收件箱由**人**裁决（换 agent 重跑 / 降低验收标准 / 人工接手 / 放弃）。
- **挂起**：执行失败 ≥3 次 → SUSPENDED，进收件箱；**无依赖关系的其他分支继续跑**。
- **豁免任务**：验收标准协商一致（或裁定豁免）后才进入 READY；豁免由决策者在规划阶段裁定（人工可覆盖）。
- 终态：DONE / CANCELLED。ESCALATED 与 SUSPENDED 为挂起态，人工处理后回到流程。

## 6. 角色与权限模型

| 角色 | 职责 | 决策权限 |
|---|---|---|
| planner | 调研分析、任务拆解、里程碑规划、角色分配建议 | 提案权，无决定权 |
| executor | 执行任务、产出交付物、上报「发现规划问题」 | 请求权 |
| acceptor | 与执行者协商验收标准、验收产物 | 验收通过/退回权 |
| **decision_maker** | 人类代理：复核变更请求、裁定豁免、裁决协商失败 | 见下 |

**决策者权限分层**（已定稿）：

- **决策者可自决**：
  - 验收标准协商失败的裁决；
  - 豁免（免验收）裁定；
  - 不触及已确认里程碑/项目目标的任务级调整。
- **必须升级到人**（进决策收件箱）：
  - 触及已确认里程碑/项目目标的变更；
  - 新增角色或启用新 agent；
  - 卡死升级（执行失败 ≥3 次 / 验收退回 ≥2 轮）的裁决。
- **决策者自身故障**：其待办直接转入决策收件箱等人裁决，相关分支挂起但不阻塞其他分支。
- **角色隔离**：决策者不得同时担任同一项目的 executor 或 acceptor（裁判不下场）；BYO 池过小时允许配置显式打开例外。

## 7. 验收机制

1. **协商**（规划阶段）：执行者与验收者就验收标准协商，一致后写入任务，任务才允许进入 READY。失败由决策者裁决。
2. **验收**：执行完成 → 验收者按验收标准检验 → 通过（DONE）或退回（附意见 → EXECUTING 重做）。
3. **退回升级**：≥2 轮退回 → ESCALATED → 人裁决。
4. **人工复核**：agent 验收过的内容，人可随时在任务详情中复核验收记录（审计），必要时推翻结论。
5. **人工验收**：用户可将任意任务的验收者指定为自己（在任务规划或详情中设置）。

## 8. 调度规则

- 任务按 `depends_on` 构成 DAG；**前置任务全部 DONE → 自动 READY → 派发执行**。
- 并行：无依赖冲突的任务同时派发，受 agent `max_parallel` 与实例占用约束；同一实例同时只跑一个任务（M1）。
- **里程碑 gate**：里程碑内全部任务 DONE → 里程碑进入 `awaiting_confirm`，进决策收件箱等待人工确认；**gate 只挂起该里程碑的下游分支，无关分支继续跑**。
- **里程碑窗口即重规划窗口**：人在 gate 确认/退回时，可顺带**追加任务或调整后续规划**。
- **动态重规划双轨**：
  - 常规纠偏：执行者/验收者上报 → 决策者复核 → 批准（生成新任务/改依赖）或拒绝；触及里程碑/目标的转人。
  - 重大调整：人在里程碑窗口直接做。
- **动态追加任务**：新任务插入 DAG 时校验不引入环；默认带验收（不豁免）。

## 9. 管控操作语义

| 操作 | 语义 |
|---|---|
| 暂停（项目级） | 冻结调度器：不派发新任务；**在途任务跑完当前尝试即停（含验收派发）**；已完成状态保留。自动流程全部冻结，但**人工裁决操作（收件箱处理、人工验收、指导）不被冻结**——人必须在暂停期间也能介入。恢复时从冻结点续跑 |
| 恢复 | 解冻调度器，续跑在途与待派发任务 |
| 编辑 | 名称/项目目标/工作区在非归档任意状态可修改（创建时目标与工作区必填） |
| 取消 | = 归档：停止一切在途会话，成果/日志/事件全量保留，项目只读 |
| 指导 | 对单个任务写入 Guidance（作用于该任务本次尝试），任务下次派发/重做时携带 |
| 介入（任务视图） | 人工介入通道：用户写一段说明 → 规划者 agent（planner 角色，会话与规划共用 memory）分析现状并给出调整方案（新增/修改/取消任务）→ 用户审阅方案、可多轮探讨（每次发送都基于最新任务全貌）→ 用户确认后逐项应用（单项失败自动跳过并汇报原因；依赖按任务标题解析，含同批新增任务；改依赖做环校验；终态任务不可改/取消）。应用过程全程留痕（`replan.proposed` / `task.created|updated|status_changed` 事件）。规划者产出仍是「建议」，是否采纳由人拍板 |
| 汇报/总结 | M3+：里程碑汇报、项目结束总结报告 |

## 10. 异常与恢复

**恢复三档降级**（任务恢复时依序尝试）：
1. **原生会话恢复**：agent 声明 `supports_resume` 且原会话可用 → 直接 resume；
2. **交接摘要重建**：用「目标/已完成/剩余/约束/产物路径」结构化交接书开新会话续作；
3. **人工重建**：两档失败 → 任务 SUSPENDED，进收件箱。

**进程重启**：调度器与任务状态机从 SQLite 事件与状态恢复；SUSPENDED/RUNNING 中断的任务按三档降级恢复。

**BYO agent 接入协议**（能力声明 = 恢复能力的前提）：
- 必备能力：`spawn`（启动执行）、`send`（输入注入）、`observe`（输出读取，流式）、`session_id`（会话标识）；
- 声明能力：`supports_resume`、`max_parallel`、上下文特征；
- M1 为 Mock 适配器；M2 落地 OpenCode 适配器（headless 执行 + 会话恢复）。

## 11. 界面信息架构（三视图 + 收件箱）

1. **项目总览（宏观）**：里程碑进度、任务完成率、风险标记（超期/阻塞/反复退回）、待确认 gate、决策收件箱入口。
2. **任务视图**：看板（按状态列）+ DAG 列表；任务详情：执行日志（流式）、中间产物、验收记录、事件时间线、指导输入。
3. **组织视图**：agent 队列与负载（当前任务、占用、状态）、能力档案、角色分布。
4. **决策收件箱**：全局侧栏，所有待人事项（升级/gate/变更复核），一键跳转对应任务。

## 12. 审计

- 事件溯源：所有状态变化追加 Event（append-only，永不改写）。
- 事件类型：`project.created/confirmed/paused/resumed/cancelled`、`task.created/updated/status_changed/guidance_added`、`task.recovered`（三档恢复审计，payload 固定 `tier/outcome/reason/task_id/attempt/session_id`）、`agent.session_started/session_ended/output`、`acceptance.recorded/rejected`、`escalation.raised/resolved`、`replan.proposed/approved/rejected` 等。
- 任务详情页 = 该任务的完整事件时间线回放。

## 13. 工作区与资源

**现状说明**：M1 未设计此项（任务仅供演示）。设计目标：BYO agent（如 OpenCode CLI）需要真实的执行工作目录与可访问的输入资源。

### 13.1 工作区模型

```
Project.workspace（新增字段，项目级、可编辑）
  {
    kind: "local" | "git",        // local：本机目录；git：远程仓库（clone 到本地）
    path | url: string,           // 本机绝对路径或 git URL
    branch?: string               // git 可选
  }
```

- **项目工作区即 agent 执行的工作目录**：适配器 spawn agent 时把 cwd 设为项目工作区（任务未来可声明相对子目录进一步收窄）。
- git 类型工作区：项目确认规划时自动 clone（或追加 pull），位置 `data/workspaces/<project_id>/`；取消归档不删除（可手工清理）。
- 一个工作区原则上只属于一个项目；并行任务同仓操作由 CODING 场景的常见手段（分支/独立 clone）隔离——属 M3 并发深化话题。
- M1 交付态：字段在 UI 可填写/编辑，调度器不校验路径存在性；M2 起 OpenCode 适配器真正用它作为 cwd。

### 13.2 资源（输入）与产物（输出）

- **资源**：项目级 `resources/` 目录（`data/projects/<id>/resources/`），UI 上传后以路径形式在任务描述/验收标准中引用；agent 通过工作区可见的同一路径访问。
- **产物**：任务执行输出默认落在工作区内；任务 `artifacts` 记录相对路径列表，验收者据此检验。
- 资源上传 UI 与大文件托管均为 M2+ 能力（M1 无上传，先定协议）。

## 14. 未来功能（明确不在 M1–M4 范围）

- 审计日志强化：agent 运行细节可视化——planner/验收等非任务级 agent 会话的原始输出与耗时、逐事件回放视图、按 agent/项目过滤的运行时间线（当前仅有任务级日志 + `data/domo.log` 服务端运行日志）
- **审计关联详情按事件类型单独设计**：不同事件的关联信息结构差异大（执行失败→当轮日志+退出码；验收退回→verdict 理由+对比基准；决策→请求上下文+裁定依据；报告→产物路径；agent 生命周期→前后配置对比……），当前通用「payload+任务快照」形态仅作过渡，M4 审计深化时按事件族逐类设计关联详情视图
- 项目级知识库与经验沉淀（人工指导升级为团队规范）
- 项目模板与跨项目经验引用
- 更多 agent 适配器（Claude Code、通用 CLI、A2A/MCP）
- 多人协作、云端托管、移动端伴侣 App
- 成本核算面板（token/时长统计深化）

## 15. 决策记录（v0.1–v0.2 定稿）

| # | 决策 |
|---|---|
| 1 | 角色是标签非绑定；实例可多角色；同任务执行≠验收实例 |
| 2 | 验收者默认 agent，用户可配置各角色 agent，可强制人验 |
| 3 | 验收标准由执行者与验收者协商一致后才开工 |
| 4 | 豁免由决策者裁定 |
| 5 | 决策者=人类代理，复核一切项目内容/计划变更请求 |
| 6 | 决策者权限分层：战术自决，战略（里程碑/目标/新 agent/卡死）升级到人；决策者故障转人；不得担任同项目执行/验收 |
| 7 | 卡死：执行失败 3 次挂起、验收退回 2 轮升级；均不阻塞无依赖分支 |
| 8 | 人工指导先做单次任务级；知识库为未来功能 |
| 9 | 暂停冻结含验收的一切在途流程；项目级暂停；取消=归档 |
| 10 | 里程碑需要中途人工确认（gate）；无里程碑项目可全程无人工介入 |
| 11 | gate 只挂起下游分支；gate 是重规划窗口 |
| 12 | 恢复三档降级；BYO agent 需声明 resume/并行等能力 |
| 13 | 人工介入 = 规划者探讨通道：planner 分析给方案，采纳权在人；方案逐项应用、单项失败跳过；与规划共用 planner 会话（memory 连续） |
| 14 | 服务端运行日志落盘 `data/domo.log`（stdout 同步输出，DOMO_LOG/LOG_LEVEL 可调）；API 错误、状态流转、opencode 运行、planner 解析失败原始输出均入日志，便于事后排障 |
| 15 | Planner 输出解析加固：围栏块→整串→首尾区间→逐括号全部候选取最长有效 JSON；planner 提示词强制「首字符 {，末字符 }」；解析失败原始输出留存日志与错误 toast |
| 16 | Agent 支持编辑/删除；删除仅被终态任务引用的实例可行——非终态引用一律先换人（收件箱裁决或任务编辑），避免悬空占用 |
| 17 | 收件箱裁决必须自证上下文：升级即附 last_error 与涉及 agent 摘要；读时再富化并给出执行端/验收端处理指引，杜绝「泛泛的 failed N times 导致人误判环节」 |
| 18 | 裁决四式扩展为五式：+reassign_acceptor（限验收退回升级态成果保留）；角色替换类操作统一先摘占位再重派，无空闲候选直接 409 保持条目 open 而非假成功 |
