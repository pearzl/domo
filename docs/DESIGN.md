# DOMO 产品设计

> 本文详细说明 DOMO 的产品功能和设计思路，技术实现约束见 [TECH](TECH.md)。（本文由人工维护，AI不得擅自修改）

## 0. 产品目标

DOMO 是一个面向个人用户使用的，单机部署的产品。通过多个 Agent 的分工与协作，在交付效果与总成本之间取得平衡，实现目标的可靠交付。

不同 Agent 产品的定价、能力和适用场景各不相同，同一个 Agent 也不一定适合承担所有工作。DOMO 的产品理念是让不同复杂度和能力要求的任务交给合适的 Agent：明确、简单的工作可以使用低成本 Agent，复杂或关键的工作使用能力更匹配的 Agent，避免所有工作都使用高成本 Agent，也避免只追求低价而因反复失败和返工增加成本。

这种平衡以满足交付契约为前提，关注完成一个合格目标的总成本，而不是单次调用的最低价格。总成本既包括规划、执行、验收和返工产生的调用费用，也包括用户监督、判断和收尾的时间投入。多 Agent 协作、任务拆分和验收是实现这一目标的手段，不以 Agent 数量、任务数量或并行度本身作为产品价值。

**面向个人**意味着不需要现实中的协作与沟通，DOMO 实现一个人就是一支团队的现实目标。任何想法都可以由 AI 帮助你实施落地。

**本地**意味着除了你提供的大语言模型调用，所有数据都保留在你的电脑上，没有云端接入和账号体系，你拥有全部的控制权。Git 为软件交付提供隔离与合入能力，不构成其他交付场景的使用前提。

**单机**意味着它可以直接部署在你的笔记本上，不需要昂贵的硬件成本。

**设计前提与原则**

DOMO 的产品流程与约束基于以下假设：Agent 具备胜任所承担职责的智能，能够在获得充足上下文信息的情况下作出恰当决策。系统负责提供必要的信息与协作条件，不以穷举情形、预设决策或增加人工审批来代替 Agent 的判断。

所有流程与约束的设计只遵循一个目标：足够支持产品核心功能的运行。仅保留实现这一目标所必需的机制，不为流程完整性本身增加环节，也不为可以由 Agent 结合上下文妥善处理的问题设置额外限制。


## 1. 领域模型

### 1.1 项目

项目是为了达成一个明确目标，在有限资源和范围内，组织起来的一次性交付单元。它承载：

- 最终的交付目标
- 项目分析与方案
- 任务DAG（含里程碑任务）
- 独立的运行时配置
- 整体进度与状态
- 总结报告

### 1.2 任务

任务是项目内的可独立执行、验收的最小单元。它承载：

- 局部的细节设计、执行和验收
- 由项目继承的独立运行时配置
- 阶段性产物、结论与里程碑

*里程碑是任务的一个特殊标记，被标记的任务需要人工进行二次验收。*

### 1.3 Agent 角色

Agent 将扮演多种角色，分别是：
- 规划者：持有项目整体信息，负责与人讨论项目目标、给出项目方案并拆解任务，最终交付验收。
- 执行者：持有简略的项目信息和任务目标，对任务目标进行设计和实现。
- 验收者：持有简略的项目信息和任务目标，对执行者的工作进行核验。

角色的划分不仅用于设置不同提示词，也用于按工作职责配置不同的 Agent 和模型。结合任务专用 Agent 池，用户可以根据任务复杂度、能力要求和验收风险分配合适的 Agent，不要求规划、执行和验收使用相同成本档位的能力。

不同角色可以分配给不同的 Agent 和模型，一个 Agent 也可同时扮演多个不同的角色。角色分离本身不保证交付质量，成本与效果的判断以实际产物、验收证据和返工情况为依据。

### 1.4 作业

一次 Agent 调用被称作一次作业。作业分两类：由任务推进的作业称为任务作业，执行者与验收者的调用属于此类；由项目流程推进的作业称为项目作业，包括规划者的项目分析、项目验收与报告、报告重写调用，以及用户显式发起的项目合入冲突处理调用。

### 1.5 工作区

每个项目拥有一个由 DOMO 维护和管理的工作区，用于存放项目运行中的所有相关信息。如任务产物、作业输出……

工作区分为普通工作区和 Git 工作区，区别在于 DOMO 对交付目录的管理方式，不代表项目本身的技术结构或开发规范。

- 普通工作区：选择或创建本地目录，交付产物不依赖 Git，无需用户初始化仓库。
- Git 工作区：基于已有仓库，为任务提供独立工作空间、任务分支、项目交付分支与合入能力。

普通工作区采用串行调度，同一项目同一时刻只推进一个任务。DAG 用于表达依赖与执行顺序，任务派生的子任务也依次执行。普通工作区不提供任务并发和隔离能力。

普通工作区是持续演进的执行现场，不提供自动回滚：

- 目录独占：同一目录及相互包含的目录不能被多个未归档普通工作区项目同时占用。
- 当前现场：所选目录及其内容就是项目输入，不要求逐文件登记。每次作业按需读取当前文件，不假定目录仍保持项目创建时的内容。
- 范围内修改：执行者可按目标、任务范围及用户约束修改已有文件和前序任务成果；来源任务不构成文件所有权或额外授权边界。用户明确要求保留的原始资料、只读路径和其他保护约束必须遵守。
- 中断接续：强制暂停、作业失败或进程中断后保留文件现场。后续执行先检查已有结果及未完成操作，能够安全处理时继续，无法判断或涉及不可逆风险时再请求人工处理，不统一要求人工确认现场。停止作业不代表撤销已经发生的文件修改。
- 外部修改：建议用户暂停后再手工编辑，避免外部程序与 Agent 同时写入。后续作业以当前目录为准，不因文件变化自动阻塞；任务与现场不一致时说明影响并按任务指导或重规划流程纠偏。这些运行约定不构成文件系统沙箱。

项目列表与详情按工作区类型展示对应信息。普通工作区不展示 base 分支、交付分支、合入状态和 Git 恢复命令。

Git 项目的不同任务可以隔离并行。任务完成或项目归档后，DOMO 回收任务执行资源，同时保留任务原工作区位置、回收时间和审计所需产物。工作区有未提交改动时，归档需要用户确认，确认后保留该工作区。归档资产的保留范围见[审计与回溯](#7-审计与回溯)。

项目的运行资源（工具链、依赖、缓存、测试夹具等）与交付物分开管理，放在工作区外或 DOMO 管理的目录中，不进入任务提交。资源是可重建的运行条件，可以覆盖和删除，不承诺长期保留；重建成本高的内容必须作为成果提交。归档时只清理 DOMO 管理的资源目录，不删除用户目录中的文件。

### 1.6 交付契约与产物

交付契约是项目目标、验收和执行约束的版本化载体，包含：

- 要解决的问题与预期交付物
- 验收标准与关键假设
- 其他约束和说明

规划、执行、验收和报告引用同一份契约。目标或约束需要调整时形成可审查的版本，并说明对任务与产物的影响。

已确认目标只能通过用户主动修改目标的入口改变。目标之外的范围、关键假设、验收标准和约束允许由 AI 自行调整，AI 根据实际情况决定是否需要向用户提问或请求授权；不对所有此类调整设置统一的人工审批。调整必须说明原因、影响及是否请求用户授权，并保留契约版本与决策记录。AI 自行调整不得偏离当前已确认目标，也不得绕过项目方案的确认方式。

任务与项目可以声明预期产物。产物索引聚焦值得查看、跨任务引用或交付的重要成果，由执行者在结果中显式登记文件或目录、来源任务与验收方式，不扫描整个工作区自动登记。成果不区分类型，最多 4 条；目录优先，单文件只在确实需要独立引用时登记。参考输入不作为成果登记，放在契约、资源目录或共享记录；登记本身不意味着文件只读。成果在任务验收通过并完成交付后发布；Git 工作区同时记录产物对应的提交版本并提供版本回溯；普通工作区只管理当前产物，不提供产物版本管理与回溯能力，需要保留初始内容时使用版本管理或备份。交付契约版本与作业、验收记录的审计不受此限制。

产生或修改交付内容的任务执行作业由执行者自行提交。Git 工作区以任务分支的提交作为交付范围，DOMO 校验提交位于任务分支、历史只追加、提交身份正确、diff 不含被忽略路径与越界文件，并读取 HEAD 作为交付版本；作业期间除当前任务分支外，项目交付分支、base 与其他任务分支的引用不得变化。提交之外的改动保留现场，但不作为交付。普通工作区没有提交，按当前目录全量核对交付范围，删除由执行者在结果说明中声明。临时日志、缓存和构建产物不得进入交付。

### 1.7 项目共享信息

每个项目拥有独立的本地共享信息空间，用于保存当前项目的事实、接口约定、任务结论、检查结果、设计决策与未解决问题，并保留版本历史。共享信息适用于两类工作区，与交付产物分开管理，不构成普通产物的版本或回滚机制。它服务于当前项目的信息一致性，不承担跨项目记忆与用户偏好学习。

只有执行者可直接提交共享信息，无需规划者逐条审批；验收者不提交，验收中发现的问题写入验收 issues。每条记录有项目内唯一编号（M1、M2……，不复用），包含来源任务与作业，正文不超过 120 字；不设主题、适用范围、证据等结构化字段。共享信息引用产物而不复制全部产物。记录在任务验收通过后发布；提交表示形成了一条可引用的项目记录，不自动改变交付契约，也不代表任务验收通过。契约调整遵循[交付契约与产物](#16-交付契约与产物)的规则。

信息以编号标识，不再按主题、接口或任务分组。修正已有结论时，新记录用 supersedes 填写被替代记录的编号；入库时旧记录标记失效，不再注入作业，但保留在历史中。无法判断哪条失效时不要写入这条记忆，在结果说明中写明分歧并按重规划处理。内容冲突由提交者说明依据，后续任务用 supersedes 纠正；不以最后提交者为准。只有影响项目方案、契约或无法局部解决的分歧才交给规划者，规划者不成为日常信息交换的必经节点。

作业开始时获取并记录所依据的共享信息版本，接收当前契约、有效记录（不含已失效编号）、前置任务结论与上次作业以来的相关变化，不默认加载全部共享信息。项目记忆是共享信息的摘要视图：总量不超过约 5k 字时全量注入，超过时只给带编号的索引并按需读取；完整记录不默认加载。运行中可按需继续读取，并记录所依据的版本；信息变化不自动改写在途作业的既有输入。需要纠偏时，按任务指导或重规划流程处理。


## 2. 核心流程

我们的目标是：用户输入 -> AI 执行 -> 结果产出。

这个模型描绘的场景令人兴奋，但现实中受限于自然语言的表达能力和 AI 的智能水平，最终的表现并不总是令人满意。事实上即便是由人组成的团队来负责执行，也很难做到一次达成。因此需要设计一套通用的流程和信息交换方式来帮助 AI 准确执行人的输入。

### 2.1 项目分析

输入的项目目标几乎总是模糊的，如前所述这种模糊来自自然语言的限制、不同的上下文信息和理解能力的不同。项目分析阶段同时完成目标确认和项目规划：规划者阅读仓库、澄清目标，并给出可执行的项目方案。

项目分析由规划者角色完成，输出两类结果：
- 提问：只询问无法通过调查获得、且影响目标理解、方案可行性或验收方式的必要信息；合并相关问题，不设置固定数量上限。用户回答后继续分析。
- 项目方案：给出确认后的目标、关键假设、项目级验收口径、范围边界和任务 DAG。任务必须可独立执行、独立验收，任务之间用依赖表示且无环；需要独立验收时，方案也可以只有一个任务。

任务是委派与验收单元，不是实现步骤。共享大量上下文且需要共同调整的工作优先由同一执行者连续处理，步骤放在任务内部；独立拆分应有实际并行、上下文隔离、专门能力或权限边界、独立交付或风险判断等具体收益，并考虑交接、验收和整合成本。粒度不由工作区类型决定；并行主要带来实际经过时间的收益，不自动提高质量或减少 Token。规划者提交前检查相邻任务是否值得合并，保留必要的独立边界、既定范围与验收要求，不以增加或减少任务数本身为目标。

项目分析包含两个可以独立跳过的步骤： AI 向用户提问澄清，以及用户对方案做最终确认。项目可以设置确认方式：
- 人工确认（默认）： AI 给出方案后，必须等待用户确认，DOMO 才创建任务并进入执行。
- 自动确认： AI 返回方案即视为确认，DOMO 直接开始执行； AI 认为仍有歧义时，仍应提问或等待确认。

任务只在方案被确认后创建。项目报告仍必须经过人工验收，项目才进入完成阶段。

重规划是对当前项目重新进行需求分析与任务拆解，遵循与首次项目分析相同的澄清、方案要求和确认方式，并受[交付契约](#16-交付契约与产物)的目标边界约束。偏离当前目标的规划草稿一律无效。

人工或项目验收发起的项目重规划暂停后续任务派发，等待在途作业结算后生成独立草稿。任务发起的请求先交给上级决策，请求本身不暂停其他任务；决策者在同一作业中决定拒绝并指导原任务，或生成完整替代方案。只有完整方案生成后，受影响范围才停止后续派发，在途作业结算后应用替代方案，不另起一次规划作业。

项目级草稿沿用本节的方案确认策略。旧任务、报告、目标与验收口径在草稿应用前保持可恢复；用户可以放弃重规划并恢复旧计划。草稿标明取消任务、保留任务、范围扩大与验收变化。应用方案不得让项目停留在新旧计划混杂的状态，进程中断后可以恢复，每轮重规划的记录均可审计。被替代的未完成任务在方案应用时才取消；Git 任务取消后丢弃工作区的未提交修改、未跟踪文件和构建产物，不撤销已合并成果，保留已提交历史及作业审计记录。普通工作区不因取消任务删除用户目录中的文件。

### 2.2 任务执行

按任务描述进行具体执行。任务执行由执行者完成。

根据执行的实际情况 AI 可以请求对项目重新规划。例如原规划中存在明确的事实错误导致当前任务无法达成。
普通任务将具体问题提交给项目规划者；子任务提交给父任务执行者。上级通过独立只读决策作业处理，不受父任务等待子任务的依赖限制，不并发修改执行工作区，也不把请求直接升级成全项目重规划。

决策作业有三种结果：拒绝重规划并提供可执行指导，原任务继续；缺少输入、授权或环境时说明解除条件并等待补齐；确需重规划时在同一结果中交付完整方案。父任务的调整仅限自身分工，遵循[任务派生](#24-任务派生)的替代规则，不额外要求人工确认；项目规划者替换项目未完成任务，沿用当前目标与验收口径，方案遵循项目确认设置。决策失败有独立重试额度，不消耗提出请求任务的执行失败或验收拒绝次数；等待条件可通过人工指导解除或重新排队决策。

AI 也可以对当前任务进行再次拆分，[派生](#24-任务派生)更多子任务。

### 2.3 任务验收

按任务验收标准对执行阶段的结果进行核查。任务验收由验收者完成。

验收结论与后续处置分别表达。验收记录必须列出对照的交付契约版本与验收标准、检查的产物、实际执行的检查与结果，以及未覆盖的假设、风险和人工检查项。产物版本的保留与回溯遵循[交付契约与产物](#16-交付契约与产物)；普通工作区记录检查时的产物路径、检查时间与结果。

未通过时由验收者结合当前情况选择退回执行、等待条件或请求上级决策，不按问题关键词自动分流。退回执行附完整问题清单并计入验收拒绝次数；等待条件保留验收阶段，说明缺项、责任方和解除条件，不计入拒绝次数，也不自动轮询外部条件。用户补齐条件后可以重新验收，不必重新执行实现。存在可修复缺陷与环境缺项时，可以先退回执行处理缺陷。请求上级决策复用任务决策机制，上级可指导执行、补充核验、等待条件或提供替代方案，不因请求本身增加拒绝次数。未验证不能视为通过。

普通工作区的任务在所需验收全部通过后完成。Git 工作区还需由 DOMO 完成任务成果合入：普通任务合入项目交付分支，子任务的交付目标见[任务派生](#24-任务派生)；合入成功任务才完成。合入冲突时任务退回执行者解决冲突，解决后重新验收，该流程与验收拒绝相同，但不计入验收失败次数。合入冲突单独计额度，默认 3 次；用尽后交规划者/父任务判断。目标分支有未提交改动或无冲突的合入失败直接阻塞，不交给执行者。

每轮验收返回当前仍未解决问题的完整清单，替换任务的待处理反馈；已解决问题不继续累积，通过后清空。执行者逐项修复并提供验证依据，验收者仍需完整核验任务标准。历轮反馈与证据保留在作业及审计记录中。

里程碑任务在验收者验收通过后等待人工二次验收。人工验收通过才满足任务的验收条件；人工验收拒绝时退回执行者再次执行，并附上拒绝原因和指导意见。里程碑人工验收未通过计入验收失败次数，未通过前任务不能完成，依赖该任务的后继任务不能启动。

连续三次验收拒绝后停止原返工循环，普通任务交给规划者、子任务交给父任务执行者判断。上级可指导继续执行或重新核验、等待条件或生成替代方案；涉及验收标准调整时遵循交付契约及方案确认规则。相同任务的次数阈值不反复触发自动决策；上级指导后仍反复被拒绝，或决策失败额度耗尽时交由[人工裁决](#5-人工裁决)，累计消耗不重置。

### 2.4 任务派生

任务派生由执行者在调查确认存在独立分工边界时提出，粒度遵循[项目分析](#21-项目分析)的原则；复杂或工作量大本身不足以派生。分工说明包含不由当前执行者继续的理由、交接成果与父任务剩余整合责任。并发能力遵循[工作区](#15-工作区)的约束。任务派生遵循以下规则：
- 任务派生由执行者决定，而项目规划由规划者决定
- 派生任务不能再继续派生新的子任务，以避免无限递归的情况
- 同一批派生子任务可以形成无环依赖，deps 只能引用本批次内子任务，不能引用父任务、其他批次或项目中的其他任务；不允许自依赖、缺失依赖或依赖环

任务派生后[任务阶段](#33-任务阶段)变更为待启动，同时所有派生的子任务在 DAG 中自动成为该任务前置任务。
父任务在某一轮作业结束时提交派生请求，之后等待所有子任务完成后将他们的输出作为自己新一轮作业的输入，继续自己的任务阶段流转流程。

子任务以父任务已有成果为起点。Git 工作区的子任务成果先合回父任务分支，不直接发布到项目交付分支。父任务等待子任务期间不同时开展写入工作；全部子任务完成后，由父任务整合成果并接受验收。

派生请求整体校验通过后才写入 DAG，不接受部分子任务。前置子任务验收并交付到父任务工作区后，后继子任务才启动；Git 工作区从包含前置成果的父任务分支创建后继工作区。

父任务被取消或整体替代时，整个任务族退出有效计划，包括已完成但尚未随父任务交付的子任务；历史提交与审计仍可追溯，不要求迁移这些内部成果。父任务仍有效、仅替换部分未完成子任务时，保留已完成兄弟任务。跨任务族依赖必须指向父任务，不能绕过父任务验收直接依赖其子任务。已完成并发布的父任务不因后续重规划自动撤销。

派生任务的阶段、状态与[验收规则](#23-任务验收)均与普通任务相同，也可以标记为里程碑。派生任务失败、取消或完成时对父任务的影响，与普通前置任务对其依赖任务的影响相同。父任务的验收仍需核验整合结果是否满足父任务目标。

### 2.5 人类干预

在项目完成前，人可以随时对项目进行干预。干预的目的是对 AI 的工作进行指导和纠偏。干预的手段包括：
- 要求重新进行[项目分析](#21-项目分析)
- 将任意未完成的任务标记为里程碑
- 对任意未完成的任务进行指导，指导的内容将在下一次作业时生效
- 修改[项目和任务状态](#3-阶段和状态)：暂停、强制暂停、归档、继续等

项目计划只有一个作者：规划者。人工不直接增加或取消任务；需要变更时通过[项目分析](#21-项目分析)的重规划表达。项目完成后不再增加任务，新需求作为新项目处理。

### 2.6 项目验收和总结

所有任务完成后，项目进入总结阶段，由规划者根据交付契约进行项目验收。任务验收验证局部任务目标，项目验收验证最终集成产物是否满足整体目标，包括任务间接口、共享假设和结果一致性，不能以任务均已通过代替整体检查。Git 项目检查项目交付分支上的集成结果。项目验收不设逐项证据字段；项目报告必须包含「验收执行记录」，逐条写明检查对象、检查范围、检查方法、实际结果与证据位置。报告只能陈述已实际检查的内容，不能把应当满足写成已满足。

项目验收只回答一个问题：能否通过更多 Agent 工作解决。能，则返回 execute：必须给出未通过项与完整重规划方案，应用后继续执行并再次验收，不产报告。不能，则返回 deliver：必须提交报告，可列出 Agent 无法解决的未闭合项；报告与未闭合项交人工验收，项目保持在总结阶段。等待外部条件、需要人的判断或取舍的，按 deliver 处理，不单独设等待状态；补齐条件后重新验收。只有实际发起重规划才计入重规划次数。标准本身要求人的判断或签字时，作为人工待办进入报告，不豁免其他硬性验收标准。

### 2.7 人工验收

项目总结的人工验收有四种动作：接受、重新验收、驳回、提问；接受带未闭合项时必须填写理由，理由进入最终交付记录。里程碑验收只有通过和拒绝两种：通过则任务完成，拒绝则退回执行并计入验收失败次数，不允许部分通过。项目总结被驳回时，由规划者判断是补工作、调整契约还是只重写报告，人工不直接选择重写或重规划；提问只问答，不改变状态、不修改报告，可多轮。重新验收用于人补齐外部条件后重新检查，不改方案。

### 2.8 项目合入

项目进入完成阶段后，人工可以把项目交付分支合入目标分支。合入是 Git 项目的可选后续操作，不属于项目完成条件，也不延伸到发布或上线流程：

项目完成后的合入只保证正确完成约定的 Git 操作，不要求对合入后的组合版本额外执行行为检查或重新验收。合入失败必须保留原因与相关上下文，向用户提供处理入口；失败不改变项目已完成的阶段。

- 无论目标分支是否已检出，合入都将项目交付历史衔接到创建时选定的 base 分支，随后只允许目标分支快进；历史保持线性，不产生合并提交。
- 目标分支在某个工作区检出时，合入要求该工作区没有未提交改动；有改动时拒绝合入，项目分支与目标分支都保持操作前状态。
- 整理项目分支时发生冲突或失败，合入终止，项目分支与目标分支都保持操作前状态，错误信息列出冲突文件。DOMO 不未经用户发起就调用 Agent 解决冲突，不强推。
- 合入成功记录合入时间、项目分支提交、被验收版本与合入版本；发生 rebase 或由 Agent 解决冲突时，标注版本差异与冲突文件。目标分支已包含项目分支提交时，再次合入返回“已是最新”，不产生新的提交、不改变分支状态。

合入冲突后，用户可以显式发起 Agent 协助，并选择处理冲突的 Agent。此次调用属于项目合入冲突处理作业，不创建普通任务；Agent 选择遵循[人工裁决](#5-人工裁决)的人工指定规则。Agent 解决冲突后 DOMO 直接继续合入，不调用独立验收者，也不要求额外的人工验收或再次确认，仍须满足本节合入约束。处理或合入再次失败时保留失败原因与作业记录，提供再次处理入口，不标记为合入成功。所选 Agent、冲突处理输出与最终合入提交进入项目审计记录。

## 3. 阶段和状态

阶段描述进行到哪一个步骤，状态描述是运行的状态。

很多时候他们容易被混淆，例如，一个任务因为前置任务未完成，和在 Agent 队列中排队，给用户的感受都是它没有在执行。

我们使用两个正交的维度来描述，希望能准确的表达这种差异。

### 3.1 项目阶段

项目阶段包括：
1. 项目分析：项目创建后自动处于该阶段，即项目的初始阶段。规划者在此阶段完成目标澄清、方案确认和任务规划。
2. 执行：按已确认方案推进任务；任务重规划决策期间保持该阶段，后续流转遵循[项目分析](#21-项目分析)的规则。
3. 总结：项目中所有任务完成后，规划者进行项目验收并撰写项目报告，随后等待人工确认和验收；项目验收返回 execute 时按重规划方案继续执行，返回 deliver 时交人工验收，不单独设等待状态。
4. 完成：项目报告和最终结果被人工确认验收后就进入完成阶段，标识整个项目成功结束。

### 3.2 项目状态

普通暂停和强制暂停对项目与任务采用相同的在途作业处理规则：普通暂停只停止后续作业派发，在途作业不受影响，仍可产生流程允许的任何结果；强制暂停终止在途作业，保留已有文件现场与可获得的执行记录，不保证恢复尚未保存的输出。解除暂停只解除派发限制，中断作业的后续处置见[作业异常与恢复](#47-作业异常与恢复)。

项目状态包括：
1. 阻塞中：项目无法自动流转，需要外部驱动。项目创建后因为还没有输入目标，因此自动处于该状态。等待用户回答澄清问题、确认方案、验收里程碑或项目报告，以及等待人工裁决，且没有其他可自动推进的项目作业或任务作业时，项目也处于该状态。
    - 进程重启后的恢复过程中，项目也处于阻塞状态；恢复完成后，根据是否仍有待人工处理事项决定能否进入运行中。
2. 运行中：只要项目中有任何项目作业或任务作业可以无需人工干预地继续执行，项目就处于该状态，包括项目分析、项目验收和报告作业。
3. 暂停中：用户命令项目暂停后进入该状态。项目暂停是覆盖所有任务的统一派发限制，不改写任务自身的暂停意图；项目恢复后只解除项目级限制，原先被用户单独暂停的任务仍保持暂停。项目暂停期间创建的任务同样受项目级限制。
4. 已暂停：用户命令项目暂停后，项目中所有作业都已经停止，自动进入该状态。
5. 已归档：由用户触发的不再关注的项目，无论项目处于哪种阶段都可以进行归档操作。
    - 已归档的项目立刻停止所有 Agent 作业派发，在途作业的终止方式与强制暂停相同。
    - 已归档后的项目无法恢复重新执行，但依然可对执行情况进行[回溯和审计](#7-审计与回溯)

*项目可以被取消，取消也视为归档操作*

项目是否存在待人工处理事项与项目状态分别表达：部分任务等待人工处理而其他任务仍可自动推进时，项目保持运行中。

### 3.3 任务阶段

任务阶段包括：
1. 待启动：前置任务未完成时。
2. 执行：全部前置任务完成时。
3. 验收：执行阶段结束时。等待验证条件时保持本阶段；需要修复实现或 Git 工作区合并冲突时回到执行阶段。
4. 完成：满足[任务验收](#23-任务验收)规定的验收与工作区交付条件时。

### 3.4 任务状态

任务状态包括：
1. 阻塞中：任务无法自动流转，需要外部驱动。如存在尚未被答复的人工裁决请求。
2. 运行中：Agent 正在执行对应阶段的作业。
3. 队列中：作业等待派发，包括等待 Agent 并发释放、冷却结束、可用时段到来或其他可预期自动恢复的条件。展示等待原因及可确定的恢复时间。
4. 暂停中：用户命令任务暂停后进入该状态，在途作业按上述统一暂停规则处理。
5. 已暂停：用户命令任务暂停后，且所有作业都已停止，自动进入该状态。
6. 已取消：退出有效计划、不再推进的任务，不能作为有效前置成果。父子任务的取消范围见[任务派生](#24-任务派生)。

阶段和状态是两个正交维度，但他们的组合结果并不总是有合理含义的，具体规则如下：

状态允许为空。项目仅在完成且未归档时状态为空；任务在待启动且未暂停、未取消时状态为空，以阶段表达依赖等待，任务完成后状态也为空。界面不为空状态显示运行或阻塞徽标，也不将其计入这些状态的筛选数量。

## 4. Agent 池

Agent 池就是一支等待调度的 AI 团队。

Agent 池承载用户对能力与成本的配置策略：角色池用于区分规划、执行和验收的能力投入，任务专用 Agent 池用于区分不同任务的能力投入。用户可以按任务复杂度和能力要求调整候选 Agent、优先级与启停状态；调度器按这些配置选择 Agent，不自动根据任务复杂度判断能力档位或升级 Agent。

系统结合验收证据、返工和交付成本提供 Agent 配置建议，说明判断依据与数据不足之处，由用户决定是否调整，不因建议自动升级 Agent 或修改角色池。

项目池继承系统默认团队，之后可独立调整；任务池的继承与调整见[任务专用 Agent 池](#46-任务专用-agent-池)。

### 4.1 配置

Agent 由用户提供，对项目和任务提供相同的能力，包括：
- 模型选择
- 负载队列，如：可并行的最大数量
- 异常检测，如：进程卡死检测
- 可用性计划，如：按时间规划、按用量规划
- 角色选择优先级
- 并发已满时让位，如：达到最大并发后允许同角色池中后续优先级的 Agent 接手

并发已满时让位是 Agent 级开关，默认关闭。项目池、任务池与默认团队共用这一个值，不提供池级覆盖。

默认团队覆盖全部已注册 Agent：每个 Agent 按其角色自动出现在对应的角色分组中，注册 Agent 或修改其角色后自动同步。角色池的成员由全局 Agent 的角色决定，用户只调整角色内的顺序与启停。

新建 Agent 时可选择「同时加入所有现有项目和任务的 Agent 池」。选项默认关闭，仅在创建时提供；勾选后按 Agent 的角色追加到所有未归档项目的对应角色池，以及这些项目下未完成、未取消任务的执行者与验收者池末尾。已归档项目、已完成或已取消任务不参与同步。新条目的启停继承 Agent 的全局启停；已有条目、顺序和优先级保持不变。

### 4.2 队列

当多个任务同时调度到同一个 Agent，且任务数量超过 Agent 的最大负载时，任务就会按调度的先后顺序开始排队。此时用户可以选择：

- 不做干涉，等待 Agent 顺序执行
- 暂停执行中的任务以停止后续派发，或强制暂停以终止在途作业并提前释放 Agent
- 调整队列中未开始的任务的排队顺序

Agent 队列是系统全局的，同一个 Agent 的所有作业共用一个队列。

队列展示等待作业阻挡的后继任务、是否阻挡里程碑或项目总结，以及对项目推进的影响，帮助用户判断是否调整顺序；默认派发仍遵循队列顺序，不自动按项目关键路径或作业长短重排。

### 4.3 可用性计划

可用性计划帮助用户自动启停 Agent，合理规划来自不同供应商的账单成本。支持的计划维度有：
- 按时间：针对限时免费和折扣活动，最大化利用优惠政策。
- 按使用量：当 Agent 达到设定阈值后自动禁用。使用量的说明参考[成本和用量](#6-成本和用量)

### 4.4 优先级与调度

每个 Agent 在每个角色下都有一个优先级，同一角色的优先级编号连续且不重复，数字越小优先级越高，0为最高优先级。

当需要对应角色的 Agent 时，按优先级升序检查角色池。可用指：遵循[启停规则](#45-启停与角色池修改)、具备该角色、未被删除、不在冷却中、处于可用时段且未达到用量限额。执行者与验收者使用[任务专用 Agent 池](#46-任务专用-agent-池)，规划者使用项目 Agent 池。

并发满额时的派发由 Agent 的“并发已满时让位”开关决定：

- 关闭：第一个可用且未满的 Agent 独占该次派发。该 Agent 满额时派发等待它释放，等待原因展示该 Agent 名称与并发占用，不检查后续优先级。
- 开启：满额 Agent 让位，调度按同角色池继续扫描下一优先级，可以连续让位多个满额 Agent。遇到关闭开关且满额的 Agent 时扫描停止，由该 Agent 承担等待，等待原因展示它的名称与并发占用。全部让位的 Agent 之后仍无 Agent 接手时，展示所有让位 Agent 及其并发占用。

让位只作用于并发满额：不可用判定、冷却、可用时段、用量限额与失败换人的处理都按同一规则执行，不因开关改变。发生让位时，排队信息说明被让位的 Agent；人工指定的派发明确标注“由人工指定”。

人工指定 Agent 的派发遵循[人工裁决](#5-人工裁决)中的例外规则。

除让位外，只有高优先级 Agent 不可用时才检查下一优先级；没有发生让位且全部 Agent 不可用时，等待或阻塞信息逐个列出每个 Agent 及其不可用原因。

正常调度不使用上次执行者做轮转，同一任务重新执行时仍从最高优先级的可用 Agent 开始。

本角色下暂时没有可用 Agent，但存在可预期自动恢复条件时，保留待派发作业并等待条件恢复，调度器在条件满足后重新按优先级选人，不要求人工重试。任务保持队列中，项目在没有其他人工阻塞条件时保持运行中。等待期间不提前清除冷却或用量限制，不重复产生失败作业或人工待办。

没有可预期自动恢复条件，或达到协议失败等明确需要人工处理的条件时，才进入阻塞，等待[人工裁决](#5-人工裁决)。阻塞原因记录失败原因与各 Agent 的不可用原因；重新派发需要人工重试、裁决或通过对应入口解决配置问题。人为停用、缺少角色配置和未设重置条件的用量限额不视为可自动恢复的等待。

### 4.5 启停与角色池修改

启停分为三层，任一层停用都不再向该 Agent 派发新作业：

- 全局开关：Agent 团队页的 Agent 级开关，影响所有项目与任务。
- 项目池开关：项目 Agent 池与默认团队中按角色的启停。项目 Agent 池的角色启停只影响当前项目，并屏蔽该项目已有任务的同角色派发；任务池自身的配置不被改写。
- 任务池开关：任务 Agent 池按角色的启停，只影响该任务。

用户可以修改 Agent 的优先级和启用状态。角色池成员由全局 Agent 的角色决定。

排序交互见 [Agent 团队与队列](#9-agent-团队与队列)。

启停状态只有开关两种状态。启停状态不影响优先级的设置。全局开关只屏蔽派发，不改写项目与任务配置。

### 4.6 任务专用 Agent 池

任务专用 Agent 池由项目 Agent 池派生，只包含执行者与验收者两个角色分组。任务创建时继承项目池对应角色的全部条目、优先级与启停状态，之后独立维护；新建 Agent 时的显式同步遵循[配置](#41-配置)中的规则。

任务池支持与项目池相同的排序与启停操作，改动只作用于该任务；不支持任意更换成员。

项目池中缺少某个成员时，不影响该成员在既有任务池中的使用。任务池为空或全部不可用时，按[优先级与调度](#44-优先级与调度)等待或阻塞并说明原因，不回退到项目池。

### 4.7 作业异常与恢复

任务作业与项目分析、项目验收、项目总结作业采用一致的异常处置规则。项目合入冲突处理作业遵循[项目合入](#28-项目合入)的专门规则。

作业每轮运行上限为 10 小时；连续 30 分钟没有运行输出时判定为长时间无输出。诊断应区分可确认的停止经过、可能的错误原因与判断依据；证据不足时明确显示未知。工具执行失败、Agent 的推理文本，以及已自行恢复的中间错误，不单独作为整个作业失败的依据。长时间无输出也不等于原会话不可恢复。

已经产出完整有效结果时，优先恢复结果收集与结算，不要求 Agent 重复已经完成的工作。支持会话恢复的 Agent 在其他情况下按以下规则处理：

| 结束原因 | 处置 |
| --- | --- |
| 运行超时，或有可靠证据的网络、供应商临时错误 | 可自动接续；自动接续结束后仍未完成的，等待人工选择。 |
| 限流 | 等待冷却，遵守明确的重试时间；没有重试时间时采用默认冷却。原会话的后续执行由人选择，不立即循环。 |
| 长时间无输出、未知退出、服务中断或人工停止 | 不自动接续，保留人工尝试继续的选择。 |
| 认证、权限、余额、配额或配置错误 | 由人修复外部条件后选择是否继续，不自动认定条件已恢复。 |
| 原会话明确不可恢复或上下文达到无法恢复的硬限制 | 提供新会话执行，不反复尝试已知无法恢复的会话。 |
| Agent 正常结束但未提供完整有效结果 | 结果缺失或不可解析最多 2 次、内容不合规最多 1 次；耗尽后阻塞，由人处理，不自动换 Agent。 |
| Agent 提交任务失败、请求重规划或验收拒绝 | 按对应业务流程处理，不当作供应商异常，也不因此自动更换 Agent。 |

自动接续与人工继续共享最多两轮额外执行；结果缺失另计 2 次、内容不合规另计 1 次，三类互不占用，合计不超过五轮。缺少可靠临时故障证据时，不以推测授权自动接续。

合法结果中的失败说明属于项目业务内容，不根据正文中的供应商名称、网络术语、状态码或源码行号判定基础设施故障。任务失败和协议错误不影响 Agent 的供应商冷却计数。基础设施重试不消耗任务连续失败预算，协议纠错使用作业内独立预算；有效执行与验收结果清除连续失败计数，作业尝试序号独立记录审计顺序。

不支持恢复原会话的作业，临时供应商故障采用同 Agent 有限重新执行、冷却和换人策略；认证或配置等不适合自动重试的错误按换人策略处理，不将新会话执行标为原会话继续。

需要换人时，下一次按原阶段及[常规调度规则](#44-优先级与调度)重新派发，临时跳过失败 Agent；派发成功后恢复常规选人规则。

## 5. 人工裁决

当系统遇到无法恢复的错误，或 AI 遇到无法解决的问题时，则需要人工裁决。
此时会提供必要信息，包括事件类型、关联项目和任务、其他必要上下文，供人类做出合适的判断。

根据类型的不同可能由不同的处置策略：
- Agent 作业失败：符合资格时继续，或新会话执行、更换 Agent
- 无可用 Agent： 更换 Agent
- 任务核验多次被退回：指导规划者重规划、指导执行者以新会话执行、更换 Agent（执行者）、更换 Agent (验收者)

### 5.1 作业继续与新会话执行

“继续”表示尝试恢复原会话，结束原因与执行额度遵循[作业异常与恢复](#47-作业异常与恢复)。Git 与普通工作区采用相同语义，不要求文件、配置或输入与上次完全一致；Agent 需要检查当前现场、已有结果和残留操作，避免重复副作用。支持恢复不代表保证成功，实际恢复失败时如实说明，不静默创建新会话。

只有仍属当前有效工作、没有后续尝试且处于适用阶段的作业可以继续。原执行及其结算必须结束，不得与同一现场的其他执行并行；已完成、取消、归档或被替代的工作不能借继续复活。继续仍受[调度规则](#44-优先级与调度)、[暂停规则](#32-项目状态)及[消耗授权](#6-成本和用量)约束，不清零任务执行失败与验收拒绝次数。

“新会话执行”、人工指导和更换 Agent 使用新会话，并提供当前上下文；已有文件与提交不因新建会话被重置。修复外部凭据或配置后选择继续，与提交新的工作指导是不同意图。业务返工与结果纠错耗尽后的再次执行使用新会话。

设计取舍见[作业继续决策记录](notes/job-continuation-decisions.md)。

### 5.2 人工指定 Agent

更换 Agent 表示临时指定执行本次任务的 Agent，可以绕过调度策略、启停状态、角色能力、冷却、可用时段、用量限额和其他可用性限制，但仍受[项目消耗授权](#6-成本和用量)约束。人工指定不遵循让位，即使该 Agent 已满额并开启让位开关，派发仍等待它释放。

选择界面必须显示风险提示，说明此次调用可能产生额外费用、使用不具备目标角色的 Agent，或在 Agent 正常不可用期间执行。常规继续与新会话执行不隐含这项授权。


## 6. 成本和用量

DOMO 将记录每次 Agent 调用的成本，包括输入与输出 token 数量，费用与时长。这些记录的信息用于：
- 支持[可用性计划](#43-可用性计划)的实施。
- 对用户提供多种维度的聚合的统计信息。
- 结合验收结果与返工记录，评估不同 Agent 配置完成合格交付的实际成本，避免只按单次调用价格判断性价比。

项目成本包含规划、执行、验收、失败尝试、返工、重规划及项目完成后的合入冲突处理等全部调用消耗，不因某次作业未产出合格结果而排除其成本。调用费用与时长用于衡量可记录的投入，不能替代对交付效果和人工监督负担的判断。

统计数据由 Agent 自身提供，无法提供的 Agent 信息也会被明确记录为未知，并在聚合展示时特殊标记。

项目支持以下预算与自动消耗边界，不以 Agent 的全局用量限额替代项目控制：

- 限制类型：可选项目费用预算、任务自动尝试上限与项目重规划次数上限；未设置费用预算时不限制项目总费用。费用预算覆盖本节定义的全部项目调用。
- 触发处理：达到限制后停止受限范围内的新作业派发，说明已知投入、未知用量与停止原因；在途作业允许结算，不默认强制终止。
- 累计与授权：继续、新会话执行、换 Agent 和重规划均不重置累计消耗。用户可以提高限制并继续，AI 不得自行提高用户明确设置的消耗上限。
- 精度边界：费用未知或延迟上报时明确提示，不把已知费用合计表示为完整项目成本。由于在途作业与统计延迟，预算不是供应商账单的精确硬上限。
- 可核对性：任务尝试与重规划的计数可从相关作业与重规划记录核对。


## 7. 审计与回溯

DOMO 详细记录项目中的所有信息，用户可以在任意时刻对已发生的行为进行详细的分析和溯源。
记录的内容包括：
- 项目的阶段和状态变更
- 任务的阶段和状态变更
- 人工裁决结果
- 人工干预、验收证据与交付契约版本
- 异常与恢复情况
- 作业记录，包括起止时间和输入输出
- 项目共享信息变更及作业引用的版本

归档项目保留完整的作业审计资产与项目共享信息。Git 项目的任务和项目分支提交在归档后仍可追溯，但不进入普通分支列表。备份与恢复必须覆盖这些归档提交、共享信息、作业记录和普通工作区当前保留的产物；历史产物的可回溯范围遵循[交付契约与产物](#16-交付契约与产物)的规定。

# 用户界面设计

## 1. 全局导航与待我处理

全局导航包含项目、待我处理、Agent 团队和成本用量。待我处理集中展示所有需要人工驱动的项目，包括：

- 待回答的项目澄清问题与待确认的项目方案；
- 待验收的里程碑任务与项目报告；
- 待处理的人工裁决、阻塞作业和无可用 Agent 的项目或任务。

每个待办展示事项类型、关联项目与任务、摘要、当前阻塞原因、等待时长与受影响的后继任务，标明项目是否仍可推进、是否阻挡里程碑或项目总结。支持按影响与等待时长查看，等待时长排序为倒序。点击后打开对应项目、任务或作业的处理位置，用户可以在该位置回答问题、确认方案、验收或裁决。处理完成后事项离开待办列表，导航中的数量同步反映当前待办总数。可预期自动恢复的资源等待不产生人工待办；已归档项目不产生待办。

## 2. 项目列表

项目列表以卡片展示项目名称、目标、工作区类型、阶段、状态、当前阻塞摘要和任务进度。已合入的项目在卡片上显示“已合入”与短提交号。顶部提供创建项目入口，以及阶段与状态两组分类标签：

- 阶段标签取项目分析、执行、总结、完成；状态标签取运行中、阻塞中、暂停中、已暂停、已归档。
- 同组多选为“或”，两组之间为“且”；组内不选表示该维度不过滤。
- 标签显示当前已加载项目中的数量；任一标签选中时提供一键重置。
- 过滤结果为空时显示空状态与重置入口；项目集合为空时显示“还没有项目”。

## 3. 创建项目

创建项目表单包含：

- 项目名称与目标；目标可以稍后补充，未输入目标的项目创建后处于项目分析阶段和阻塞状态。
- 工作区类型与本地目录；普通工作区支持选择已有目录或创建目录，Git 工作区支持选择已有仓库。
- Git 项目的 base 分支，默认使用仓库当前分支，并允许在创建时选择其他分支。
- 方案确认方式，默认人工确认。
- Agent 池与独立运行时配置，默认继承系统模板，创建时可以展开调整。

创建后进入项目详情。项目分析产出的交付契约、验收标准与预期产物在方案区域展示，不以创建表单中的简短目标替代完整契约。

## 4. 项目视图

项目视图包含基本信息、目标与交付契约、共享信息、任务、产物、项目报告、作业、事件、成本用量和 Agent 池。页头展示阶段、状态、当前推进事项或阻塞原因，并提供暂停、强制暂停、继续、重规划、归档等适用操作。强制暂停与归档需要确认；归档确认说明[工作区](#15-工作区)规定的资源保留结果。

项目视图优先呈现最新可查看的交付结果、交付契约逐项满足情况、待决策事项、未验证风险和累计投入，不以任务完成数量代替交付进展。用户无需先阅读 DAG 或作业日志即可了解当前结果、尚缺内容和需要自己处理的事项；任务、作业与审计作为进一步查看依据的入口。

交付契约支持查看版本差异及其对任务与产物的影响。成果区域按[产物定义](#16-交付契约与产物)展示，支持按任务过滤，提供查看、预览、打开所在目录与适用的版本回溯入口；工作区路径直接表示项目输入范围，不以全量文件清单或逐路径授权控制台代替成果导航。

共享信息区域按编号展示记录，提供来源、替代关系及提交历史的查看入口，具体规则见[项目共享信息](#17-项目共享信息)。

任务面板支持列表与 DAG 两种视图，默认列表，视图选择不作为长期偏好保存。列表支持按阶段、状态和里程碑标记过滤，展示前置依赖、当前 Agent、等待原因和验收结果。

DAG 视图按任务依赖计算拓扑层级：同层任务并列，依赖边由前置任务指向后继任务，派生任务与父任务的关系用虚线表示。节点展示任务 key、标题、阶段与状态徽标、里程碑与派生标记；取消的任务不进入图。节点可以点击或用键盘 Enter/Space 打开任务抽屉。依赖缺失或存在环时给出提示，并保留列表视图作为任务访问入口。

项目详情展示完成横幅。项目处于完成阶段且目标分支尚未包含项目分支提交时，横幅提供“合入到 base 分支”按钮；点击前需要确认，执行期间按钮禁用。成功、已是最新和失败结果都显示在横幅内。目标分支已包含项目分支提交时（包括在 DOMO 之外完成的合入），横幅不再显示合入按钮；DOMO 记录的合入显示目标分支、合入时间与短提交号，刷新后保持。普通工作区不展示该合入横幅。

合入失败时，横幅展示失败原因和冲突文件，提供重新合入入口。存在冲突时提供“选择 Agent 协助解决”入口与选择确认表单，展示风险提示、费用预算限制及实时处理结果。横幅单独展示合入作业的等待与运行状态，行为遵循[项目合入](#28-项目合入)的规则。

## 5. 项目分析与重规划

项目分析区域按当前活动展示澄清问题、分析进度或项目方案。澄清问题支持逐项回答和统一提交；项目方案展示确认后的目标、关键假设、范围边界、项目级验收口径、预期产物和任务 DAG。人工确认模式下提供确认入口，确认前可以要求规划者继续调整；自动确认模式展示方案内容与自动执行状态。

重规划区域沿用项目分析的交互，额外展示草稿差异及任务与产物受到的影响，提供应用前的放弃入口和应用后的历史草稿查看入口。确认与恢复行为遵循[项目分析](#21-项目分析)的规则。

## 6. 人工裁决与验收

人工裁决展示事件类型、关联项目和任务、阻塞原因、相关作业及必要上下文，按[人工裁决](#5-人工裁决)提供适用操作。人工指定 Agent 时展示风险提示，确认本次选择后才允许派发。

等待用户或外部条件时，处理区域优先展示阻塞摘要、原因与需要处理的问题（issues），并可展开 Agent 执行指导；不另设结构化用户说明字段。技术依据和历史记录按需展开，不以内部审批术语或整份交接报告代替原因。没有可行动说明的记录保留原始详情，不推测操作或宣称条件已满足。

任务验收按[任务验收](#23-任务验收)的记录要求展示证据及适用的产物版本信息；项目验收展示报告与验收执行记录，不要求逐项证据字段。用户可以在同一视图查看相关产物与作业输出，并通过或拒绝验收；拒绝时必须填写原因。

里程碑与项目报告验收提供[人工验收](#27-人工验收)规定的操作入口。验收期间的对话、意见、证据和结果都进入审计记录。

## 7. 任务视图

任务视图包含任务目标、验收标准、阶段与状态、前置与后继依赖、父子派生关系、里程碑标记、运行时配置、Agent 池、产物、验收记录、作业列表和事件时间线。

用户可以对未完成任务添加指导下一次作业的内容、设置里程碑、调整任务 Agent 池，以及执行暂停、强制暂停或继续。任务视图区分任务自身暂停与项目级暂停限制，说明继续操作实际解除的限制。验收区域区分验收者验收与里程碑人工验收，展示每轮拒绝原因、检查证据和退回记录。派生任务额外展示派生标记。

## 8. 作业视图

作业视图展示关联项目与任务、项目阶段或任务阶段、角色、Agent、模型、会话、排队与运行状态、起止时间、等待原因、输入输出、引用的共享信息版本和 Agent 实时输出。用量区域展示输入与输出 token、费用、时长以及未知数据标记。

异常作业展示[作业异常与恢复](#47-作业异常与恢复)规定的结束原因、诊断依据和未知状态，并提供[作业继续与新会话执行](#51-作业继续与新会话执行)允许的操作。用户可以查看历轮输入输出、费用及处置记录。

## 9. Agent 团队与队列

Agent 团队页展示全部 Agent 的启用状态、角色、模型、并发占用、冷却、可用时段和用量限额，并提供[配置](#41-配置)中规定的编辑项。“并发已满时让位”在 Agent 编辑表单中设置，角色池面板只读展示“可让位”徽标。

默认团队、项目池和任务池使用一致的角色分组面板，支持启停、拖动排序以及上移、下移。拖动可跨越多个位置；上移和下移与相邻条目交换位置，已在边界时无变化。任务池标明其继承来源，项目池对既有任务的约束在对应条目中说明。

全局队列按 Agent 展示运行中和排队中的作业及其所属项目、任务、角色、等待原因、可确定的恢复时间及对项目推进的影响。排队中的作业支持调整顺序；运行中的作业提供暂停或强制暂停入口，遵循[统一暂停规则](#32-项目状态)。人工指定 Agent 时在等待原因和作业事件中保留明确标识。角色池展示[Agent 池](#4-agent-池)规定的配置建议与依据。

## 10. 成本用量与审计回溯

成本用量页支持按时间、项目、任务、角色、Agent 和模型聚合，展示 token、费用、作业时长与调用次数。无法由 Agent 提供的数据明确标为未知，不以零值参与汇总；提供原始作业记录入口以核对聚合结果。项目视图提供预算与自动消耗限制表单、限制触发提示及继续处理入口，行为遵循[成本和用量](#6-成本和用量)的规则。

项目审计视图以统一时间线呈现[审计与回溯](#7-审计与回溯)规定的记录。用户可以按对象和事件类型过滤，从事件跳转到相关作业、共享信息版本或可用产物。归档项目保留只读审计入口，Git 项目同时展示可回溯的提交和保留工作区信息。
