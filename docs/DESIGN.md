# DOMO 产品设计

> 本文详细说明 DOMO 的产品功能和设计思路。（本文由人工维护，AI不得擅自修改）

## 0. 产品目标

DOMO 被设计为一个面向个人用户使用的本地单机部署的多 Agent 协作平台。

**面向个人**意味着不需要现实中的协作与沟通，DOMO 实现一个人就是一支团队的现实目标。任何想法都可以由 AI 帮助你实施落地。

**本地**意味着所有除了你提供的大语言模型调用，所有数据都保留在你的电脑上，没有云端接入和账号体系，你拥有全部的控制权。

**单机**意味着不需要它可以直接部署在你的笔记本上，不要昂贵的硬件成本。


## 1. 领域模型

### 1.1 项目

项目是为了达成一个明确目标，在有限资源和范围内，组织起来的一次性交付单元。它承载：

- 最终的交付目标
- 项目分析与方案
- 任务DAG（含里程碑任务）
- 独立的运行时配置
- 整体进度与状态
- 总结报告

### 1.2 任务

任务是项目内的可独立执行、验收的最小单元。它承载：

- 局部的细节设计、执行和验收
- 由项目继承的独立运行时配置
- 阶段性产物、结论与里程碑

*里程碑是任务的一个特殊标记，被标记的任务需要人工进行二次验收*。

### 1.3 Agent 角色

Agent 将扮演多种角色，分别是：
- 规划者：持有项目整体信息，负责与人讨论项目目标、给出项目方案并拆解任务，最终交付验收。
- 执行者：持有简略的项目信息和任务目标，对任务目标进行设计和实现。
- 验收者：持有简略的项目信息和任务目标，对执行者的工作进行核验。

角色的划分并不是为了给不同任务设置不同提示词，虽然它确实承担了这个职责，但这个设计的主要目的是允许给不同的复杂度的任务使用不同的 Agent 和模型。

可将不同角色的分配为不同的 Agent 和模型，根据需要在成本和效果之间找到最佳平衡。一个 Agent 可同时扮演多个不同的角色。

### 1.4 作业

一次 Agent 调用被称作一次作业。作业分两类：由任务推进的作业称为任务作业，执行者与验收者的调用属于此类；由项目阶段推进的作业称为项目作业，规划者的项目分析、直接完成与总结调用属于此类。

### 1.5 工作区

每个项目拥有一个由 DOMO 维护和管理的工作区，用于存放项目运行中的所有相关信息。如任务产物、作业输出……

对于 git 项目，还会利用 worktree 对不同任务进行并发隔离。任务完成或项目归档后，DOMO 回收 worktree 与分支：任务保留原 worktree 路径和回收时间，项目归档保留 `jobs` 目录，分支提交保存在 `refs/domo-archive`。工作区有未提交改动时，归档需要用户确认，确认后保留该 worktree。

## 2. 核心流程

我们的目标是：用户输入 -> AI 执行 -> 结果产出。

这个模型描绘的场景令人兴奋，但现实中受限于自然语言的表达能力和 AI 的智能水平，最终的表现并不总是令人满意。事实上即便是由人组成的团队来负责执行，也很难做到一次达成。因此需要设计一套通用的流程和信息交换方式来帮助 AI 准确执行人的输入。

### 2.1 项目分析

输入的项目目标几乎总是模糊的，如前所述这种模糊来自自然语言的限制、不同的上下文信息和理解能力的不同。项目分析阶段同时完成目标确认和项目规划：规划者阅读仓库、澄清目标，并给出可执行的项目方案。

项目分析由规划者角色完成，输出三类结果：
- 提问：只有缺少会改变任务拆分的关键信息时才向用户提问，用户回答后继续分析。
- 项目方案：给出确认后的目标、关键假设、项目级验收口径、范围边界和任务 DAG。任务必须可独立执行、独立验收，任务之间用依赖表示且无环。
- 直接完成：目标简单到不需要拆分任务时，由 AI 一次性完成实现、自检和总结。

项目分析包含两个可以独立跳过的步骤： AI 向用户提问澄清，以及用户对方案做最终确认。项目可以设置确认方式：
- 人工确认（默认）： AI 给出方案后，必须等待用户确认，DOMO 才创建任务并进入执行，或开始直接完成。
- 自动确认： AI 可以在结果中声明方案已明确，DOMO 直接开始执行； AI 认为仍有歧义时，仍应提问或等待确认。

任务只在方案被确认后创建。直接完成不经过独立验收者，自检结果作为项目报告的一部分；项目报告仍必须经过人工验收，项目才进入完成阶段。

自动确认只影响项目分析阶段，不跳过项目报告的人工验收。

重规划同样经过项目分析阶段。已经确认过方案的项目在重规划后直接应用新方案，不再等待人工确认；如果规划者需要澄清，则重新等待用户回答。

### 2.2 任务执行

按任务描述进行具体执行。任务执行由执行者完成。

根据执行的实际情况 AI 可以请求对项目重新规划。例如原规划中存在明确的事实错误导致当前任务无法达成。
此时执行者应当把当前的具体问题提交给规划者，重新进行[项目分析](#21-项目分析)。

AI 也可以对当前任务进行再次拆分，[派生](#24-任务派生)更多子任务。

### 2.3 任务验收

按任务验收标准对执行阶段的结果进行核查。任务验收由验收者完成。

验收结果只有通过或者拒绝两种。验收通过后，DOMO 把任务分支合并到项目交付分支，合并成功任务才完成。合并冲突时任务退回执行者解决冲突，解决后重新验收；该流程与验收拒绝相同，但不计入验收失败次数。验收被拒绝，则要退回执行者再次执行，并附上拒绝的原因。

如果多次验收都未通过，则应该交由规划者判断，规划者可选择修改验收标准重新验收，或保持现状交由[人工裁决](#5-人工裁决)。

### 2.4 任务派生

任务派生是将一个复杂的，工作量巨大的任务拆分成多个小的、可并行的任务。这个过程很像项目规划的任务拆分，区别是：
- 任务派生由执行者决定，而项目规划由规划者决定
- 派生的任务不需要验收者验收，直接跳过验收阶段
- 派生的任务不能再继续派生新的子任务，以避免无限递归的情况
- 派生的所有子任务之间没有相互依赖关系

任务派生后[任务阶段](#33-任务阶段)变更为待启动，同时所有派生的子任务在 DAG 中自动成为该任务前置任务。
父任务在某一轮作业结束时提交派生请求，之后等待所有子任务完成后将他们的输出作为自己新一轮作业的输入，继续自己的任务阶段流转流程。

派生任务的失败处理逻辑与普通任务相同。

### 2.5 人类干预

在项目完成前，人可以随时对项目进行干预。干预的目的是对 AI 的工作进行指导和纠偏。干预的手段包括：
- 要求重新进行[项目分析](#21-项目分析)
- 将任意未完成的任务标记为里程碑
- 对任意未完成的任务进行指导，指导的内容将在下一次作业时生效
- 修改[项目和任务状态](#3-阶段和状态)：暂停、强制暂停、归档/取消、继续等
- 增加新任务并添加到 DAG。增加新任务可能导致已完成/总结阶段的项目重新回到执行阶段，原项目报告需要重新撰写。

### 2.6 人工验收

流程与验收者相同，都是通过或拒绝两种，同时附上拒绝原因。但根据不同的场景，人工验收还有额外的处理策略

里程碑验收：可要求重新规划或重新执行，附带指导意见
项目总结：可针对报告内容进行多轮讨论，并要求重新撰写、重新规划执行或增加新任务

### 2.7 项目合入

项目进入完成阶段后，人工可以把项目交付分支合入目标分支：

- 合入前在项目 worktree 中对项目分支执行 rebase，目标分支是项目创建时记录的 base 分支。rebase 成功后才把目标分支快进到项目分支提交，历史保持线性，不产生 merge commit。
- 目标分支在某个 worktree 检出时，合入要求该 worktree 没有未提交改动；有改动时拒绝合入，项目分支与目标分支引用都保持操作前的提交。
- rebase 冲突或失败时执行 rebase --abort，项目分支与目标分支都回到操作前提交，错误信息列出冲突文件。DOMO 不自动解决冲突，不强推。
- 目标分支未在任何 worktree 检出时，通过引用更新把目标分支快进到项目分支提交；已检出时在该 worktree 执行 fast-forward 合并。
- 合入成功记录合入时间与项目分支提交。目标分支已包含项目分支提交时，再次合入返回“已是最新”，不产生新的提交、不改变引用。

## 3. 阶段和状态

阶段描述进行到哪一个步骤，状态描述是运行的状态。

很多时候他们容易被混淆，例如，一个任务因为前置任务未完成，和在 Agent 队列中排队，给用户的感受都是它没有在执行。

我们使用两个正交的维度来描述，希望能准确的表达这种差异。

### 3.1 项目阶段

项目阶段包括：
1. 项目分析：项目创建后自动处于该阶段，即项目的初始阶段。规划者在此阶段完成目标澄清、方案确认和任务规划。
2. 执行：方案确认后创建任务并进入该阶段；任务发起的重规划请求被同意也会将项目重置到项目分析阶段。
3. 总结：项目中所有任务完成后，规划者撰写项目报告，并等待人工确认和验收。
4. 完成：项目报告和最终结果被人工确认验收后就进入完成阶段，标识整个项目成功结束。

### 3.2 项目状态

项目状态包括：
1. 阻塞中：项目无法自动流转，需要外部驱动。项目创建后因为还没有输入目标，因此自动处于该状态。
    - 进程重启后的恢复过程中，项目也处于阻塞状态，当状态全部恢复后自动解除阻塞进入运行中。
1. 运行中：只要项目中有任何任务可以无需人工干预的继续执行，项目就处于该状态。
2. 暂停中：用户命令项目暂停后进入该状态。
    - 暂时时项目中所有任务也同时暂停；同理恢复时所有任务也同时恢复。
3. 已暂停：用户命令项目暂停后，项目中所有作业都已经停止，自动进入该状态。
4. 已归档：由用户触发的不再关注的项目，无论项目处于哪种阶段都可以进行归档操作。
    - 已归档的项目立刻停止所有 Agent 作业派发，并终止所有在途作业。
    - 已归档后的项目无法恢复重新执行，但依然可对执行情况进行[回溯和审计](#7-审计与回溯)

*项目可以被取消，取消也视为归档操作*

### 3.3 任务阶段

任务阶段包括：
1. 待启动：前置任务未完成时。
2. 执行：全部前置任务完成时。
3. 验收：执行阶段结束时。若验收未通过，或验收通过后合并到项目交付分支发生冲突，则回到执行阶段。
4. 完成：所有验收通过并合并成功时。

### 3.4 任务状态

任务状态包括：
1. 阻塞中：任务无法自动流转，需要外部驱动。如存在尚未被答复的人工裁决请求。
2. 运行中：Agent 正在执行对应阶段的作业。
3. 队列中：对应角色的 Agent 尚未被释放。
4. 暂停中：用户命令任务暂停后进入该状态。正在进行的作业完成后，不再继续新的作业派发。
5. 已暂停：用户命令任务暂停后，且所有作业都已停止，自动进入该状态。
6. 已取消：不再继续推进的任务，可能处于任意未完成阶段。如被项目重规划后丢弃的旧任务。

### 3.5 正交补充

阶段和任务是两个正交维度，但他们的组合结果并不总是有合理含义的，具体规则如下：

## 4. Agent 池

Agent 池就是一支等待调度的 AI 团队。

项目和任务会使用已配置的 Agent 池，按池的调度策略自动使用。
项目的 Agent 池继承自系统已配置模板，任务的角色池继承自项目，但均可独立修改优先级和启用规则。

### 4.1 配置

Agent 由用户提供，对项目和任务提供相同的能力，包括：
- 模型选择
- 负载队列，如：可并行的最大数量
- 异常检测，如：进程卡死检测
- 可用性计划，如：按时间规划、按用量规划
- 角色选择优先级

默认团队覆盖全部已注册 Agent：每个 Agent 按其角色自动出现在对应的角色分组中，注册 Agent 或修改其角色后自动同步。角色池的成员由全局 Agent 的角色决定，用户只调整角色内的顺序与启停。

角色内优先级在 Agent 池面板中支持拖动条目调整，也提供上移/下移按钮作为键盘替代操作；两种方式保存时都会把该角色内优先级连续重排为 0..n-1。项目池、任务池与默认团队使用同一套面板交互。

### 4.2 队列

当多个任务同时调度到同一个 Agent，且任务数量超过 Agent 的最大负载时，任务就会按调度的先后顺序开始排队。此时用户可以选择：

- 不做干涉，等待 Agent 顺序执行
- 暂停/强制暂停执行中的任务，提前释放 Agent
- 调整队列中未开始的任务的排队顺序

Agent 队列是系统全局的，同一个 Agent 的所有作业共用一个队列。

### 4.3 可用性计划

可用性计划帮助用户自动启停 Agent，合理规划来自不同供应商的账单成本。支持的计划维度有：
- 按时间：针对限时免费和折扣活动，最大化利用优惠政策。
- 按使用量：当 Agent 达到设定阈值后自动禁用。使用量的说明参考[成本与用量](#6-成本与用量)

### 4.4 优先级与调度

每个 Agent 在每个角色下都有一个优先级，同一角色的优先级编号连续且不重复，数字越小优先级越高，0为最高优先级。

当需要对应角色的 Agent 时，按优先级升序检查角色池，第一个可用的 Agent 独占本次派发。

可用指：全局启用、项目 Agent 池对应角色启用、任务 Agent 池启用、具备该角色、未被删除、不在冷却中、处于可用时段且未达到用量限额。执行者与验收者使用任务 Agent 池，同时受项目 Agent 池对应角色的启停约束；规划者使用项目 Agent 池。
可用但并发已满的 Agent 不派发也不让位：任务保持队列中，等待原因记录该 Agent 名称与并发占用（如“等待 Agent X 释放（并发 1/1）”）。
只有高优先级 Agent 不可用时才检查下一优先级；全部不可用时，阻塞信息逐个列出每个 Agent 及其不可用原因。

正常调度不使用上次执行者做轮转，同一任务重新执行时仍从最高优先级的可用 Agent 开始。

作业失败后的处置对任务作业和项目作业一致：

- 作业失败时按失败原因分类，记录在作业与 Agent 上。原因分为限流、供应商波动、永久错误和任务失败。
- 限流：立即让该 Agent 冷却，冷却时长取 Agent 返回的重试信息，没有信息时使用默认值。
- 供应商波动：同一 Agent 先按有限次数重试，次数用尽后让该 Agent 冷却并换人。
- 永久错误：不在该 Agent 上重试，直接换人。
- 任务失败：如验收未通过、结果不符合协议，属于任务自身的问题，不更换 Agent。

需要换人时，本次派发记录一次性跳过失败 Agent 的状态：下一次派发跳过它，派发成功后清除。项目作业的跳过状态记在项目上，规划者的分析、直接完成和总结作业共用同一份记录。

换人后作业按原阶段重新派发：

- 任务作业：任务保持队列中，重新派发前按任务池优先级选人。
- 项目作业：项目保持运行中，由调度器重新派发，按项目池优先级选人。

只有任务作业或项目作业在本角色下已经没有可用 Agent 时才进入阻塞，等待[人工裁决](#5-人工裁决)。阻塞原因记录失败原因；阻塞后不清理 Agent 冷却，也不由调度器自动重派，重新派发需要人工重试或裁决。

### 4.5 启停与角色池修改

启停分为三层，任一层停用都不再向该 Agent 派发新作业：

- 全局开关：Agent 团队页的 Agent 级开关，影响所有项目与任务。
- 项目池开关：项目 Agent 池与默认团队中按角色的启停。项目 Agent 池的角色启停只影响当前项目，并屏蔽该项目已有任务的同角色派发；任务池快照不被改写。
- 任务池开关：任务 Agent 池按角色的启停，只影响该任务。

用户可以修改 Agent 的优先级和启用状态。角色池成员由全局 Agent 的角色决定。

优先级变更每次可将一个Agent的优先级调高一级，原上一级优先级的Agent自动下降一级。无更高优先级时无变化。

启停状态只有开关两种状态。启停状态不影响优先级的设置。全局开关只屏蔽派发，不改写项目与任务配置。

### 4.6 任务专用 Agent 池

任务专用 Agent 池由项目 Agent 池派生，只包含执行者与验收者两个角色分组。任务创建时在同一事务内把项目池对应角色的全部条目、优先级与启停状态快照到任务池；已有任务在首次访问或首次调度时完成快照。项目池后续变化不会改写既有任务池。

任务池支持与项目池相同的排序与启停操作，改动只作用于该任务。任务池成员由项目池快照确定，只调整顺序与启停。

执行者与验收者按任务池的严格优先级选人，同时要求项目池对应角色处于启用状态。项目池对应角色停用后，已有任务也不再派发该 Agent；重新启用后任务池原有启停恢复。项目池中缺少该条目时不阻塞任务池，历史快照保持可用。任务池某角色只有一个启用 Agent 时，该角色的全部作业都派给该 Agent。任务池为空或全部不可用时，任务保持等待并给出原因，不回退到项目池。规划者仍使用项目池。

任务上保留 executor_agent_id/verifier_agent_id 作为只读兼容字段。旧任务首次初始化时，这两个字段会迁移为对应角色的单 Agent 池。旧的任务 Agent 覆盖接口作为兼容入口：指定 Agent 映射为单 Agent 池，清除覆盖映射为按项目池重置该角色。


## 5. 人工裁决

当系统遇到无法恢复的错误，或 AI 遇到无法解决的问题时，则需要人工裁决。
此时会提供必要信息，包括事件类型、关联项目和任务、其他必要上下文，供人类做出合适的判断。

根据类型的不同可能由不同的处置策略：
- Agent 作业失败：重试、更换 Agent
- 无可用 Agent： 更换 Agent
- 任务核验多次被退回：指导规划者重规划、指导执行者重试、更换 Agent（执行者）、更换 Agent (验收者)

*更换 Agent的含义是：临时使用指定的 Agent 执行本次任务，不遵循 Agent 池的调度策略和启用约束。*

作业重试是用户在作业层面解除阻塞的手段，界面上的重试按钮落在具体作业上。项目分析、直接完成或总结阶段的作业失败使项目停住时，作业重试让该阶段的作业重新排队，项目随之从阻塞回到运行中。其他原因造成的项目阻塞由对应机制解除，不通过作业重试处理。

作业重试只在派发成功以后才清除冷却与失败计数，并按角色清除，只清除本次重试实际派发到的单个 Agent：项目作业重试作用于规划者，清除项目池规划角色中该 Agent 的冷却；任务作业重试与人工裁决作用于该任务的执行者与验收者，清除任务池对应角色中该 Agent 的冷却。其余 Agent 保持原有退避。


## 6. 成本和用量

DOMO 将记录每次 Agent 调用的成本，包括输入与输出 token 数量，费用与时长。这些记录的信息用于：
- 支持[可用性计划](#43-可用性计划)的实施。
- 对用户提供多种维度的聚合的统计信息。

统计数据由 Agent 自身提供，无法提供的 Agent 信息也会被明确记录为未知，并在聚合展示时特殊标记。


## 7. 审计与回溯

DOMO 详细记录项目中的所有信息，用户可以在任意时刻对已发生的行为进行详细的分析和溯源。
记录的内容包括：
- 项目的阶段和状态变更
- 任务的阶段和状态变更
- 人工裁决结果
- 异常与恢复情况
- 作业记录，包括起止时间和输入输出

归档项目的 `jobs` 目录作为审计资产保留。任务和项目分支的提交保存在 `refs/domo-archive`，该命名空间不进入普通分支列表；备份仓库时使用 `git bundle create <file> --all` 或显式推送 `refs/domo-archive/*`。

# 用户界面设计

## 8. 项目列表

项目列表以卡片展示项目名称、目标、阶段、状态和任务进度。已合入的项目在卡片上显示“已合入”与短提交号。顶部提供阶段与状态两组分类标签：

- 阶段标签取项目分析、执行、总结、完成；状态标签取运行中、阻塞中、暂停中、已暂停、已归档。
- 同组多选为“或”，两组之间为“且”；组内不选表示该维度不过滤。
- 标签显示当前已加载项目中的数量；任一标签选中时提供一键重置。
- 过滤结果为空时显示空状态与重置入口；项目集合为空时显示“还没有项目”。

## 9. 项目详情

项目详情展示完成横幅。项目处于完成阶段且目标分支尚未包含项目分支提交时，横幅提供“合入到 base 分支”按钮；点击前需要确认，执行期间按钮禁用。成功、已是最新和失败结果都显示在横幅内。目标分支已包含项目分支提交时（包括在 DOMO 之外完成的合入），横幅不再显示合入按钮；DOMO 记录的合入显示目标分支、合入时间与短提交号，刷新后保持。

## 10. 任务 DAG 视图

任务面板支持列表与 DAG 两种视图，默认列表，视图选择只保存在页面状态。

DAG 视图按任务依赖计算拓扑层级：同层任务并列，依赖边由前置任务指向后继任务，派生任务与父任务的关系用虚线表示。节点展示任务 key、标题、阶段与状态徽标、里程碑与派生标记；取消的任务不进入图。节点可以点击或用键盘 Enter/Space 打开任务抽屉。依赖缺失或存在环时给出提示，布局不会进入死循环。

## 11. 原始内容视图

作业结果、项目报告、消息与事件等原始内容默认使用友好视图展示：Markdown 内容按 Markdown 渲染，JSON 内容按结构化的键值层级展示。每一处友好视图都保留原文切换，便于查看未经渲染的原始文本。
