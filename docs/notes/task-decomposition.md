# 任务拆分如何影响成本与交付效果：方案比较与选择依据

> 2026-11-06：围绕任务拆分的收益、代价和适用条件，记录 DOMO 的方案取舍与决策依据。

## 1. 要优化的不是任务数量，而是合格交付的总成本

将复杂目标拆成多个任务，是多 Agent 系统最自然的组织方式之一：每个执行者只处理一部分问题，各自完成后再整合。它看起来既降低了单个任务的难度，又为并行和独立检查创造了条件。因此，很容易进一步推导出“拆得更细，执行就更可靠”。

这个推导缺少一个前提：**拆分产生的收益，必须足以支付任务之间的交接和整合成本。** 如果子任务高度耦合，增加任务可能只是把同一项工作分散到更多上下文中，再花额外成本恢复它的完整性。是否存在这种问题，取决于任务边界和信息依赖，而不是工作被安排为串行还是并行。

反过来，不拆分也不是天然更好。一个执行者承担过大的目标，可能逐渐丢失约束、漏掉分支、难以定位错误；某些工作确实需要独立探索、专门能力或权限隔离。任务粒度的选择不是“单 Agent 与多 Agent 谁更先进”，而是在不同任务结构下，选择更合适的协作方式。

我们的目标是：**在满足相同交付标准的前提下，降低完成一个合格目标所需的总成本。** 总成本包括调用费用、实际经过时间、返工，以及用户监督和收尾的投入。任务数量、Agent 数量、局部通过率和并行度都只是过程指标，不能独立代表这个目标。

## 2. 拆分通过哪些机制影响成本和效果？

### 2.1 正向作用：聚焦、并行与风险隔离

拆分可以让执行者只携带与当前工作有关的上下文，减少无关信息干扰。独立工作如果拥有稳定输入和清晰输出，还可以并行推进，或者使用更适合的工具、模型与权限。任务边界也可以成为检查点，让错误在进入下一阶段之前被发现，避免将返工推迟到最终交付。

这些收益并不要求任务一定很小。例如，一个独立资料调查可能需要大量搜索，但只向主流程交付少量有来源的结论，因而能够有效隔离上下文；一个技术验证即使只能串行执行，也可能提前排除不可行路线，减少后续无效实现。

### 2.2 负向作用：上下文重建、信息损失与整合返工

每建立一个交接边界，接收者都需要理解目标、约束、当前状态和前序结果。摘要能够降低传输量，但不能无损保留全部推理背景；为了保证正确性，下一个执行者或验收者往往还要回到原始文件和证据重新核对。

如果多个任务反复读取相同代码、理解相同协议，并调整同一组约束，拆分没有真正隔离复杂度，只是重复支付理解成本。局部任务还可能各自成立、组合后不成立：接口假设不一致、责任落在边界之间，或者每一方都把关键接线留给后续任务。此时“全部子任务通过”并不能消除整合工作。

但重复检查不应一概视为浪费。独立验收者从不同角度复核同一行为，可能发现执行者自测遗漏的真实缺陷。需要减少的是没有相应收益的重复，而不是所有重复。

### 2.3 费用、时长和质量不是同一条曲线

需要区分两个决策：任务拆分决定工作由哪些执行单元承担、需要传递什么信息以及如何整合；任务调度决定这些工作何时执行。假设任务划分、模型、输入、验证要求和执行路径不变，仅将可独立的工作从串行改为并行，主要改变的是实际经过时间，并不必然改变累计 Token 或最终质量。串行执行也不使一个原本合理的任务边界失去价值。

并行可能通过信息和状态的相互作用间接改变成本与质量。例如，接口仍在变化时，同时实现可能增加假设分歧与返工；独立探索也可能减少相互锚定，提供不同视角。这些影响来自共享状态、信息依赖和协调方式，不是“同时执行”天然更好或更坏。较长的单个任务也可能减少交接，却增加长上下文处理和错误恢复的成本。

因此，不能假定存在一个适用于所有目标的“最佳任务数”，也不能从任务时长短、验收投入高，直接推出过度拆分。更合理的比较是：

> 增加一个任务边界，能获得什么原本得不到的收益？为这个边界付出的重复理解、验证、交接和整合，是否值得？

这是一种定性决策框架，不要求 AI 编造精确节省分钟数，也不意味着收益随粒度变化一定服从某条固定曲线。

## 3. 不同拆分方式的优劣势

以下方式并非互斥：一个项目可以按能力划分主任务，在其中保留独立技术验证，再对真正独立的模块并行分工。比较的重点是各类边界能隔离什么、又会引入什么成本。

| 组织方式 | 主要收益 | 主要代价或风险 | 更适合的条件 |
|---|---|---|---|
| 一个执行者连续推进完整目标 | 共享完整上下文，减少交接，跨层调整直接 | 目标过大时上下文负担重，容易遗漏，缺少执行并行 | 目标可控、强耦合、需要频繁共同调整 |
| 按步骤、工序或文件细拆 | 工作清单清楚，局部反馈早，易指定狭窄职责 | 交接多；按文件分开不等于工程独立；实现、测试和文档可能反复理解相同背景 | 工序接口稳定、步骤可机械验证，或确有专业分工与权限要求 |
| 按模块、技术层拆分 | 能利用模块化和专业能力；稳定接口下可独立实现与复用 | 容易推迟集成，局部完成可能只证明替身或接口成立；跨层缺陷到整合时才暴露 | 模块边界成熟，输入输出明确，独立交付有真实消费者 |
| 按可验证能力或交付闭环拆分 | 更早形成可用结果；同一执行者负责跨层一致性，减少责任缝隙 | 单任务更大；不同能力可能修改公共部分；并非所有工作都能独立形成闭环 | 需要较早验证真实链路，组件之间耦合较强 |
| 将调查、技术验证或风险判断独立成任务 | 先减少不确定性，避免错误路线扩大；可隔离大量搜索背景 | 容易把本可顺手完成的调查形式化；如果结论无人消费，就增加一次无效交接 | 验证结果会改变方案选择，且结论可独立核查 |
| 随认识深化逐步拆分，而非预先穷尽全部细节 | 减少基于假设的过早分工，能根据真实边界调整 | 会增加规划和协调；连续派生可能掩盖原范围估计不足，并使完成边界不断后移 | 长期、高不确定性工作，且调整范围、保留成果和完成条件可控 |

### 3.1 为什么按技术层拆分经常合理，却不适合作为默认模板？

技术分层首先服务于代码结构和复用，不必然对应 Agent 的委派边界。数据查询、格式转换、文件生成和下载接口，在代码中可以分开；但如果它们需要不断共同调整，分别交给不同上下文执行，反而会加大约定解释与接线成本。

以一个假设的报表导出功能为例，可以依次派发“查询—格式转换—文件生成—下载接口—整合测试”，也可以先让一个执行者完成一种格式从查询到下载的闭环，再扩展其他格式和大数据量处理。这个示例用于比较组织方式，不对应具体项目的任务记录。

前一种方式的优势是模块职责清楚，适合接口已经稳定的工程；后一种方式的优势是较早验证字段含义、数据权限和下载内容是否一致，更适合接口仍在形成的工程。我们不认为前者错误，而是认为**不能仅因为架构图分了五层，就默认需要五次委派。**

### 3.2 为什么也不选择“一律按端到端能力拆分”？

稳定协议库、独立数据集、带来源的研究结论，都可能是有价值的中间交付。强求每个任务端到端，可能迫使不同任务重复实现公共部分，或者把本来能独立完成的工作绑在一起。公共文件频繁冲突时，表面上的多个能力也未必能够真正并行。

因此，“完整能力”是优先考虑的边界，不是唯一合法边界。关键仍是交接结果能否独立核查、是否有明确消费者，以及分开之后是否真的减少了每个执行者需要掌握的复杂度。

## 4. 拆分与独立验收：两个需要分开决定的问题

任务拆得细，通常会带来更多验收，但不能因此把独立验收的收益全部归给拆分，也不能为了减少拆分成本而一并取消验收。

| 执行与检查组合 | 优点 | 局限 |
|---|---|---|
| 单个执行者完成并自检 | 流程最短，没有外部交接与审查成本 | 实现和检查共享盲点，对高风险目标可能不够 |
| 较完整的执行单元，加独立验收 | 保留执行连续性，同时获得不同上下文的检查 | 仍需支付独立理解和核验成本；单元过大时反馈可能偏晚 |
| 细粒度委派，每个任务独立验收，再做整体验收 | 局部问题可较早阻断，适合需要分别交付的工作 | 验收与交接次数多，可能重复证明相近行为；局部通过仍不能替代集成 |

我们更关注第二种组合：**让必须一起调整的内容一起执行，让值得独立判断的交付接受独立验收。** 在 DOMO 中，这体现为选择合适的任务边界，而不是让执行者自行跳过某些任务的验收。每个独立任务仍遵循验收流程。

单任务方案也不等于直接完成。一个高风险目标即使不值得拆成多个执行单元，也可能必须由独立验收者检查。执行者连续处理同样不意味着无限延长会话、不保留检查点，或由验收者顺手修复交付物。

## 5. 示例推演与公开研究：选择依据及其限度

### 5.1 从假设场景看收益如何随边界改变

以下场景经过抽象和脱敏，仅用于推演不同组织方式的影响，不是具体项目的运行记录，也不构成实测效果证据。

**场景一：强耦合的报表导出。** 查询、转换和下载分别由不同执行者完成，各自测试都通过，但整合时发现时区、字段含义与数据权限的理解不一致。如果这些约定仍需反复共同调整，分层委派就可能增加重新理解与返工。让一个执行者先跑通一种格式的完整链路，可能更早暴露组合问题；但目标范围过大时，也可能推迟反馈、增加遗漏。这支持优先考虑能力闭环，不支持一律合并所有模块。

**场景二：可独立消费的资料调查。** 一份研究报告需要比较不同地区的公开政策，检索范围可分离，结果可以统一为带来源、适用日期和限制的结构化结论。分工能够隔离大量原始材料，这项价值在串行和并行执行下都可以成立；并行可能额外缩短交付时间，但不能据此推断调查质量更高或累计 Token 更少。若所有调查者都重新设计比较口径，整合成本仍会升高。这说明清晰的消费接口比任务大小或执行顺序本身更重要。

**场景三：实现通过自检，但独立检查提出反例。** 报表执行者验证了常规导出，验收者另外检查跨租户权限或空数据边界，发现了遗漏。此时额外检查可能有价值，但不能据此证明查询、转换和下载必须由不同执行者完成：较完整的单个执行任务也可以接受同样的独立验收。

这些推演解释了成本和效果可能如何变化，不能量化哪种方案更好。要判断净收益，仍需相同目标、相同起点和可比预算的实际对照；不能把局部通过、验收发现问题或任务数量变化直接当作最终交付改善。

### 5.2 公开研究支持按条件选择，不支持固定答案

[研究 1](#参考资料) 在受控配置中发现，协作效果高度依赖任务和架构：可分解金融分析有明显收益，强顺序规划可能显著退化；较强单 Agent 基线下，额外协作的收益趋于递减。其软件工程与终端任务每配置仅 20 个实例，不能直接外推到长期跨仓库工程，更不能把经验阈值当作 DOMO 的规则。

[研究 2](#参考资料) 从多 Agent 轨迹中归纳出系统设计、Agent 间失配和任务验证等失败模式。它说明问题可能来自组织与交接，而非单个模型能力不足；但失败分类本身不是单、多 Agent 的成本效果对照。

[实践 3](#参考资料) 展示了多 Agent 对广度研究的价值，同时指出大量共享上下文、密集依赖和多数编码任务较难获得同样的并行收益。其内部评测和 Token 统计不能直接当作等预算架构比较，尤其“约 15 倍 Token”的参照是普通聊天，不是单 Agent。[研究 4](#参考资料) 对单、多 Agent 按请求级联的探索，也提示应把协作看作可选择的策略，而不是固定组织形式。

这些材料共同支持的决策方法是：**以强单 Agent 或连续执行为参照，识别具体任务的瓶颈，再增加有针对性的协作。** 它们没有证明某个任务数、某种粒度或我们选择的方案普遍最优。

## 6. 当拆分由 AI 决定，应该用什么方式约束？

即使认同上述权衡，仍有第二层选择：由平台怎样影响 AI 的拆分判断。不同控制方式也会影响成本。

| 控制方式 | 优点 | 不足 | 我们的取舍 |
|---|---|---|---|
| 降低任务数量上限，或规定目标任务数 | 简单、确定，能限制极端膨胀 | 不理解耦合关系；可能把无关工作塞进巨型任务，或促使模型凑数 | 数量上限只作为安全边界，不作为粒度优化目标 |
| 按文件重叠、依赖链长度等规则自动合并 | 可机械执行，不增加模型审查调用 | 相同文件不一定必须同任务；无共同文件也可能高度耦合；误合并可能改变授权和验收范围 | 不用于自动修改已确认计划 |
| 增加一个专门审查粒度的 Agent | 提供第二视角，可集中发现不合理边界 | 自身增加调用、交接和决策分歧；收益尚不足以证明需要常驻流程 | 不作为默认步骤，只有证据证明净收益时再考虑 |
| 增加工作项、执行组、验收组等多层对象 | 可分别表达进度细节与实际委派、验收边界 | 状态、依赖、版本和恢复语义更复杂，平台维护成本上升 | 不先扩展对象体系；优先用任务内部步骤承载工作细节 |
| 在现有规划中显式比较分工收益和交接成本 | 适应语义和项目差异，不增加常驻角色，可同时覆盖初始规划与执行中派生 | 依赖模型判断，可能给出形式化理由，不能靠协议校验保证质量 | 作为当前选择，保留效果不确定性 |

这里没有一个免费且完全可靠的控制器。当前选择优先补全 AI 的决策依据：在尚无证据证明需要更多流程对象或固定数量限制时，先让规划考虑分工收益与交接成本，能以较小的系统复杂度验证方向。这个选择是风险与复杂度的权衡，不是对问题根因的实测定论；不能因为它改动小，就假定它一定有效。

## 7. 我们选择的方案及其理由

### 7.1 选择：以交接价值决定委派边界，默认连续处理强耦合工作

我们的默认不是“始终单 Agent”，也不是“始终粗粒度”，而是：**实现步骤可以细，委派边界应当有理由。** 对共享大量上下文、需要共同调整的工作，优先放在同一个执行单元；能够获得实际并行、上下文隔离、专门能力、必要授权隔离或独立风险判断时，再拆出任务。

这保留了几种方案各自有价值的部分：连续执行减少强耦合交接，能力闭环帮助提前验证集成，模块分工和独立调查在边界清楚时仍然成立。它不追求一套固定模板覆盖所有工程。

### 7.2 为什么要求说明收益，并在提交前考虑合并？

“少拆一点”缺少可执行判据，“任务复杂就拆”又只考虑了局部难度。要求说明具体收益，相当于把交接成本纳入同一次规划的决策，而不是在执行之后才发现组织成本过高。

判断重点是：如果不交接，由当前执行者继续，会失去什么？如果相邻任务要重复理解大部分相同背景，或者中间结果只有等后续接线才可验证，而分开又没有独立价值，就更适合保留为同一任务内的步骤。反之，明确的授权边界、稳定接口和影响路线的技术验证不应为了少几个任务而被合并。

只限制首次规划不足以维持这个选择。执行中派生和重规划也应采用同样的判断，否则初始大任务仍会在后续被逐层拆碎。尤其是父任务派生后仍需整合和验收，不能只计算子任务变简单的收益，而忽略父任务重新恢复全局理解的代价。

### 7.3 为什么保留独立验收，而不是直接压缩全部流程？

独立检查提供不同于实现者自检的观察角度，有机会发现共同盲点之外的缺陷；前面的假设场景说明，这种价值不依赖于把实现拆成很多任务。对需要质量保证的交付，相比直接取消检查，先减少没有必要的执行交接，风险更可控，也更容易识别优化来自哪里。这是保留检查机制的理由，不是独立验收收益已经得到量化的结论。

因此，我们通过合理的任务单元减少不必要的交接和重复验收，不降低已约定标准，不让“减少任务数”成为选择自检模式的理由。已确认计划仍受原有范围和确认约束，粒度原则不是随时合并现有任务的授权。

### 7.4 为什么将任务边界与调度安排分开判断？

拆分的质量与 Token 权衡，主要看是否隔离复杂度、是否重复理解、交接是否损失信息、整合是否增加返工，以及独立检查是否值得。执行设施提供的并发能力不直接回答这些问题，不作为决定粒度的分类依据。

并行是可以单独评估的时长收益：在质量要求和资源预算允许时，它可能使清晰的独立分工更有吸引力；但不应仅为创造并行度拆开强耦合工作，也不应仅因串行执行合并合理的独立任务。工程依赖始终表达成果之间的真实前置关系，不能为迁就调度而制造或隐藏依赖。

## 8. 这个决定仍承担哪些风险？

较完整的任务可能推迟反馈，增加一次失败的恢复范围；模型也可能过度纠偏，把所有工作收进一个巨大任务。反过来，要求分工理由可能只得到“便于并行”“降低复杂度”等形式化解释，而没有实际收益。因此，解释完整不等于边界合理，任务数下降也不等于优化成功。

我们将这个选择视为有依据、但需要交付结果检验的默认策略，而不是研究已经证明的最优解。最重要的对照是：在同样质量要求下，“连续执行加独立验收”与“细粒度委派加独立验收”各自付出了什么、交付了什么；另设“单执行者自检”作为参照，才能区分独立检查与任务拆分的作用。

评价应关注最终成功率、严重缺陷与漏检、实际经过时间、可靠费用数据、整合返工和用户投入，并使用可比目标、起点、权限与预算。规则被正确投递、流程测试通过，只能证明机制按预期工作，不能证明拆分质量提升。

如果数据表明较大单元持续导致遗漏和昂贵返工，就应重新细分；如果边界稳定的并行任务持续获益，就应更积极分工；如果粒度判断本身成为主要失败来源，再评估独立规划审查或更丰富的执行分组。重新考虑的依据应是这些净收益，而不是追求更简单或更复杂的组织形式本身。
