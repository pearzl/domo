## 一、规划与任务（H1–H3）

### H1–H2 用户目标 → 分析方案 → 确认

> 2026-11-07 定稿。本文定义项目创建到方案确认之间的交接：目标怎么表达、约束与假设怎么分离、方案怎么讨论与确认。
> 上游：用户输入。下游：H3（方案 → 任务记录）。
> 不在范围：任务派发（H5/H6）、重规划决策（H4）。

### 1. 现状与本次调整

现状：

- 创建项目时选择确认方式（自动 / 人工）；
- 分析作业输出 questions / plan / direct 三种结果；
- 自动确认模式下，规划者用 skip_confirmation 决定是否直接执行；
- 确认时提交的方案必须与库里完全一致，否则报“方案已变化”；
- 存在“直接完成”模式，不拆任务。

本次调整：

- **移除“直接完成”**：所有项目都必须拆成任务，流程只有一条；
- **移除 skip_confirmation**：确认方式只由项目设置决定，Agent 不参与；
- 确认之前方案都是草稿，不引入版本号；
- 不再做方案的结构化对比，改由规划者在回复里说明改了什么。

### 2. H1：目标、约束、假设三分

#### 2.1 为什么分

三样东西的命运不同：

- **目标**：要达成什么，会被执行；
- **约束**：不能违反什么，会被违反；
- **假设**：方案成立的前提，会被推翻。

混在一段文字里，就没人能判断“这条是要做的、不能碰的，还是先这么认为的”。

#### 2.2 目标

用户要达成的东西，原样保留。不做结构化拆解，由规划者在方案里解释。

#### 2.3 约束

用户明确提出、不能违反的限制。例如：

- 某个目录只读；
- 报告不写入仓库；
- 必须使用指定的工具链版本；
- 不得引入某类依赖。

规则：

- **由规划者在分析时从目标与对话中提取**，用户不填专门字段；
- 方案面板中逐条展示，用户可以核对；
- 随契约注入每个执行作业（H6 已有位置）；
- 与假设分开：约束是“必须遵守”，假设是“目前这么认为”。

#### 2.4 假设

**定位：规划者对方案前提的判断。**

它有三个作用：

1. 方案成立的依据；
2. 执行者的检查清单；
3. 重规划的触发线索。

写作要求：

- 每条必须**可被验证**，不能写成模糊判断；
- 每条必须说明**若不成立会影响什么**；
- 不是所有假设被推翻都要重规划，只有“若不成立会影响方案有效性”的才需要。

执行者发现假设被证伪时，按 H7 的 replan 提交请求，说明哪条假设、证据、影响与建议；不得自行改方案继续做。

### 3. H2：方案讨论与确认

#### 3.1 两种确认模式

| 设置 | 方案返回后 | 讨论 | 要改方案 |
|---|---|---|---|
| 人工确认 | 展示，等待确认 | 可以 | 讨论后规划者修订 |
| 自动确认 | 直接生效，开始执行 | 不可以 | 走重规划 |

自动模式下没有讨论窗口：方案一经返回即视为已确认，项目进入执行。用户要改，只能发起重规划。

#### 3.2 讨论通道（仅人工确认模式）

人只有一个输入框：**跟规划者讨论**。不需要先判断“我这是在提问还是在提意见”。

理由：

- 真实讨论是混着的：“为什么用 A？我觉得 B 更好”既是提问也是意见；
- 要求人先分类，是把系统的分类负担转给人；
- 由规划者判断“要不要改方案”，比人判断“这算不算意见”更可靠。

规则：

- 讨论期间项目状态不变，不进入执行；
- 可以多轮；
- 规划者每条回复必须声明方案是否修改；
- 确认或归档后，通道关闭。

与报告讨论不同：报告描述的是已验收的交付，讨论中不允许修改报告（H15）；方案还是草稿，所以可以改。

#### 3.3 规划者必须声明是否修改

分析结果只有三种：

| kind | 含义 | 结果 |
|---|---|---|
| reply | 只回答，方案不变 | 对话继续 |
| questions | 需要澄清，尚未形成方案 | 等待用户回答 |
| plan | 方案（首次或修订） | 展示方案，等待确认或继续讨论 |

讨论中如果方案没变，必须返回 reply，不能返回内容相同的 plan。否则系统分不清“回答了”和“改了”。

返回 plan 时，message 必须说明本次改了什么；没有单独的变更字段，也不做结构化对比。

#### 3.4 草稿与确认

- 确认之前，方案都是草稿；被覆盖的草稿只留在对话记录里，不单独保留版本；
- 确认作用于**当前草稿**；确认即冻结，成为本次执行的契约版本；
- 不引入方案版本号，也不做“与上一版对比”的机械判断。

#### 3.5 逐条回复

每个分析作业对应一条用户消息（有作业在跑时拒绝新消息），所以回复天然一一对应。

一条消息里提了多件事，就在 message 里逐段回答，不强制结构化。

#### 3.6 方案提问

提问与讨论是同一个通道，不单独区分：

- 只在人工确认模式下存在；
- 只回答时返回 reply；需要改方案时返回 plan 并在 message 中说明；
- 不改变项目状态；
- 讨论记录进入项目历史，与方案放在一起。

#### 3.7 目标变更

- 确认后目标锁定；
- 修改目标走单独入口，触发一次重规划；
- 已完成项目不允许改目标，需要新项目；
- 界面上要说明“改目标 = 重新规划整份方案”。

#### 3.8 放弃

讨论中途放弃只能归档项目。不提供“丢弃草稿回到旧方案”，因为旧方案也是草稿，从未生效。

### 4. 分析作业的结果契约

#### 4.1 三种结果

~~~json
{ "kind": "reply", "message": "回答" }

{ "kind": "questions", "message": "为什么需要澄清", "questions": ["问题"] }

{
  "kind": "plan",
  "message": "方案摘要；修订时必须说明本次改了什么",
  "goal": "项目目标",
  "constraints": ["不能违反的限制"],
  "assumptions": ["方案前提；可验证，并说明若不成立的影响"],
  "acceptance": ["项目级验收标准"],
  "tasks": [
    { "key": "T1", "title": "……", "description": "……",
      "acceptance": ["……"], "deps": [] }
  ]
}
~~~

#### 4.2 字段说明

| 字段 | 适用 | 说明 |
|---|---|---|
| message | 全部 | 面向人的回复或说明，Markdown，≤1000 字 |
| questions | questions | 需要用户澄清的问题 |
| goal | plan | 项目目标，确认时写入项目 |
| constraints | plan | 约束列表，展示并注入执行 |
| assumptions | plan | 假设列表，每条可验证并写明影响 |
| acceptance | plan | 项目级验收标准 |
| tasks | plan | 任务列表，key 唯一、deps 无环 |

没有 skip_confirmation：确认方式由项目设置决定。

#### 4.3 为什么 message 限 1000 字

对话里的话应该能被读完。超过 1000 字，说明内容该放进任务描述或文档，而不是当成一句回复。修订说明也包含在内，因此修订应当聚焦，不必复述整份方案。

### 5. 场景推演

| 场景 | 处理 |
|---|---|
| 目标为空 | 项目阻塞，等待输入 |
| 目标含糊、缺关键信息 | 规划者返回 questions，不强行出方案 |
| 目标里夹着约束 | 规划者提取到约束列表，方案面板展示 |
| 人工模式：人问“为什么这么拆” | 返回 reply，方案不变 |
| 人工模式：人指出拆分有问题 | 返回 plan，message 说明改了什么 |
| 人工模式：人一次提三件事 | 逐段回答；涉及方案的说明改动 |
| 自动模式：方案返回 | 直接生效，进入执行 |
| 自动模式：人想改 | 发起重规划 |
| 人工模式：人不确认也不说话 | 项目停在等待确认 |
| 确认后要改目标 | 单独入口，触发重规划 |
| 讨论中途放弃 | 归档项目 |
| 执行中发现假设不成立 | 按 replan 请求，说明假设、证据与影响 |

### 6. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| 直接完成模式 | 保留 / 移除 | **移除**，流程只有一条 |
| skip_confirmation | 保留 / 移除 | **移除**，确认方式只由项目设置决定 |
| 目标与约束 | 混在目标文本 / 独立约束列表 | **独立约束列表**，规划者提取、方案面板核对、注入执行 |
| 假设的定义 | 未证实的事实 / 方案前提 | **方案前提**，必须可验证并写明影响 |
| 讨论方式 | 分“提问”和“意见” / 一个通道 | **一个通道**，规划者判断是否修改 |
| 方案对比 | 结构化变更清单 / Markdown 文本 / 机械 diff | **Markdown 文本**，限 1000 字 |
| 方案版本 | 引入版本号 / 草稿不分版 | **草稿不分版**，确认时冻结当前草稿 |
| 结构核对 | 机械提示 key 增删 / 不做 | **不做**，这些信息对人没有意义 |

### 7. 决策依据

1. **流程只有一条**：移除直接完成，所有项目走任务、验收、报告、人工，不需要为特例解释。
2. **确认方式不该由 Agent 决定**：项目设置已经表达用户意图，Agent 再加一层会让行为不可预测。
3. **目标、约束、假设的命运不同**：一个要被实现，一个不能被违反，一个可能被推翻。
4. **假设是重规划的线索**：只有写明“不成立会影响什么”，执行者才知道什么时候该停下来请求决策。
5. **讨论不该要求人先分类**：问和说是混着的，判断权交给规划者更自然。
6. **确认前都是草稿**：既然没有生效，版本号、对比算法都是多余的；人读规划者的说明即可。

### 8. 移交 H3

- 方案里的任务如何落成任务记录；
- 任务 key 的唯一性（H3 已定：终身唯一）；
- 约束与假设如何随任务进入执行（H6 已定注入，H3 定存储）。

### 9. 风险

- 约束由规划者提取，可能漏掉用户随口提到的一条；缓解：方案面板展示，用户可补。
- 假设要求“写明影响”，可能被写成套话；缓解：验收时可检查假设是否可验证。
- 自动模式没有讨论窗口，方案不合适时只能重规划；这是“自动”的代价，选择该模式即接受。
- 变更说明由规划者撰写，可能漏报；系统不做核对，靠人读方案判断。
- 草稿不保留版本，被覆盖后只能从对话记录追溯。


### H3 方案 → 任务记录

> 2026-11-07 定稿。本文定义已确认方案如何变成任务记录，以及任务身份（key）的规则。
> 上游：H1–H2（方案确认）。下游：H5/H6（依赖与执行上下文）。
> 不在范围：任务派发、执行、验收。

### 1. 定位

方案是计划，任务记录是执行单位。这一步只做两件事：

- 把方案里的任务落成记录；
- 给每个任务一个在整个项目生命周期内都唯一的身份。

任务描述与验收标准以契约为准（H6），任务记录只额外承载运行状态、指导与反馈。

### 2. 任务字段

| 字段 | 来源 | 说明 |
|---|---|---|
| key | 方案 | 项目内唯一，终身不复用 |
| title | 方案 | 简短标题 |
| description | 方案 | 目标、范围与边界 |
| acceptance | 方案 | 至少一条；不允许为空 |
| deps | 方案 | 只能引用本批次任务，无环、不自依赖 |

### 3. key：终身唯一的身份

#### 3.1 规则

- key 在**整个项目**内唯一，取消任务也不释放；
- 新任务从已用最大编号之后继续；
- 派生任务使用父任务 key 加点号（如 T31.1、T31.2），同样终身唯一。

#### 3.2 为什么不再复用

现在取消任务会释放 key，历史里因此出现两个 T17（一个取消、一个完成）。key 同时承担：

- 人读的标签；
- 依赖解析的依据；
- 历史讨论里的指代。

一旦复用，任何按 key 的引用都可能指错。不复用的代价只是编号变大，换来的是**所有引用永远确定**。

#### 3.3 编号规则写进提示词

分析作业的提示词里要给出：

- 当前已使用的最大编号；
- 已占用但已取消的 key；
- 规则：从最大号之后继续，禁止复用任何已出现过的 key。

这样规划者一开始就能用对编号，冲突不该成为常态。

### 4. 校验

落库前按顺序校验：

1. 至少一个任务，数量不超过上限；
2. key 非空、长度受限、**在项目内未被使用过**（包括已取消）；
3. title、description 非空；
4. acceptance 至少一条，**不允许为空**；
5. deps 只能引用本批次任务，且存在；
6. 无自依赖、无环。

任何一条不通过，方案不能确认。

#### 4.1 为什么拒绝空的验收标准

现在会默认填一句“实现任务描述中的要求，并通过项目已有测试”。这等于悄悄降低了验收强度：任务看起来有标准，实际无法判定。

没有验收标准的任务不应该被创建。规划者必须写清“怎么算完成”。

### 5. key 冲突：一次纠正，再冲突就换人

- 正常情况下按编号规则不该冲突；
- 真发生冲突，视为规划者的失误，**自动纠正一次**：把已占用的 key 列表发给它，要求改用未占用的编号；
- 纠正后仍冲突 → 阻塞，提示人工更换规划者。

这与 H8 处理内容协议错误的思路一致：一次纠正，仍不行就停下并建议换 Agent，而不是无限重试。

### 6. 任务由谁创建

#### 6.1 项目计划层面的任务：只有规划者

- 移除人工添加任务的入口；
- 需要新任务时，走项目重规划：说明原因 → 规划者出方案 → 确认 → 落成任务；
- 这样项目计划只有一个作者，方案、任务、验收标准始终同源。

#### 6.2 派生任务：执行者在自己的任务范围内

执行者可以在自己的任务里派生 1–25 个子任务（H7 的 derive）。这不违反“规划者是唯一作者”，因为：

- 派生子任务不改变项目计划，只是父任务内部的拆分；
- 子任务的依赖自动加入父任务的依赖，完成后成果先合回父任务分支；
- 子任务 key 用父 key 加点号，天然唯一；
- 父任务仍然负责整合并接受验收。

父任务在上级决策作业中给出的替代方案（H4）也属于任务内部拆分，规则相同：只影响自己的子任务，直接应用；需要项目级变更时，它应返回等待，由人决定是否重规划。

#### 6.3 人工添加任务移除后的连带影响

- 项目**完成后不能再加任务**。有新需求就开新项目；如果以后需要“重新打开”，那是另一个能力，不在 H3 定义。
- 里程碑属性不是创建路径：它可以设置在已有任务上，与谁创建任务无关。
- 人工不能再直接改任务描述或验收标准；要改就走重规划，由规划者改。

### 7. 方案与任务记录的关系

- 确认的方案作为契约版本冻结；
- 任务记录绑定到该契约版本；
- 任务描述与验收标准以契约为准，任务记录只承载状态、指导、反馈、次数等运行信息；
- 重规划产生新契约，旧任务按规则保留或取消，新任务进入新契约。

### 8. 场景推演

| 场景 | 处理 |
|---|---|
| 首次方案确认 | 按方案创建任务，key 从 T1 开始 |
| 重规划 | 保留已完成任务，取消未完成任务，新任务从最大编号之后继续 |
| 规划者复用了已取消的 key | 拒绝，自动纠正一次；仍冲突则阻塞并建议换规划者 |
| 任务没有验收标准 | 拒绝确认 |
| 依赖指向不存在的任务 | 拒绝确认 |
| 依赖成环 | 拒绝确认 |
| 用户想临时加一件事 | 走重规划，由规划者决定是否加 |
| 执行者发现任务太大 | 派生 1–25 个子任务，仍在父任务范围内 |
| 项目已完成，用户想加需求 | 开新项目 |

### 9. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| key 复用 | 取消后释放 / 终身唯一 | **终身唯一**，避免引用歧义 |
| key 冲突 | 静默重编号 / 拒绝并纠正 | **拒绝 + 一次纠正**，确认的就是创建的 |
| 空验收标准 | 填默认值 / 拒绝 | **拒绝**，默认值等于降低验收强度 |
| 谁创建任务 | 规划者 + 人工 / 只有规划者 | **只有规划者**；派生属于任务内部拆分 |
| 人工加任务 | 生成新契约 / 移除 | **移除**，避免契约与任务两份账 |
| 完成后加需求 | 重开项目 / 新项目 | **新项目**；重开能力另议 |

### 10. 决策依据

1. **引用必须确定**：key 被依赖、被讨论、被检索，复用会让所有引用产生歧义。
2. **确认的就是创建的**：静默重编号会让用户确认的方案与实际任务不一致。
3. **验收标准不能默认**：默认值制造“看起来有标准”的假象。
4. **计划只有一个作者**：方案、任务、验收标准同源，才不会出现执行者与验收者看两份东西。
5. **派生不是计划变更**：它发生在任务内部，边界由父任务承担。

### 11. 影响

- 移除人工添加任务的入口与相关接口；
- 分析提示词增加已用 key 列表与编号规则；
- 落库前增加“key 项目内唯一”与“验收标准非空”校验；
- 重规划保留已完成任务时，编号策略改为“从最大号继续”；
- H6 的契约切片因此始终能找到本任务（不会出现“人工任务不在契约里”）。

### 12. 风险

- 编号只增不减，长期项目 key 会变大（如 T120）；可读性略降，但不影响正确性。
- 移除人工加任务会降低“临时补一件事”的灵活性；由重规划承担，代价是多一次方案确认。
- 一次纠正依赖规划者理解反馈；弱模型可能再次犯错，因此纠正后仍失败要换人而不是继续重试。
- 派生任务与规划任务共用 key 空间，若父任务 key 含点号需保证解析一致。


## 二、执行与结果（H4、H6–H8）

### H4 执行者 → 上级决策

> 2026-11-07 定稿。本文定义执行者在任务中遇到障碍时，如何向上请求决策、谁来决定、决策如何落地。
> 上游：H6（执行上下文）、H7（结果契约）。下游：H3（任务变更）、H10（验收退回）。
> 不在范围：任务级验收退回（H10）、项目级重规划（H14 的 execute）。

### 1. 定位

执行者只有三种结果：完成、自己拆、请求上级。没有"失败"这种自评。

理由：质量是否达标由验收判断，不由执行者判断。执行者若认为本轮产出不达标，仍报完成并如实说明未覆盖部分，由验收退回；若做不下去，则请求上级。这样"失败"这个判断只存在于验收侧，不会出现执行者和验收者各有一套结论。

### 2. 三种出口

| 出口 | 什么时候用 | 谁处理 |
|---|---|---|
| done | 完成任务并自检 | 验收 |
| derive | 任务确实过大，能拆出独立边界 | 执行者自己（1–25 个子任务） |
| replan | 缺外部条件，或计划本身需要上级判断 | 父任务执行者 / 项目规划者 |

运行时失败（进程崩溃、超时、限流、没有结果文件）不属于这三种：它由系统观测，走调度重试，不是 Agent 的声明。

#### 2.1 什么时候用 replan

- 缺自己拿不到的输入、授权、环境；
- 发现事实前提与方案不符（接口不存在、数据不可得）；
- 范围、约束、验收方式需要上级判断；
- 计划不可行，继续做只会浪费。

不用于：任务过大（用 derive）、产出不达标（报完成，由验收判断）。

### 3. 请求内容与上级输入

执行者提交的请求只有两样：

- **原因**：为什么做不下去，已经核实了什么，缺什么，影响是什么；
- **任务标识**：key 与标题，让上级知道在说哪个任务。

上级决策时看到：

- 当前请求原因；
- 任务 key 与标题；
- **上一轮的请求原因、决策与指导**（如果有）。

不附：任务描述、验收标准、完整历史作业、来源作业结果、尝试次数。

理由：

- 上级就是任务的作者（父任务执行者或规划者），它安排了这个任务；
- 需要细节时可以看工作区，不需要预先嚼碎；
- 次数是聚合值，不带内容，无法判断该不该继续；
- 只注入上一轮，是因为不复用上下文时上级看不到自己上次说过什么，可能重复同类指导，也无法判断是否同一问题。一轮足够形成连续性，完整历史只是噪声。

### 4. 路由

- **子任务** → 父任务的执行者；
- **顶层任务** → 项目规划者。

不设"子任务跳过父任务"的例外：规划者可能不了解子任务的局部情况，先给父任务处理。

### 5. 决策

| 决策 | 含义 | 结果 |
|---|---|---|
| 继续 | 请求不成立或不需要改计划，给指导 | 任务恢复执行；可指定恢复到执行或补验收 |
| 等待 | 需要人提供条件或做决定 | 任务阻塞，给用户具体操作说明 |
| 替换方案 | 计划要改 | 用新方案替换未完成任务，已完成任务保留 |

#### 5.1 继续

必须给出可执行的指导，不能只说"再试一次"。指导进入任务，随下一次执行进入 prompt（H6）。

#### 5.2 等待

等待是**等人**，不是等时间：

- 缺什么（输入、授权、环境、决定）；
- 为什么挡住交付；
- 人处理完后从哪里继续。

只写"稍后重试"不属于等待。

#### 5.3 替换方案

返回完整方案（message、goal、constraints、assumptions、acceptance、tasks），不是补丁。

其中 goal 必须等于当前项目目标：决策作业不能修改目标，改目标走单独入口。任务数量与依赖规则按 H3。

### 6. 方案如何应用

| 谁审 | 影响范围 | 是否需确认 |
|---|---|---|
| 父任务执行者 | 只影响本任务内部（子任务拆分） | 直接应用 |
| 项目规划者 | 改变项目计划 | 按项目确认方式：自动模式直接生效，人工模式等待确认 |

父任务方案相当于一次受控的任务内拆分；项目方案会改变任务集合与验收口径，按 H1–H2 的确认规则走。

应用时保留已完成任务，取消未完成任务（含其子任务族），新任务按 H3 的编号规则创建。

### 7. 反复请求与升级

- 不设次数阈值；
- 由上级自己判断：如果同一个问题反复上报、继续已经无效，上级应该选择等待（交给人）或替换方案，而不是重复给同类指导；
- 父任务解决不了且需要项目级调整时，返回等待，请人决定是否发起项目重规划；不自动跳级。

代价是：如果上级判断失准，可能出现"继续 → 再请求"的循环。接受这个风险，靠上级的判断与人工观察兜底。

### 8. 系统重试（与业务无关）

决策作业的结果无效（格式错误、字段缺失）时，系统自动重试，最多 3 次；仍无效则停住，等待人工指导或重试。

这是系统对"结果不可用"的处理，不是业务次数，也不计入任务。

### 9. 结果结构

~~~json
{ "kind": "replan_review", "decision": "continue", "reason": "判断依据", "guidance": "继续执行的具体指导", "resume_stage": "executing" }

{ "kind": "replan_review", "decision": "wait", "reason": "判断依据", "guidance": "给后续 Agent 的要求",
  "user_action": { "summary": "缺什么或需要决定什么", "why": "为什么影响交付",
                   "owner": "谁来处理", "steps": ["具体操作"], "after": "处理完从哪里继续" } }

{ "kind": "plan", "message": "替代方案说明", "goal": "当前项目目标",
  "constraints": [], "assumptions": [], "acceptance": [], "tasks": [ … ] }
~~~

### 10. 场景推演

| 场景 | 处理 |
|---|---|
| 缺 GPU，无法验证 | replan → 父/规划者 → 等待（请人提供环境） |
| 接口与方案描述不符 | replan → 上级核实 → 继续（调整实现）或替换方案 |
| 任务确实过大 | derive，不请求上级 |
| 本轮实现不达标 | 报完成并说明未覆盖部分，由验收退回 |
| 同一问题第三次上报 | 上级识别为重复，选择等待（交人）或替换方案 |
| 父任务方案影响其他任务 | 不允许：父任务方案只能改动自己的子任务；需要项目级变更时返回等待 |
| 决策结果格式错误 | 系统重试 3 次，仍失败则等待人工 |

### 11. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| 是否有 failed | 保留（重试信号） / 删除 | **删除**：质量由验收判断，执行者不做自我判决 |
| 上级输入 | 完整上下文 / 原因 + 标识 + 上一轮处置 | **后者**；完整历史与次数均不注入 |
| 是否给次数 | 给 / 不给 | **不给**：复用上下文时已知；不复用时原因应说明 |
| 子任务路由 | 可直接给规划者 / 必须先给父任务 | **必须先给父任务**，规划者可能不了解局部 |
| 决策种类 | 继续 / 等待 / 替换方案 | **三种**；足够覆盖"不改 / 等人 / 改计划" |
| 升级 | 计数升级 / 上级判断 | **上级判断**，不设阈值 |
| 方案确认 | 一律确认 / 父直接、项目按设置 | **后者** |

### 12. 决策依据

1. **质量判断只在一个地方**：验收说行不行，执行者只说自己做了什么、缺什么。两套判断必然冲突。
2. **上级有工作区**：它不需要预嚼的上下文，需要的是"为什么卡住"和"卡在哪个任务"。
3. **层级先自己处理**：父任务最了解局部，规划者最了解全局；子任务先给父任务，避免越级。
4. **升级靠判断而非计数**：次数是间接指标，能否解决只有上级知道。
5. **方案的影响范围决定确认方式**：影响自己子任务的直接应用，影响项目计划的按项目设置确认。

### 13. 影响

- H7：删除 failed，执行结果只剩 done / replan / derive；
- H8：删除"业务失败"分支，失败分类只剩传输/协议/replan；
- H6：执行上下文不再有名称为"失败记录"的固定区块（已在 H6 按条件处理）；
- H10：验收退回仍由验收者判断，与执行者自评无关。

### 14. 风险

- 没有 failed，执行者可能把没做完的活报成 done，依赖验收拦截；验收标准必须足够具体。
- 不设次数阈值，可能出现反复"继续"；靠上级判断与人工观察。
- 子任务必须先给父任务，父任务若判断失误，会多绕一层。
- 上级输入精简后，若请求原因写得含糊，决策质量会下降；提示词要求写清事实、缺项与影响。


### H6 任务记录 → 执行作业上下文

> 2026-11-07 定稿。本文定义执行作业开工时，prompt 里应该有什么、按什么顺序、哪些按条件出现。
> 上游：H3（任务）、H7（结果契约）、H13（下游不看 summary）。
> 不在范围：其他角色的上下文差异（验收、规划、项目验收），只在需要时说明。

### 1. 现状与问题

实测最近一次执行作业的 prompt，共 17,315 字符：

| 区块 | 字符 | 占比 |
|---|---|---|
| 交付契约快照（完整方案 JSON） | 7,508 | 43% |
| 项目共享信息（完整 JSON） | 3,254 | 19% |
| 固定规则 | ~5,400 | 31% |
| 任务描述 + 验收标准 + 指导 + 反馈 + 前置任务 | ~1,180 | 7% |

三个问题：

1. **契约是整份方案**：包含其他 6 个任务的完整描述与验收、方案摘要、重规划影响。本任务的标题、描述、验收标准在里面又出现一次。
2. **共享信息还是旧格式**：topic / body / scope / evidence / supersedes / conflicts 的完整 JSON，外加索引和读取说明；而 H7 已把它简化为 ≤5 条 ×120 字的项目记忆。
3. **规则与 H7 冲突**：仍写着“DOMO 负责暂存、提交和合并”“不执行 git add / commit”，而 H7 已改为 Agent 自己提交。

### 2. 目标结构

顺序按“稳定 → 项目 → 本次 → 结果”：

~~~text
1. 角色与权限（稳定：只读边界、运行权限、长命令）
2. 项目目标 / 项目级验收标准 / 约束 / 关键假设（同一项目内稳定）
3. 本次任务（key、标题、描述、验收标准）
4. 上轮反馈与指导（仅驳回后）
5. 项目记忆（有内容时）
6. 可参考的成果入口（有内容时）
7. 工作区与资源目录
8. 结果协议（稳定，紧邻写结果）
~~~

理由：稳定内容在前，有利于 Agent 侧的前缀缓存；任务与反馈靠后，紧邻结果协议，注意力仍在；完整契约 JSON 不再进 prompt，只写 context.json 供审计。

### 3. 契约切片

#### 3.1 切什么

只取四个部分：

| 字段 | 实测大小 | 说明 |
|---|---|---|
| 项目目标 | 168 | 原样 |
| 项目级验收标准 | 770（7 条） | 原样，逐条列出 |
| 约束 | 数条短句 | 原样，逐条列出；用户明确要求、不能违反的限制 |
| 关键假设 | 717（7 条） | 原样，逐条列出 |
| 本任务（key、标题、描述、验收、deps） | ~600 | 只取当前这一条 |

合计约 2.3–2.5k，替换掉 7.5k 的完整快照。

不取：其他任务、方案摘要、重规划影响、空的 verification。

#### 3.2 谁切

**DOMO 机械选字段**。契约是结构化数据，切片不需要理解语义，因此不需要额外作业，也不需要规划者改方案格式。

#### 3.3 任务信息以契约为准

作业绑定的是某个契约版本，验收也按该版本核对。因此任务的描述与验收标准从契约冻结版取；任务记录只提供状态、指导、反馈。避免“按新描述做、按旧标准验”。

#### 3.4 为什么要传项目级验收标准

它不是给验收者看的，而是**跨任务的硬约束**，单个任务的验收标准覆盖不到。两个真实例子：

- 项目级标准「全部阶段报告及图像在独立被忽略目录生成」。T31 的执行者不知道，把 var/render-world/.../report.json 登记为成果，撞上“成果必须被 Git 跟踪”，整轮作废。知道这条就会明白：报告是运行产物，不是交付物。
- 项目级标准「相同正式输入三次回放的核心状态与事件哈希一致」。一个渲染任务自己的验收只要求画面正确；若实现引入随机或时间依赖，任务能过，项目级标准却已不可能满足。

所以项目级标准必须在动手前给到执行者。

### 4. 规则分层

#### 4.1 三类规则

| 类型 | 例子 | 处理 |
|---|---|---|
| 角色常量 | 只读边界、运行权限、长命令、结果协议 | 固定，去重 |
| 项目常量 | 目标、项目级标准、假设 | 每个作业相同 |
| 本次条件 | 派生规则、冲突规则、反馈、前置任务、项目记忆、成果 | 不成立就整节省略 |

#### 4.2 条件注入清单

- **派生规则**：只有可派生的顶层任务给；派生出的子任务只给一句“禁止再派生”；
- **合并冲突规则**：只有任务处于冲突状态才给，不是每个 Git 任务都给；
- **上轮反馈**：只有验收驳回后才有；是完整清单（H10）；
- **前置任务**：无前置任务时整节省略；
- **项目记忆**：为空时省略；
- **成果入口**：为空时省略；
- **结果协议**：只列该角色允许的 kind。

#### 4.3 执行失败记录

执行失败分两种，处理不同：

| 类型 | 例子 | 是否给执行者 |
|---|---|---|
| 验收驳回 | issues + 指导 | **必给**，完整清单 |
| 执行失败 | 限流、超时、崩溃、中断 | 默认不给 |

执行失败只在一种情况下给一句提示：**与作业起点相比，工作区有未提交改动或分支有新提交**，说明上次被中断、可能留有半成品，要求先检查现场。

失败分类（rate_limit / transient / permanent）不进入 prompt：它影响调度，不改变任务。

#### 4.4 去重

现在三处都在讲“字段是给谁看的”：输入来源与适用范围、输出内容与消费边界、结果协议里的说明。合并为一段“字段与读者的对应关系”，放在结果协议之前，只讲一次。

持续工作资源中关于共享记录写入的长段说明，按 H7 的新格式（{text, supersedes} 对象数组、≤5 条 ×120 字）重写并缩短。

### 5. 项目记忆与成果入口

#### 5.1 项目记忆

- 全项目可见，不按依赖过滤（H8）；
- 注入格式：每条一行 `- [M17][T31] 正文`，不展开 JSON；已失效编号不注入；
- 总量 ≤5k 字符时全量注入；超过则只给索引（索引条目同样带编号），正文按固定版本读取；
- 末尾一句说明：这是项目记忆，不是本任务要求。

#### 5.2 成果入口

- 每个任务最多 4 条，任务完成后才发布（H7/H11），因此总量天然受控；
- 每条只给：路径 + 一句说明 + 来源任务；不列 kind、format、版本等字段；
- 空则整节省略。

#### 5.3 前置任务

H13 已定：不注入前置任务的 summary。没有前置任务时整节省略；有前置任务时只列 key 与标题，说明其成果已在当前分支中，具体内容直接看工作区。

### 6. 预期效果

- 总长度从约 17k 降到约 8–9k；
- 任务相关内容的占比从 7% 升到 20% 以上；
- 项目级标准与假设仍然完整，跨任务约束不丢失；
- 稳定前缀变长，有利于缓存。

### 7. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| 契约怎么给 | 完整 JSON / 切片 / 只给目标与任务 | **切片**：目标 + 项目级标准 + 假设 + 本任务 |
| 谁来切 | 规划者预先写精简版 / DOMO 选字段 | **DOMO 选字段**，不加新字段、不加作业 |
| 项目级标准是否压缩 | 压成短约束清单 / 原样 | **原样**。实测仅 770 字，压缩不划算 |
| 任务信息以谁为准 | 任务记录 / 契约冻结版 | **契约**，避免描述与验收漂移 |
| 顺序 | 任务最前 / 稳定在前 | **稳定在前**，兼顾缓存 |
| 失败记录 | 固定区块 / 按现场决定 | **按现场**，无半成品痕迹就不给 |

### 8. 决策依据

1. **注意力应该落在任务上**：现在 93% 的内容与本次任务无关，属于结构性浪费。
2. **项目级标准是跨任务约束**：不传会重复出现 T31 那类“局部正确、整体违规”的失败。
3. **切片不需要智能**：字段是结构化的，机械选取即可，不需要额外 Agent 或新字段。
4. **稳定在前**：既符合阅读顺序，也有利于模型侧缓存。
5. **不把调度信息混进任务上下文**：限流、超时属于调度，写进 prompt 只会误导。

### 9. 影响

- 结果协议与提交规则需要按 H7 重写（Agent 自己提交、无 commit_files、artifacts ≤4、shared_updates 为 {text, conflict} 对象数组）；
- 共享信息格式按 H7/H8 改写；
- 成果导航按 H7/H11 改写（≤4、完成后发布、无类型）；
- 这些不是 H6 的独立改动，而是 H7/H8/H13 落到提示词层的必然结果。

### 10. 风险

- 切片后执行者看不到其他任务的描述，可能与其他任务产生理解冲突。缓解：项目级标准与假设仍在，项目记忆可查，工作区是事实来源。
- 项目级标准是长段落，执行者可能只扫一眼。缓解：放在靠前位置并逐条编号。
- 条件注入让不同作业的 prompt 结构不一致，排查问题时需要看 prompt.md 才能知道当时给了什么。缓解：prompt.md 与 context.json 落盘保留。
- 执行失败不给记录，可能让执行者重复踩同样的环境问题。缓解：只有当现场无变化时才省略，有变化时仍会提示。


### H7 Agent → result.json

> 2026-11-07 讨论定稿。本文只定义 H7 的内容契约，不涉及实现改造。
> 范围：执行作业（executor）的 `result.json` 内容，以及它与提交、验收、下游消费的边界。
> 前提：文件存在、可解析、是合法 JSON 对象。
> 不在本文范围：文件缺失、写错位置、编码损坏、Markdown 围栏、非 JSON。这些属于 Agent 适配层的执行恢复，不进入任务/作业交接。

### 1. 为什么单独定义 H7

`result.json` 是 Agent 向 DOMO 交付的唯一通道：

- 作业启动时 DOMO 删除旧文件（`server/src/runner/mod.rs:139-141`）
- 提示词要求写入绝对路径，stdout 只作审计（`server/src/prompts.rs:343-365`）
- 结算时只读该文件（`server/src/runner/mod.rs:651`）

T31 的案例说明：技术工作已经完成（68 分钟、28 个检查点、exit 0），但结果里的 `artifacts` 登记了被 Git 忽略的 `var/` 报告，整轮被判协议失败并阻塞。问题不在“会不会写 JSON”，而在“结果里应该表达什么”。

### 2. 最终定稿

#### 2.1 Git 工作区：done

```json
{
  "schema_version": 1,
  "kind": "done",
  "summary": "交付内容、实际验证、未覆盖范围与后续工作",
  "delivery": {
    "commits": {
      "base": "<作业启动时的 HEAD>",
      "head": "<本轮结束时的 HEAD>",
      "commits": ["<sha1>", "<sha2>"]
    }
  },
  "artifacts": [
    {
      "path": "docs/render-contract.md",
      "format": "text/markdown",
      "verification": "阅读 3.7 节核对覆盖事实与未知项"
    }
  ],
  "shared_updates": [
    "真实切片的帧矩阵在对象内不变，逐帧覆盖只能算合成"
  ]
}
```

#### 2.2 Git 工作区：derive

```json
{
  "schema_version": 1,
  "kind": "derive",
  "summary": "为什么不由当前执行者继续、交接了什么、父任务剩余整合责任",
  "delivery": {
    "commits": { "base": "<作业启动时的 HEAD>", "head": "<当前 HEAD>" }
  },
  "tasks": [
    {
      "key": "T31.1",
      "title": "子任务标题",
      "description": "目标、边界与交接内容",
      "acceptance": ["可独立核验的标准"],
      "deps": []
    }
  ],
  "shared_updates": []
}
```

派生规则沿用现有实现：仅顶层任务可派生；单次 1–25 个；key 在活动任务中唯一；`deps` 只能引用本批次；禁止自依赖、缺失依赖和环；父任务的 `deps` 自动加入子任务 key；父任务回到 `pending`，全部子任务完成后恢复并整合。

派生时工作区必须干净：有未提交改动则拒绝，执行者先提交再重新提交 derive。理由：子任务从父任务分支创建，未提交改动不可见；脏工作区也可能在清理或恢复时丢失。

#### 2.3 Git 工作区：failed / replan

```json
{ "schema_version": 1, "kind": "failed", "reason": "失败原因、已完成工作、再次尝试依据" }
{ "schema_version": 1, "kind": "replan", "reason": "需上级处理的输入、环境、授权或方案问题" }
```

不要求 `delivery`，也不要求 `shared_updates`。分支上做到哪算哪，DOMO 通过分支 HEAD 查看现场。

#### 2.4 普通工作区：done / derive / failed / replan

```json
{
  "schema_version": 1,
  "kind": "done",
  "summary": "交付内容、实际验证、未覆盖范围",
  "artifacts": [],
  "shared_updates": []
}
```

没有 `delivery`，没有 `changes`，没有新增/修改/删除列表。普通工作区是持续演进的现场，不做变更追踪；验收按当前目录全量核对，删除是隐式的。

#### 2.5 字段说明

| 字段 | 类型 | 必填 | 说明 | 校验 |
|---|---|---|---|---|
| `schema_version` | integer | 是 | 结果契约版本，当前为 1 | 必须为已知版本；未知版本拒绝 |
| `kind` | string | 是 | `done` / `failed` / `replan` / `derive` | 必须属于该角色允许的 kind |
| `summary` | string | 是（done/derive） | 面向人和下游的交付说明：交付了什么、怎么验证、未覆盖什么 | 非空；不建议超过 2000 字 |
| `delivery` | object | Git 的 done/derive 必填 | 本轮交付的提交区间 | 见 2.6 |
| `delivery.commits` | object | 是 | 提交区间 | 只在 Git 工作区出现；普通工作区必须缺省 |
| `delivery.commits.base` | string | 是 | 作业启动时的分支 HEAD，由 DOMO 注入 `context.json` | 必须是 `head` 的祖先；必须等于 `job_start_head` |
| `delivery.commits.head` | string | 是 | 本轮结束时的分支 HEAD | 必须等于结算时 `git rev-parse HEAD`；必须在任务分支上 |
| `delivery.commits.commits` | string[] | 否 | 本轮新增的提交列表，供审计/UI 使用 | 可省略；`base..head` 已足够表达交付 |
| `artifacts` | array | 否 | 任务级成果入口，最多 4 条 | 见 2.7 |
| `artifacts[].path` | string | 是 | 工作区相对路径，文件或目录 | 路径安全、存在；Git 必须可达；目录下不得再登记子项 |
| `artifacts[].format` | string | 否 | MIME 或简短格式说明 | 自由文本 |
| `artifacts[].verification` | string | 否 | 一句检查方式说明 | 自由文本，不当作验收结论 |
| `shared_updates` | string[] | 否 | 项目记忆候选，最多 5 条，每条 ≤120 字 | 非空、去重；不发布，验收后入库 |
| `tasks` | array | derive 必填 | 派生子任务 | 1–25 个；规则见 2.2 |
| `reason` | string | failed/replan 必填 | 失败或请求原因 | 非空 |

#### 2.6 Git 交付校验

结算时按顺序校验：

1. `schema_version` 已知，`kind` 属于 executor 允许集合。
2. `summary` 非空（done/derive）。
3. `delivery.commits.head` 等于任务分支当前 HEAD。
4. `delivery.commits.base` 等于作业启动时注入的 `job_start_head`。
5. `base` 是 `head` 的祖先。
6. 本轮 HEAD 必须仍是上一轮 HEAD 的后代（append-only）；不满足说明发生了 amend/rebase/reset，拒绝。
7. 当前分支必须是任务分支（`domo-task/<project>/<seq>-<key>`）。
8. `base..head` 的 diff 不得包含被忽略路径、`.git`、越界路径；出现则拒绝或标记。
9. 提交作者/邮箱必须等于注入的运行时身份（见 2.8）。
10. `artifacts` 不超过 4 条并按优先级排序；只允许本任务产出的入口，不接受参考输入；路径安全且存在；Git 项目必须已跟踪或在 `base..head` 的 diff 中；已登记目录下不得再登记子项；路径去重。
11. `shared_updates` 不超过 5 条、每条不超过 120 字、去重。
12. derive 的 `tasks` 按现有规则校验；工作区必须干净。

失败处理：

- 校验失败按协议错误处理，任务不进入验收；已产生的提交保留在任务分支。
- 重试时 `base` 取新的 `job_start_head`（即上一轮 HEAD），继续追加提交。
- 不允许回滚已提交内容来“重来”；修正用新提交。

#### 2.7 artifacts：任务级成果入口

定位：**人类可读的成果入口书签**，不是知识库，不是文件清单，不参与验收。

- 最多 4 条，按优先级排序，第一条是主入口；目录优先，单文件只在确实需要独立引用时登记。
- 只有一种成果类型：本任务产出的入口。参考输入不是成果，放契约、资源目录或共享记录。
- 父任务对子任务成果的规则统一：保留，或显式退役（重命名/合并/移除 + 理由）。
- 登记目录后，禁止再登记其子项。T17 曾逐条登记 102 个缓存对象，导致索引退化为文件清单，这是反例。
- 同一路径去重。
- 执行结果里的 `artifacts` 只是**候选入口**：结算时不发布，任务验收通过并合入后才进入项目成果面板。草稿不展示。发布时机与状态属于 H11。
- 不参与提交、不决定提交范围、不参与任务验收或项目验收。
- 知识、结论、接口约定写入 `shared_updates`，不要塞进 artifacts。

#### 2.8 提交模型

- **Agent 自己提交**。DOMO 不再暂存和提交任务成果；DOMO 只校验、记录、合入。
- 任务分支 **append-only**：禁止 amend/rebase/reset；修正用新提交（fix/revert）。
- 允许一次作业产生一串提交；`base..head` 表达本轮范围，不要求逐提交枚举。
- 提交身份固定为：

  ```
  DOMO <domo+<runtime-short-sha>@<hostname>>
  ```

  `runtime-short-sha` 取 `version::git_hash()`；`hostname` 小写并把非法字符替换为 `-`，为空时用 `localhost`。
  通过 `GIT_AUTHOR_*` / `GIT_COMMITTER_*` 环境变量注入所有 Agent 进程；同时设置 `commit.gpgsign=false`。
- 作业/Agent 信息写入 commit message trailer，而不是作者：

  ```
  Domo-Job: job_xxx
  Domo-Task: T31
  Domo-Agent: <agent name>
  Domo-Runtime: <short sha>
  ```

- 合入仍是 squash merge。squash 后 `verified_commit` 通过现有 `refs/domo-archive/heads/...` 保持可达，归档策略保持现状（不在项目归档时删除）。DB 记录 `verified_commit → merge_commit` 映射；artifacts 记录 `verified_commit`，下游读项目分支，审计看 verified。

#### 2.9 普通工作区

- 没有 `delivery`，没有提交，没有变更列表。
- 验收按当前目录全量核对；删除是隐式的。
- `artifacts` 可选，最多 4 条，仍是任务级入口书签。
- 没有版本回溯；预览只读当前文件。

#### 2.10 shared_updates：项目记忆候选

定位：**项目记忆的候选**，不是文档，不是任务报告，也不是定向投递给某个下游任务。

- 字符串数组，最多 5 条，每条 ≤120 字。
- 不需要 topic、scope、evidence、source、状态等字段。
- 自动关联产生它的 task / job / commit，作为来源。
- 执行者只回答三个问题：本轮验证过吗？从代码/提交/文档看不出来吗？别人重新发现要花明显成本吗？三条都成立才写。
- 执行者不需要知道下游是谁；系统按项目记忆处理，不按 DAG 过滤。
- 数据来源：执行作业；验收者不提交 shared_updates，只审查和拒绝。
- 可见性：验收通过后进入项目共享记录，全项目可见；注入时超过 5k 字改为索引 + 按需读取；当前作业的候选记录始终单独注入验收者。
- 发布时机：任务完成（合入成功、里程碑人工验收通过）后；H8 只校验不发布。

### 3. 考虑过的方案与取舍

#### 3.1 谁负责提交

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A | Agent 自己 commit，结果写 commit 区间 | 提交就是事务；大变更集无需逐文件枚举；系统协议最简 | 需要 Git 写权限；需约束历史、身份、diff 范围；Agent 可能提交垃圾 | **采用** |
| B | DOMO 按选择/排除清单提交 | 权限可控；先校验后提交 | 需要选择语言、双重记账；Agent 与 DOMO 对“提交什么”各有一半决定权 | 未采用 |
| C | 两阶段：Agent 写意图，DOMO 提交后生成交付记录 | 职责清晰 | 多一个系统产物和状态机 | 未采用 |

选择 A 的依据：产品假设是“Agent 具备胜任职责的智能，系统提供必要信息与协作条件”，而不是用流程替代判断。B 的“选择语言”本质上是用系统规则补 Agent 的判断，复杂度更高。A 把复杂度移到**可机械校验的不变量**（分支、HEAD、祖先、身份、diff 范围），而不是业务选择。

#### 3.2 结果通道

| 方案 | 结论 |
|---|---|
| 只认 `result.json` | **采用**。stdout 只作审计，避免从日志里猜结果 |
| 文件缺失时从最后消息提取 | 未采用。缺失/不可解析属于适配层恢复，不属于 H7 |

#### 3.3 schema 组织

| 方案 | 结论 |
|---|---|
| 每个角色独立 schema | **采用**。executor / verifier / acceptance / analysis / summary / merge 各自演进 |
| 统一 superset | 未采用。字段互相污染，解析器难以收紧 |

H7 只定义 executor 的 schema。

#### 3.4 交付身份

| 方案 | 结论 |
|---|---|
| 单个交付 SHA | 未采用。重试、squash、rebase 都会让 SHA 变化 |
| 任务分支 | **采用为稳定身份**。整个任务生命周期不变 |
| 提交区间 `base..head` | **采用为本轮身份**。重试自然追加，不需要保持任何 SHA 不变 |
| 逐文件 `commit_files` | **删除**。与 commit 重复，且大变更集不可用 |

#### 3.5 squash 后的 provenance

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 直接用 `merge_commit` | 简单 | 不能代表验收时的状态；项目分支可能已包含其他任务 | 不采用 |
| 保留任务分支 | 可复现 | 分支列表增长 | 不采用 |
| 隐藏 ref `refs/domo-verified/...` | 精确、轻量 | 需要新机制 | 不需要：现有 `refs/domo-archive/heads/...` 已实现 |
| squash + archive ref + 映射 | 保持线性历史，verified 可达 | 需要记录映射 | **采用** |

现有实现已经把合并后的任务分支移到 `refs/domo-archive/heads/<branch>`（`git.rs:213-241`、`artifacts.rs:143-152`），所以不需要新增隐藏 ref，也不需要改变归档策略。

#### 3.6 工作区差异

| 方案 | 结论 |
|---|---|
| 同一字段 + `mode` 标签 | 未采用 |
| Git 用 `delivery.commits`，普通工作区无 `delivery` | **采用**。两种工作区的交付机制本来就不同，不应伪装成同一字段 |
| 普通工作区也逐文件声明 | 未采用。没有基线，变更无法定义；全量验收即可 |

#### 3.7 删除表达

| 方案 | 结论 |
|---|---|
| 显式 add/modify/delete | 普通工作区也不需要；Git 的 commit diff 天然包含 A/M/D |
| Git 用 commit diff，普通工作区隐式 | **采用** |

#### 3.8 artifacts 的定位

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 项目知识库 | 统一入口 | 与 shared records 重叠；文件不是知识 | 不采用 |
| 全量文件清单 | 完整 | 退化为 inventory；prompt/UI 噪声 | 不采用 |
| 任务级成果书签，≤4 条 | 可读、可导航、可验收后发布 | 需要限制和策展 | **采用** |
| 按 delivery / intermediate / input 分类 | 可区分最终、中间、输入 | 实际未用起来；增加判断负担 | 未采用 |
| 删除 artifacts | 协议最简 | 失去人类入口 | 未采用 |

发布时机：**任务完成后**，不展示草稿。具体发布与映射属于 H11。

#### 3.9 shared_updates 的定位与可见性

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 共享知识库（带 topic/scope/evidence/状态） | 结构化 | 概念多；执行者要猜 scope；验收者要逐条裁决 | 未采用 |
| 项目记忆候选，≤5×120 字，无 scope | 简单；执行者只判断“是否非显然且值得记住” | 可能产生少量无关记录 | **采用** |
| 按 DAG 上下游过滤 | 相关性强 | 执行者不知道下游；跨领域复用会漏 | 未采用 |
| 全项目可见，≤5k 全量注入 | 不依赖 DAG；实现简单 | 项目大时 prompt 增长 | **采用**，超过 5k 改索引 + 按需读取 |

#### 3.10 其他决策

| 问题 | 选项 | 结论 |
|---|---|---|
| derive 时工作区脏 | 拒绝 / DOMO 自动提交 | **拒绝**。既然 Agent 自己提交，DOMO 自动提交会绕过约定并带入垃圾 |
| `head == base` 的 done | 允许 / 拒绝 | **允许**，但 `summary` 必须说明为什么没有提交 |
| `summary` 拆分 | 一份 / 人读+下游两份 | **一份**。下游结构化交接留给 H13 |
| no-op 任务 | 允许 / 视为异常 | 允许；验收仍全量检查 |

### 4. 决策依据

1. **信任 Agent 的判断，系统只保留可机械校验的不变量**：分支、HEAD、祖先关系、提交身份、diff 范围。这些不需要理解业务，却足以防止“交付错版本/丢历史/提交越界”。
2. **提交是最自然的事务单位**：一个 commit 已经包含新增、修改、删除、重命名；再要求逐文件清单是重复表达，且在大变更集下不可维护。
3. **结果协议要能承受重试**：任务经常多次执行（T17 5 次、T30 4 次）。用“分支 + 区间”而不是“唯一 SHA”，重试就是追加，不需要改写历史。
4. **验收要能复现**：squash 会改变 SHA，但 archive ref 保留验收时的状态；映射表区分“验了什么”和“落到哪”。
5. **artifacts 必须被限制**：不限制就会从“入口”退化为“清单”。119 条、102 个缓存对象的实际数据就是证据；4 条上限迫使执行者做取舍。
6. **普通工作区不假装有历史**：没有基线就不定义变更；全量验收是唯一诚实的做法。
7. **共享记录是项目记忆，不是定向交接**：执行者不需要知道下游；只判断事实是否非显然、是否值得别人避免重复发现。系统负责可见性。
8. **成果不需要类型**：每个任务最多 4 个入口，顺序表达优先级；参考输入不属于成果。类型没有带来实际区分，只增加了判断负担。

### 5. 移交 H8 / H11 的事项

H8 已定稿（见本文 H8 章节）。H11 讨论见本文 H11 章节（当时讨论中），以下事项移交 H11：

- artifacts 候选和共享记录候选在任务完成时的发布顺序、幂等与失败处理。
- `verified_commit → merge_commit` 映射的存储位置与写入时机。
- 里程碑任务人工验收通过后的发布。
- 合入失败/冲突时，候选记录的保留与再次验收。
- `context.json` 注入 `job_start_head` 与任务分支名（H8 实现前提）。
- 旧结果（`commit_files` 版本）的兼容与迁移策略。

### 6. 风险

- Agent 提交垃圾/密钥：需要 diff 范围检查、忽略路径检查；必要时增加提交前扫描。
- Agent 改写历史：靠 append-only 校验拦截；被改写的旧结果无法恢复。
- Agent 不支持 Git 提交：适配层需要显式失败，而不是静默退回旧协议。
- 普通工作区没有结构化交付：下游只能依赖 `summary` 和共享记录，必须在提示词里说清。
- archive ref 长期增长：当前策略保留；如后续需要清理，必须先 bundle 再删 ref。
- 共享记录全项目可见：项目大时 prompt 增长；用 5k 阈值和索引兜底。


### H8 result.json → 结算

> 2026-11-07 讨论定稿。承接 H7；本文只定义结算，不涉及验收、合入与下游消费。
> 范围：一个合法的执行结果如何变成任务状态和作业状态。
> 前提：H7 的结果文件存在、可解析、内容校验见本文 P1。
> 不在本文范围：文件缺失/不可解析（Agent 适配层）；验收（H9/H10）；合入（H11）；下游消费（H13）。

### 1. 目标与原则

H8 只做两件事：**校验**和**状态流转**。

- 不提交。提交由 Agent 在写结果之前完成，是既成事实。
- 不发布 artifacts。artifacts 候选留在执行结果里，任务完成后由 H11 发布。
- 不发布共享记录。`shared_updates` 是候选，验收通过、任务完成后由 H11 入库。
- 只有一个 DB 事务。没有跨 Git/DB 的原子性要求。
- 结算必须幂等、可恢复。

### 2. 最终定稿

#### 2.1 结算流水线

| 阶段 | 动作 | 写入 | 失败处理 |
|---|---|---|---|
| P0 前置 | 作业仍 `running`；任务存在；项目未归档/暂停；读取 `context.json` 的 `job_start_head` 和任务分支名 | 无 | 作业取消/归档，直接退出 |
| P1 校验 | 按 H7 校验 schema、delivery、工作区干净、artifacts、shared_updates、derive 规则 | 无 | 协议错误，进入 P2 |
| P2 失败分类 | 区分传输错误、内容协议错误、业务 failed/replan | 无 | 见 2.4 |
| P3 事务 | 任务转 `verifying`，作业转 `succeeded`，写 `task_executed` 事件 | 一个 DB 事务 | 回滚，作业失败，可恢复重跑 |
| P4 通知 | 唤醒调度器派发验收作业 | 总线通知 | 不影响已提交状态 |

#### 2.2 P1 校验顺序

1. `schema_version` 已知，`kind` 属于 executor 允许集合。
2. `summary` 非空（done/derive）。
3. Git 的 `delivery.commits.head` 等于当前 HEAD。
4. `delivery.commits.base` 等于注入的 `job_start_head`。
5. `base` 是 `head` 的祖先。
6. HEAD 仍是上一轮 HEAD 的后代（append-only）；否则说明发生 amend/rebase/reset，拒绝。
7. 当前分支是任务分支。
8. `base..head` 的 diff 不含被忽略路径、`.git`、越界路径。
9. 提交作者/邮箱等于注入的运行时身份。
10. 工作区干净（done/derive）；`failed` / `replan` 允许脏。
11. `artifacts` ≤4；路径安全、存在、Git 可达；目录下无子项；去重。
12. `shared_updates` ≤5 条、每条 ≤120 字、去重。
13. derive 的 `tasks` 规则与工作区干净。

全部只读；失败不产生任何写入。

#### 2.3 P3 DB 事务

只在 P1 全部通过后进入：

```sql
BEGIN IMMEDIATE;

UPDATE tasks
   SET stage = 'verifying',
       status = 'queued',
       result_summary = ?,
       last_error = NULL,
       waiting_reason = NULL,
       updated_at = ?
 WHERE id = ? AND status = 'running';

UPDATE jobs
   SET status = 'succeeded',
       result = ?,
       finished_at = ?,
       input_tokens = ?,
       output_tokens = ?,
       cache_read_tokens = ?,
       cache_write_tokens = ?,
       reasoning_tokens = ?,
       cost = ?,
       usage_known = ?
 WHERE id = ? AND status = 'running';

INSERT INTO events(project_id, task_id, job_id, kind, message, payload, created_at)
VALUES (?, ?, ?, 'task_executed', ?, ?, ?);

COMMIT;
```

规则：

- 任务和作业必须同时成功；任何一个更新 0 行（并发或状态已变）就回滚并重新加载状态。
- 不写 `artifacts` 表，不写 `shared_records`，不调用 `git commit`。
- 事件写在事务内；总线通知在提交后发送。
- `result_summary` 取 `summary`，供验收者/下游读取（验收 prompt 接入属于 H9）。

#### 2.4 P2 失败分类

| 类型 | 判据 | 处理 |
|---|---|---|
| 传输/供应商 | 429、限流、超时、进程异常退出 | rate_limit / transient / permanent；换 Agent、冷却、重试；已有提交不回滚 |
| 内容协议 | H7/H8 校验失败，文件存在且可解析 | 原会话纠正一次；仍失败则阻塞，建议换 Agent |
| 业务失败 | `kind=failed` | 走现有失败策略，任务重试或阻塞；提交保留 |
| 重规划 | `kind=replan` | 提交重规划请求，作业结束；任务不进入验收 |
| 适配层 | 没有 result.json、无法解析、写错位置 | 不属于 H8；由 Agent 适配层恢复或报结构化失败 |

**内容协议错误只纠正一次**：

- 把具体错误（字段、期望、实际、文件路径）追加给同一会话。
- 只允许修 `result.json` 和工作区（清理或补提交），不重做任务。
- 仍不通过 → 任务 `blocked`，`last_error` 写明“建议更换 Agent”；由人工裁决决定是否 `switch_agent`。
- 不与超时/中断续写共用预算。

#### 2.5 工作区干净

- `done` / `derive`：`git status --porcelain` 必须为空；被忽略文件不算。
- `failed` / `replan`：允许脏，保留失败现场。
- 提示词必须说明：测试数据、截图、缓存放作业目录或被忽略的 `var/`；交付文件提交；其余删除。
- 脏工作区 → 内容协议错误，走一次纠正。

#### 2.6 共享候选记录

- `shared_updates` 是**项目记忆候选**，字符串数组，≤5 条，每条 ≤120 字，去重。
- H8 只校验格式，**不写 `shared_records`，不写共享 Git 仓库**。
- 候选随 `jobs.result` 持久化；验收作业通过 `execution_job_id` 读取，注入 prompt（接入属于 H9）。
- 验收者按任务整体验收：内容错误、或缺少下游必需的信息 → 在 `issues` 中拒绝；没有单独的 `shared_review` 字段。
- 验收者不提交 `shared_updates`；其发现写入 verdict 的 `reason` / `issues` / `guidance`。
- 任务完成后由 H11 入库；入库时自动带 task / job / verified commit。
- 可见范围：项目记忆，全项目可见；注入 ≤5k 字全量，超过则索引 + 按需读取；当前候选始终单独注入验收者。

#### 2.7 artifacts

- `artifacts` ≤4；规则见 H7。
- H8 只校验，**不写 `artifacts` 表**；候选随 `jobs.result` 持久化。
- 任务完成后由 H11 发布；验收拒绝时保留在结果里，下一轮覆盖。
- 草稿不进入项目成果面板。

#### 2.8 三个分支

- **done**：上面的 P0–P4。
- **derive**：P3 事务额外创建子任务、更新父任务 deps、父任务回到 `pending`；工作区必须干净；不发布 artifacts/shared。
- **failed / replan**：不进入 `verifying`；更新任务失败/重规划状态；分支提交保留；不发布。

#### 2.9 崩溃恢复与幂等

- 服务重启时，`recover` 发现 `running` 作业：
  - 结果有效 → `resume=2`，不调用 Agent，重跑 P1–P3。
  - 结果无效 → 走协议/失败路径。
- 幂等保证：
  - 任务已是 `verifying` → 不重复更新。
  - 作业已是 `succeeded` → 不重复结算。
  - 重复执行 P1–P3 不产生额外副作用。
- 提交是外部既成事实；DB 事务失败时任务保持原状态，重试重新结算。

### 3. 考虑过的方案与取舍

#### 3.1 结算时发布 vs 任务完成时发布

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| H8 发布 artifacts/共享记录 | 一步到位 | 验收拒绝要撤回；共享记录提前进知识库；跨 Git/DB 事务复杂 | 未采用 |
| H8 只校验，H11 完成时发布 | 单一 DB 事务；草稿不入库；失败可重试 | 完成时发布逻辑更集中 | **采用** |

#### 3.2 候选记录存哪里

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 新建 pending 表 + 状态字段 | 查询方便 | 引入 proposed/accepted 状态机；草稿入库 | 未采用 |
| 留在 `jobs.result` | 不变、可审计；无新状态 | 验收者需要按 `execution_job_id` 读取 | **采用** |

#### 3.3 验收者逐条 review vs 任务整体验收

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| `shared_review` 数组 + 四条判据 | 结构化 | 复杂；用系统规则替代验收判断；偏离信任前提 | 未采用 |
| 作为任务交付的一部分，错误/缺失就拒绝 | 简单；复用现有 issues | 无逐条记录 | **采用** |

#### 3.4 共享记录可见性

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 按 DAG 上下游过滤 | 相关性强 | 执行者不知道下游；跨领域复用会漏 | 未采用 |
| 全项目可见，≤5k 全量注入 | 简单；不依赖 DAG | 项目大时 prompt 增长 | **采用** |
| 全项目可见 + 索引按需 | 可扩展 | 多一步读取 | 超过 5k 时采用 |

#### 3.5 协议纠正次数

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 沿用 5 轮 | 给弱 Agent 更多机会 | 同一错误重复烧时间；延迟阻塞 | 未采用 |
| 1 轮 | 快速失败；符合“换 Agent”判断 | 少数可修复错误会多一次人工 | **采用** |

#### 3.6 任务/作业事务边界

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 分开更新 | 改动小 | 可能出现任务已验收、作业还在跑 | 未采用 |
| 一个事务 | 状态一致；幂等简单 | 需要重构 `finish_job` | **采用** |

#### 3.7 artifacts 候选

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 结算时写 pending 表 | UI 可提前展示 | 草稿可见；多一套状态 | 未采用 |
| 留在 `jobs.result`，完成时发布 | 无草稿；简单 | 完成时才看得到 | **采用** |

### 4. 决策依据

1. **提交是输入，不是结算的副作用**：Agent 已经提交，H8 只校验；这样没有“提交成功但任务没更新”的中间态。
2. **一个 DB 事务**：任务和作业状态必须一起变；否则会出现验收作业已派发、任务还在执行的竞态。
3. **候选不等于知识**：`shared_updates` 和 `artifacts` 在验收前只是候选，入库/发布放在任务完成，避免撤回和草稿污染。
4. **验收者整体判断**：把共享记录当作任务交付的一部分，错误/缺失走现有 `issues` 拒绝；不另设评审协议，符合信任 Agent 的前提。
5. **项目记忆不依赖 DAG**：执行者不需要知道下游；系统按项目记忆注入，超过 5k 用索引兜底。
6. **协议错误快速失败**：一次纠正后阻塞，避免弱 Agent 在同一错误上重复消耗；由人工决定是否换 Agent。

### 5. 移交 H11

- artifacts 候选与共享记录的发布顺序、幂等、失败处理。
- `verified_commit → merge_commit` 映射的存储位置与写入时机。
- 里程碑任务人工验收通过后的发布。
- 合入冲突/失败时候选记录的保留与再次验收。
- 旧结果（`commit_files` 版本）兼容与迁移。
- `shared_updates` 从对象数组迁移为字符串数组的解析与入库映射（topic/scope/evidence 的默认值）。

### 6. 实现前提

- `context.json` 注入 `job_start_head` 与任务分支名。
- `jobs` 增加 `start_head`（或等价字段）用于审计与恢复。
- `finish_job` 重构为可参与同一个 DB 事务，或在事务后调用且幂等。
- 验收作业通过 `execution_job_id` 读取执行结果中的候选记录（H9）。

### 7. 风险

- 一次纠正不足以修复弱 Agent 的表达错误：这是有意的快速失败，人工可换 Agent。
- 候选只存在 `jobs.result`：如果结果被后续轮次覆盖，历史候选只能从 `job_runs` 或旧作业目录追溯；需要在实现时确认审计范围。
- DB 事务失败后作业标记失败，但提交仍在分支上：重试会追加提交，不会回退；这是 append-only 的预期行为。
- 5k 阈值后按需读取依赖 Agent 主动读取；提示词必须明确读取方式。
- 工作区干净检查可能误伤未被忽略的临时文件；提示词必须提前说明放置位置。


## 三、任务验收与合入（H9–H13）

### H9 执行者 → 验收者

> 2026-11-07 定稿。本文定义**验收输入**；验收结果与流转见 H10。
> 范围：验收者看到什么、按什么判断。
> 不在范围：验收结果格式、通过/拒绝后的处理（H10）；合入（H11）。

### 1. 范围

H9 只定义验收输入：

- 验收者看到哪些上下文；
- 验收工作区是什么；
- 哪些东西明确不给；
- 验收者如何判断成果一致性、候选项目记忆和子任务成果。

### 2. 当前输入与调整

当前验收者能看到：任务描述、验收标准、上一轮问题与指导、任务分支的独立工作区、改动规模统计、项目共享记忆、项目成果索引。

调整后：

- 增加执行者 summary，标明“自述，不是证据”。
- 改动规模改为“与目标的合并基到当前版本的 diff”；不注入预生成的文件清单。
- 增加候选项目记忆。
- 增加执行者的成果清单，用于一致性检查。
- 父任务增加子任务成果清单。
- 明确验收者做成果一致性检查，但不做质量评审。
- 明确验收者不提交共享记录。

### 3. 最终输入

1. 任务描述与验收标准。
2. 项目目标、项目级验收标准、约束与关键假设（与 H6 相同的契约切片）。
3. 执行者 summary（自述，不是证据）。
4. 任务与目标的合并基、当前版本（Git 用于 diff；普通工作区用于确认当前现场）。
5. 上一轮问题与指导（必须复核，但不是全部范围）。
6. 候选项目记忆（≤5 条 ×120 字，含 supersedes 指向的编号）。
7. 已接受的项目记忆（≤5k 全量；超过用带编号的索引 + 按需读取；已失效编号不注入）。
8. 执行者的成果清单（≤4）与 retired_artifacts（如有）。
9. 父任务额外：子任务成果清单。
10. 独立任务分支工作区（Git）或当前项目目录（普通工作区）。

不给：

- 预生成的文件清单；
- 完整 diff（工作区里可以自己看）；
- 执行者的提交记录（验收者只关心当前分支状态）。

### 4. 逐项决策

#### 4.1 执行者 summary

**给。** 标明“执行者自述，不是证据”。

理由：验收者能知道执行者声称做了什么、自己说没覆盖什么，避免漏查；验收标准固定、证据必须逐条填写，锚定风险可控。

#### 4.2 改动范围

**不注入文件清单。** Git 工作区由验收者用“与目标的合并基到当前版本”做 diff；普通工作区是全量检查。

理由：文件清单是 Git 已经能提供的事实，不需要系统再复制一遍。给任务起点就够了。

#### 4.3 上一轮问题与指导

**保留，作为补充复核清单。** 全量验收所有标准仍然是强制的。

理由：

- 任务被拒后，执行者是按这些问题修的；验收者需要确认旧问题真的关闭；
- 不给会重复发现同一个问题，也失去“上次的出口条件是什么”；
- 但旧问题不能缩小范围，修复可能引入新问题，所以全量重验必须保留。

#### 4.4 候选项目记忆

**给。** 每条 ≤120 字，最多 5 条。验收者按任务整体判断：内容错误、或缺少下游必需的信息 → 在 issues 里拒绝。带 supersedes 的候选，还要判断替代是否成立：目标编号存在、本条确实应替代它；不成立 → issue，要求改为新增或撤销。

不设单独的逐条 review 字段；验收者不提交 shared_updates，其发现写入 issues / reason。

#### 4.5 已接受的项目记忆

**给。** 全项目可见；每条带编号；≤5k 字全量注入，超过则带编号的索引 + 按需读取；已失效编号不注入。

理由：执行者不需要知道下游；项目记忆不按 DAG 过滤。项目大时用索引控制上下文。

#### 4.6 成果一致性检查

验收者要看执行者的成果清单（≤4）、retired_artifacts 和 summary，做**一致性检查**，不做质量评审：

- 路径存在，类型对（文件/目录）；
- 目录非空，文件可读；
- 内容和描述/格式大致一致（如“报告”是文本，“夹具目录”里有文件）；
- summary 声称交付的东西，在实际成果或改动里找得到；
- 不一致 → execute + issue。

**父任务额外检查子任务成果：**

- 路径可达 → 通过；
- 不可达但父任务给出了 retired_artifacts（path + reason）→ 验收者判断理由是否成立；成立则通过；
- 不可达且没有退役 → execute + issue，要求保留或退役。

理由：一致性检查防止“声明了但不存在/不对”；它不判断入口好不好用，那是验收标准的事。

#### 4.7 验收工作区

**默认独立任务分支，只读，不合并、不做合并预演、不写目标分支。**

冲突解决后，任务分支已经包含目标分支；此时验收的是集成任务分支，diff 仍从“与目标的合并基”算。

理由：

- 验收验局部，项目验收验集成；
- 让验收者合并会把目标分支提前写入未验收内容，里程碑也无法在人工通过前保持干净；
- 冲突留给 H12；
- 落地后不重验（H11），集成问题由项目验收兜底。

### 5. 验收者明确不做的事

- 不修改交付物；
- 不提交、不合并、不写目标分支；
- 不提交 shared_updates；
- 不对成果做质量评审，只做一致性检查；
- 不把上一轮问题当成全部验收范围。

### 6. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| 给不给执行者 summary | 不给 / 给（标明自述） | **给**。避免漏查，锚定风险可控 |
| 改动范围 | 预生成文件清单 / 验收者自己 diff | **自己 diff**。合并基由 DOMO 计算 |
| 验哪里 | 独立任务分支 / 集成预览 / 验收者合并 | **独立任务分支**。局部验收，集成留给项目验收 |
| 上一轮问题 | 不给 / 只查旧问题 / 全量 + 旧问题复核 | **全量 + 旧问题复核** |
| 自己的成果 | 不审 / 一致性检查 / 质量评审 | **一致性检查**。不审质量 |
| 父任务子任务成果 | 不看 / 看清单 | **看清单**，保留或退役 |
| 候选记忆 | 逐条 review / 任务整体验收 | **任务整体验收**，错误/缺失走 issues |

### 7. 决策依据

1. **验收者要独立判断，但不需要重新发现一切**：summary 和旧问题是上下文，不是结论；全量标准和证据仍然强制。
2. **Git 事实由 DOMO 或验收者自己读取**：不注入文件清单，避免系统重复表达。
3. **任务验收只验局部**：把集成塞进任务验收会让范围变宽、责任不清；项目验收是集成关口。
4. **成果一致性不是质量评审**：只防止“声明了但不存在/不对”，不把入口好不好用变成新门槛。
5. **共享记录是任务交付的一部分**：错误/缺失走 issues，不另设评审协议，符合信任 Agent 的前提。

### 8. 移交 H10

- 验收结果的结构：pass / execute / request。
- issues 的 title/detail 规则。
- 候选记忆错误、子任务成果缺失如何写入 issues。
- 成果一致性问题如何写入 issues。
- 通过后进入 H11；execute 退回执行；request 交给规划者/父任务。

### 9. 风险

- 给 summary 可能锚定验收者：用“自述，不是证据”标注，并要求逐条证据。
- 旧问题可能缩小注意力：明确要求全量验收所有标准。
- 不注入文件清单依赖验收者主动 diff：提示词必须说明合并基和查看方式。
- 候选记忆可能被当成已接受知识：标注“候选”，验收后入库。
- 一致性检查可能被误用成质量评审：提示词必须限定“存在、类型、非空、描述一致”。


### H10 验收者 → 执行者 / 决策层

> 2026-11-07 定稿。承接 H9；本文定义**验收结果**及三种结果的后续流转。
> 范围：验收者返回什么、任务如何流转。
> 不在范围：合入（H11）、项目验收（H14）、规划者/父任务的决策内容（H4）。

### 1. 三种互斥结果

验收结果只有一个字段表达结论：

- **pass**：通过，进入 H11。
- **execute**：存在可修复缺陷，退回执行者返工。
- **request**：任务内部无法闭合，请求规划者/父任务介入。

三种结果互斥；结果里不再有 reason / blocked_on / why 这些额外说明字段。

#### 1.1 pass

~~~json
{
  "result": "pass",
  "evidence": {
    "contract_id": 3,
    "artifact_version": "<验收时的任务版本>",
    "criteria": [
      { "criterion": "验收标准原文", "passed": true,
        "checks": [{ "method": "实际检查方法", "result": "实际结果" }] }
    ]
  }
}
~~~

- issues 缺省；
- 进入 H11。

#### 1.2 execute

~~~json
{
  "result": "execute",
  "issues": [
    { "title": "候选记忆与实测不符",
      "detail": "候选原文「…」与实际结果不一致；应改为「…」或删除" }
  ],
  "evidence": { "...": "沿用现有验收证据" }
}
~~~

- issues 至少 1 条，表示可修复缺陷；
- 计入验收拒绝次数；
- 连续 3 次 execute 由系统升级到规划者/父任务；
- 退回执行者，任务回到执行阶段。

#### 1.3 request

~~~json
{
  "result": "request",
  "issues": [
    { "title": "缺少 V1.04a 原机截图",
      "detail": "没有原机截图，无法判断相机与摆位是否保真" }
  ],
  "evidence": { "...": "沿用现有验收证据" }
}
~~~

- issues 至少 1 条，表示需要外部提供/决定的内容；支持多条；
- 不带 guidance / user_action；
- 不计验收拒绝次数；
- 统一交给规划者或父任务，按 H4 的三种决策处理：继续（给指导）、等待（等人）、替换方案；
- 验收者只报告“缺什么、为什么过不去”，不规定下一步。

### 2. 字段规则

| 字段 | 适用结果 | 规则 |
|---|---|---|
| result | 全部 | pass / execute / request，互斥 |
| evidence | 全部 | 沿用现有验收证据；逐条对应标准，版本固定 |
| issues | execute / request | 至少 1 条；title 必填 ≤30 字；detail 可选 ≤400 字 |

- pass 出现 issues 不合法；
- execute / request 缺少 issues 不合法；
- execute 的 issues 是可修复缺陷；request 的 issues 是外部缺失项。

### 3. issues 规则

- **用途**：只列需要行动的事项，不是验收证据的复述。
- **结构**：title 必填，独立说清问题或缺失项；detail 可选，是 title 的补充说明。
- **顺序**：按重要性排序；不设严重程度字段。
- **范围**：
  - execute：验收标准、交付一致性、成果一致性、项目记忆问题；
  - request：外部资源、授权、输入、标准解释、范围/计划问题。
- **替换**：每轮 issues 是当前完整清单，替换上一轮；已解决的不再重复。
- **候选记忆**：title 概括，detail 引用原文并说明错在哪、应改成什么。supersedes 指向错误或替代理由不成立时，detail 写明目标编号与正确关系。
- **子任务成果缺失**：title 指明子任务和成果，detail 给路径和“保留或退役”的要求。
- **summary 与事实不符**：也是 issue，比如声称交付了某个入口但实际没有。
- **条数**：不硬限；一长串说明任务本身有问题。

### 4. evidence

沿用现有验收证据格式，不在 H10 重新设计：

- 逐条对应验收标准，条目数与顺序一致；
- 每条写实际检查方法和结果；
- 证据固定到验收时的任务版本；
- pass 时全部通过；execute / request 时未完成项标为未通过，并说明原因。

详细字段沿用既有验收结果契约。

### 5. 成果一致性检查

验收者要看执行者的成果清单（≤4）、retired_artifacts 和 summary，做**一致性检查**，不做质量评审：

- 路径存在，类型对（文件/目录）；
- 目录非空，文件可读；
- 内容和描述/格式大致一致（如“报告”是文本，“夹具目录”里有文件）；
- summary 声称交付的东西，在实际成果或改动里找得到；
- 不一致 → execute + issue。

父任务额外检查子任务成果：

- 路径可达 → 通过；
- 不可达但父任务给出了 retired_artifacts（path + reason）→ 验收者判断理由是否成立；成立则通过；
- 不可达且没有退役 → execute + issue，要求保留或退役。

### 6. 拒绝次数与升级

- execute 计入验收拒绝次数；request 不计；
- 连续 3 次 execute，系统自动升级到规划者/父任务；
- 升级是系统行为，不是验收者的一个可选结果；
- 验收者仍然返回 execute，由系统决定是否升级。

### 7. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| wait / review 是否分开 | 分开 / 合并 | **合并**为 request；都由规划者/父任务先判断 |
| 结论字段 | pass + next_action / 单一 result | **单一 result**；三者互斥 |
| request 怎么表达 | reason + blocked_on / 复用 issues | **复用 issues**；支持多条，字段统一 |
| reason 是否保留 | 保留 / 删除 | **删除**；issues 已表达问题和缺失，pass 有 evidence |
| request 是否带 guidance/user_action | 带 / 不带 | **不带**；决策层决定下一步 |
| issues 结构 | 纯字符串 / title+detail | **title+detail**；可展示、可行动 |
| 成果是否审 | 不审 / 一致性检查 / 质量评审 | **一致性检查**；不审质量 |
| 退役表达 | summary 解释 / 结构化 retired | **结构化 retired**；否则无法核对 |

### 8. 决策依据

1. **三种结果互斥**：pass、返工、请求介入是三种不同状态，用一个字段表达最清楚。
2. **issues 是统一行动清单**：execute 是“要修什么”，request 是“缺什么”；结构相同，支持多条。
3. **不再需要 reason**：问题/缺失已经由 issues 表达；pass 由 evidence 和 result 表达。
4. **验收者只报告事实**：缺什么、为什么过不去；不决定找谁、下一步怎么做。
5. **决策层拥有路由权**：所有 request 先给规划者/父任务，由它判断是否需要用户。
6. **一致性检查不是质量评审**：只防止“声明了但不存在/不对”。

### 9. 移交

- pass → H11：合入、发布、完成。
- execute → 执行者返工；下一轮验收重新走 H9/H10。
- request → 规划者/父任务决策（H4）；决策结果可能给指导、要求用户操作或生成替代方案。
- 候选记忆修正：执行者全量重提最新列表（text 与 supersedes）；编号由 DOMO 维护，执行者不改编号。

### 10. 风险

- execute 与 request 都使用 issues，靠 result 区分；提示词必须说明两者语义不同。
- request 全部先给规划者/父任务，会增加一次决策作业；换来协议更简单、请求先被正确性确认。
- 一致性检查可能被误用成质量评审；提示词必须限定“存在、类型、非空、描述一致”。
- issues 只有 title/detail，复杂问题可能表达不全；detail 上限 400 字，超出应拆分或写进证据。
- 子任务成果退役可能被滥用；验收者必须判断 reason 是否成立。
- 三次 execute 自动升级是系统行为，验收者不需要也不能选择 review。


### H11 验收通过 → 合入

> 2026-11-07 定稿。里程碑人工验收的细节见 H19。
> 范围：验收返回通过之后，到任务完成之前。
> 包括：验证版本冻结、落地目标、落地版本、成果与知识的发布、里程碑与普通工作区差异。
> 不包括：合入冲突后的具体处理（H12），H11 只定义“冲突时不发布、退回执行者”。

### 1. 产品流程

1. **验收通过**：确定并冻结“验证版本”——验收者实际检查的任务版本。
2. **里程碑任务**：停在人工验收；验证版本不变。人工通过后才继续；人工拒绝则退回，不发布。
3. **确定落地目标**：父任务分支或项目交付分支。
4. **落地**：
   - 成功且有新提交 → 记录“落地版本”；
   - 成功但没有新提交 → 落地版本 = 目标当前版本；
   - 失败或冲突 → 不发布，退回执行者；重新验收后更新验证版本。
5. **发布**：落地成功后，先发布项目记忆，再发布成果。记忆发布在一个事务内分配编号（M1、M2……）、写入记录、把 supersedes 指向的旧记录标记失效；两者都幂等；任一步失败，任务保持未完成，重试发布，不重复落地。
6. **完成**：两项发布都成功后任务才完成；不静默完成。
7. **普通工作区**：没有落地步骤；验收通过（或人工通过）后直接发布并完成。
8. **统一路径**：正常验收和里程碑人工验收走同一条完成路径，避免发布逻辑分叉。

### 2. 成果规则

#### 2.1 成果是什么

- 任务产出的、值得人打开或下游引用的入口，最多 4 个。
- 只有一种类型，不区分最终/中间/输入；顺序即优先级，第一条是主入口。
- 目录优先；单文件只在确实需要独立引用时登记。
- 参考输入不是成果，放在契约、资源目录或共享记录。

#### 2.2 子任务与父任务

- **子任务完成时**：只发布项目记忆（shared_updates）；成果暂存，不进入项目成果面板。
- **父任务落地到项目交付分支时**：发布自己的成果，以及子任务成果中“在落地版本里可达”的部分。
- **父任务取消/失败**：子任务知识保留；成果不发布。
- **父任务修改了子任务成果的内容**：路径仍可达，则发布父任务版本，来源注明“由父任务修改”。

#### 2.3 缺失的成果不能跳过

- 子任务成果在父任务验收时是输入的一部分。
- 每个子任务成果必须满足其一：
  - 路径在父任务版本里可达；
  - 父任务显式退役：说明重命名、合并或移除，并给出新路径或理由。
- 两者都不满足 → **父任务验收失败**，退回执行者处理。
- 不允许静默跳过；跳过会造成“声明过、后来消失”的静默丢失。
- 检查放在父任务验收，而不是落地时：复用现有验收失败/退回路径。

#### 2.4 普通工作区

- 没有落地概念，但为保持“成果必须真的在项目里”，子任务成果同样等父任务完成后再发布。
- 子任务完成时只发布知识；父任务完成时发布自己的成果和可达的子任务成果。
- 父任务删除或替换子任务成果时，同样必须保留或显式退役。

### 3. 交付记录

每个任务保留一条最终交付记录：

- 验证版本：验收者实际检查的版本；
- 落地版本：最终落到的版本；没有新提交时等于目标当前版本；
- 落地目标：父任务分支或项目交付分支。

不单独保留“每次验证→落地”的历史；过程通过事件审计。理由：一个任务只向一个目标交付一次，重试和冲突都是同一次交付的过程。

#### 3.1 发布失败

发布分两步：项目记忆、成果。任一步都可能失败（仓库写入失败、锁冲突、元数据写入失败、路径已不可达等）。

- 记忆失败 → 任务不完成，重试记忆；不尝试成果。
- 记忆成功、成果失败 → 任务不完成，只重试成果；记忆不重复写入。
- 连续失败 → 任务阻塞，交人工处理；不能标记完成。
- 记忆先发布意味着“知识可见、任务未完成”可能短暂存在；知识是主张，不是完成声明，UI 应能看出任务状态。
- 记忆发布失败时，编号分配与失效标记整体回滚；重试使用同一候选，编号只在成功事务中生效。
- supersedes 目标存在但已被其他记录失效时，仍接受本条并记录事件，不重复失效。

### 4. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| 什么时候发布 | 落地前 / 落地后 | **落地后**。落地失败的任务不应把成果和知识发布到项目层 |
| 子任务成果 | 完成即发布 / 等父任务落地 | **等父任务落地**。否则父任务删除后会出现悬空入口 |
| 子任务成果缺失 | 跳过 / 失败 | **失败**，除非父任务显式退役。跳过会造成静默丢失 |
| 成果类型 | 保留 delivery/intermediate/input / 删除 | **删除**。实际未用起来，增加判断负担 |
| 交付记录 | 保留每次历史 / 只保留最终记录 | **只保留最终记录**；过程用事件审计 |
| 完成路径 | 正常验收与人工验收各走一套 / 统一 | **统一**，避免发布逻辑分叉 |
| squash 没有新提交 | 视为失败 / 记录目标当前版本 | **记录目标当前版本**。内容已经在目标里 |
| 落地后集成验证 | 做 / 不做 | **不做**；组合问题由项目验收兜底 |
| 发布顺序 | 记忆先 / 成果先 | **记忆先**。成果失败时用户不会先看到未完成任务的交付物 |

### 5. 已确认事项

1. **交付记录（已确认）**：每个任务一条最终记录，不单独保留交付历史；过程用事件审计。
2. **落地后的集成验证（已确认）**：不做；组合问题由项目验收兜底。
3. **发布顺序（已确认）**：记忆先、成果后；发布失败则任务不完成，重试发布。
4. **父任务验收输入（已确认）**：父任务验收者需要看到子任务成果清单；接入 H9。
5. **里程碑人工验收（已确认）**：通过则完成并合入，拒绝则退回执行并计入失败次数；不允许部分通过。细节见 H19。

### 6. 决策依据

1. **成果必须真的在项目里**：用户看到的成果入口，应该能在项目交付版本里打开；否则就是误导。
2. **知识可以先走**：共享记录是事实/约束，不依赖落地；子任务完成后即可帮助其他任务。
3. **缺失不能静默**：声明过的入口消失，必须由父任务解释；否则用户和下游都会失去线索。
4. **任务只有一个最终交付**：重试、冲突、再验收都是过程；保留一条最终记录足够，历史交给事件。
5. **统一完成路径**：正常验收和人工验收如果各走一套，发布和映射迟早会不一致。

### 7. 风险

- 父任务可能不知道子任务成果，导致“缺失即失败”变成误伤。缓解：父任务验收输入必须包含子任务成果清单。
- 父任务显式退役可能被滥用，用来绕过保留要求。缓解：退役必须给出新路径或理由，验收者判断。
- 成果路径存在但内容被大幅修改：入口还在，但已不是子任务原样产出。需要来源注明，不能让用户误以为是子任务原始成果。
- 子任务知识在父任务未落地时可见，可能被误读为“项目已实现”。提示词必须要求写成事实/约束，不写完成声明。
- 落地后不做集成验证：组合问题推迟到项目验收；这是有意的取舍，不另设高风险冒烟。


### H12 合入冲突 → 执行者

> 2026-11-07 定稿。承接 H11；本文定义合入冲突的交接、解决与重新验收。
> 范围：目标分支与任务分支冲突时的处理。
> 不在范围：正常合入与发布（H11）、规划者/父任务的决策内容（H4）。

### 1. 触发

H11 尝试把任务分支合入目标分支（squash）时，如果目标分支在任务创建后已经前进，可能发生冲突。

处理顺序：

1. 在目标分支上尝试合入；
2. 冲突 → 目标分支保持原状，回到合入前；
3. 在**任务工作区**里把目标分支 merge 进来，留下冲突；
4. 任务退回执行者。

不是 rebase。原因：

- rebase 会改写任务分支历史，违反 append-only；
- 所有提交 SHA 都会变，之前验收的版本、archive ref、审计记录全部对不上；
- 执行者也不应该碰目标分支。

另一种失败：目标分支有未提交改动，或合入失败但没有文件冲突。这两种不交给执行者，直接阻塞，由用户/规划者处理。

### 2. 交接给执行者

任务回到执行阶段，带一条冲突说明：

- 目标分支是哪个；
- 冲突文件有哪些；
- 工作区已经处于 merge 冲突状态；
- 要求消除冲突标记，保留任务需要的改动。

冲突说明复用 issues 的 title/detail：

- title：合入冲突：目标分支（≤30 字）；
- detail：主要冲突文件、工作区状态、处理要求（≤400 字）；文件太多时指向工作区。

### 3. 执行者怎么解决

执行者在**任务工作区**里解决，不在目标分支上操作：

- 编辑冲突文件，消除冲突标记；
- 保留任务需要的改动；
- 提交，产生一个 merge commit；
- merge commit 的两个父提交是：任务分支原来的 HEAD + 目标分支的 HEAD；
- 目标分支在解决期间完全不变。

merge commit 是追加，不是改写，所以 append-only 仍然成立；仍然禁止 rebase / amend / reset。

如果解决冲突需要改变任务范围、验收标准或方案，执行者应走 replan/decision，不能在冲突解决里静默扩大范围。

### 4. 重新验收

解决后，验收者拿到的是**集成后的任务分支**：任务分支已经包含目标分支的历史。

验收范围：

- base = 目标分支与任务分支的合并基（也就是被 merge 进来的目标 HEAD）；
- head = 任务分支当前 HEAD（merge commit）；
- diff 范围 base..head，只包含本任务改动 + 冲突解决；
- 目标分支带来的其他任务改动是上下文，不算本任务改动。

必须**完整重验**，不能只查冲突文件。冲突解决可能影响其他行为。

验收版本仍是任务分支 HEAD；artifact_version 记录这个版本。

### 5. 再次合入

验收通过后，H11 再对目标分支做 squash 合入：

- 合入范围是 base..head，也就是本任务真正带来的改动；
- 目标分支得到新的 squash commit；
- 任务分支随后归档。

如果这期间目标分支又前进，可能再次冲突，回到 H12。

冲突尝试额度建议 3 次：

- 每次冲突退回执行者，冲突次数 +1；
- 3 次仍冲突 → 不再自动重试，交给规划者/父任务；
- 冲突次数不占验收拒绝次数。

### 6. 规则汇总

- 冲突解决在任务分支，不在目标分支；
- 允许 merge commit；禁止 rebase / amend / reset；
- 目标分支保持干净，直到验收通过后才合入；
- 验收 diff 用“与目标的合并基 → 任务 HEAD”；
- 解决后完整重验；
- 冲突尝试 3 次后交规划者/父任务；
- 目标分支脏或无冲突失败：阻塞，不创建执行作业；
- 冲突解决影响子任务成果时，用 retired_artifacts 声明。

### 7. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| 用 rebase 还是 merge | rebase / merge | **merge**；rebase 改写历史、改变 SHA |
| 在哪解决 | 目标分支 / 任务分支 | **任务分支**；目标分支保持干净 |
| 验收范围 | 只查冲突文件 / 完整重验 | **完整重验**；冲突解决可能影响其他行为 |
| 冲突计不计拒绝 | 计入 / 单独额度 | **单独额度**，3 次后交上级 |
| 冲突提示 | 自由文本 / issues 结构 | **issues title/detail**；与 H10 一致 |

### 8. 决策依据

1. **目标分支只接收验收通过的内容**：冲突解决在任务分支，目标分支在通过前不变。
2. **append-only**：merge 是追加，rebase 是改写；只能 merge。
3. **验收要看到真实集成状态**：解决后的任务分支包含目标内容，验收者看集成后的任务，但 diff 只算本任务改动。
4. **完整重验**：冲突解决可能影响其他行为，只查冲突文件不够。
5. **冲突不是任务缺陷**：单独额度，不计验收拒绝次数；反复冲突交上级判断。

### 9. 影响

- H9：验收 diff 的 base 从“任务起点”改为“与目标的合并基”；独立任务分支在冲突后变成集成任务分支。
- H8：diff 范围校验同样使用“与目标的合并基”；append-only 仍用作业起点。
- H7：明确允许冲突解决产生 merge commit。
- H11：合入范围是合并基..任务 HEAD；冲突后可再次合入。

### 10. 风险

- 任务分支变成集成分支，验收者会看到其他任务的改动；diff base 必须准确，否则会把别人的改动算进任务。
- merge commit 让任务历史非线性；squash 合入后会扁平化，但审计要看任务分支。
- 冲突可能反复发生；3 次额度后必须交上级，不能无限循环。
- 执行者可能在解决冲突时改变范围或标准；必须走 replan/decision。
- 冲突文件很多时，detail 400 字放不下；指向工作区，不逐文件列举。


### H13 任务完成 → 下游任务

> 2026-11-07 定稿。承接 H11/H12；本文定义下游任务看到什么。
> 范围：一个任务完成后，依赖它的后续任务如何获取上下文。
> 不在范围：任务派发与依赖门（H5）、成果发布（H11）、项目验收（H14）。

### 1. 最终模型

下游任务启动时拿到：

- 自己的任务描述与验收标准；
- 项目目标、项目级验收标准、约束与关键假设（H6 的契约切片，所有任务相同）；
- 项目分支当前状态（Git）或当前目录（普通工作区）；
- 已接受的项目记忆；
- 项目成果索引；
- 其他任务产生的、已经进入项目分支的内容（通过项目现状体现）。

不拿：

- 前置任务的 summary；
- 前置任务的结果文件、提交区间、验收证据；
- 按依赖过滤后的项目记忆；
- 按依赖过滤后的成果视图。

**依赖关系只决定“什么时候可以开始”，不再负责传递文本。**

### 2. 为什么下游不看 summary

summary 是给人看的：

- 说明交付了什么、怎么验证、还有什么没覆盖；
- 也是验收者判断“执行者自述”的输入；
- 但它不是项目事实，容易过期，也容易自我表扬。

下游真正需要的是项目现状和事实：

- 代码和文件是什么样，直接看项目分支；
- 已经确认的结论、约束、接口，看项目记忆；
- 值得打开的入口，看项目成果。

如果上游有下游必须知道的限制或未覆盖项，应该写进项目记忆，而不是藏在 summary 里。验收者也要检查是否遗漏了关键信息（H9/H10）。

风险是上游把重要限制只写在 summary 里。缓解方式：

- 提示词明确要求“下游必须知道的限制写进 shared_updates”；
- 验收者把“缺少关键项目记忆”作为 issue；
- summary 写长写短不再影响下游，只影响人类阅读。

### 3. 项目记忆的可见性

- 全项目可见，不按 DAG 过滤；
- 每条带编号与来源任务，例如 [M17][T31]；已失效的编号不注入；
- 注入时 ≤5k 字全量，超过用带编号的索引 + 按需读取；
- 下游可能看到与本任务不直接相关的记忆；提示词要说明“这是项目记忆，不是本任务要求”。

### 4. 成果的可见性

- 任务完成后的成果进入项目索引，全项目可见；
- 子任务成果等父任务落地后才进入索引；
- 下游即使看不到子任务成果的索引条目，也能在父任务分支的工作区里直接看到文件；成果索引只是导航。
- 不做“只看前置任务成果”的过滤视图。

### 5. summary 的定位

- 服务人、验收者和审计；
- 不作为下游交接；
- 长度保持软建议（约 2000 字以内），不做硬性协议校验；
- 重要事实放项目记忆，详细说明放报告/成果。

### 6. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| 下游看什么 | 前置 summary / 项目现状 + 记忆 + 成果 | **项目现状 + 记忆 + 成果** |
| 要不要结构化交接 | 新增 handoff 字段 / 用项目记忆 | **用项目记忆**；不新增字段 |
| 记忆是否按 DAG 过滤 | 按依赖 / 全项目 | **全项目**；执行者不需要猜下游 |
| 成果是否按依赖过滤 | 只看前置 / 全局索引 | **全局索引**；来源任务可筛选 |
| summary 是否给下游 | 给 / 不给 | **不给**；summary 给人、验收和审计 |
| summary 是否硬限长 | 硬上限 / 软建议 | **软建议**；写长是体验问题，不是交付错误 |

### 7. 决策依据

1. **项目现状是唯一事实来源**：代码、文件、合入结果都在项目分支上，下游直接看。
2. **项目记忆负责事实和约束**：summary 是叙述，记忆是可复用的结论；下游不需要叙述。
3. **依赖不传递文本**：依赖只解决顺序和集成；把 summary 当交接会让过期叙述变成下游依据。
4. **全项目可见避免猜下游**：执行者不需要知道谁消费；系统按项目记忆提供。
5. **成果是导航**：子任务成果延迟发布不影响下游执行，因为文件已经在分支里。

### 8. 移交 H14

- 项目验收是否使用任务 summary：属于 H14 的输入设计。
- 项目验收如何汇总任务证据与项目记忆。
- 集成问题在项目验收阶段如何暴露。

### 9. 风险

- 关键限制只在 summary 里，没进项目记忆：提示词和验收者要兜住。
- 全项目记忆过多：5k 阈值 + 索引按需读取。
- 子任务成果延迟发布：下游看不到索引，但能在工作区看到文件；导航能力暂时缺失。
- 不相关的项目记忆可能分散注意力：提示词说明“项目记忆不是本任务要求”。
- 下游不看 summary 可能重复发现上游已说明的问题：这被接受，换取下游以项目事实为准。


## 四、项目验收与人工验收（H14、H15、H19）

### H14 全部任务 → 项目验收

> 2026-11-07 定稿。本文定义**项目验收**的输入、结果与后续流转。
> 上游：H11/H12/H13。下游：H15（人工验收）。
> 不在范围：人工验收的具体交互（H15）、项目分支合入 base（H16）。

### 1. 定位

项目验收是**唯一的集成关口**：H11 已决定落地后不做集成验证，任务级验收只验任务分支。因此项目验收必须实际检查最终项目分支，而不是汇总“任务都通过了”。

项目验收作业由**规划者角色**执行（与项目分析、重规划同一个 Agent 池）。因此它既做判定，也做“不通过时怎么继续”的方案，不需要再转交另一个规划作业。

### 2. 最终契约

~~~json
{
  "result": "deliver" | "execute",
  "issues": [
    { "title": "…", "detail": "…" }
  ],
  "report": "Markdown 报告",
  "plan": {
    "message": "为什么这样调整",
    "goal": "当前项目目标（不得修改）",
    "constraints": [],
    "assumptions": [],
    "acceptance": [],
    "tasks": [ … ]
  }
}
~~~

#### 2.1 deliver

**含义：Agent 侧已闭合，交付人工。**

- report 必填；
- issues 可选：Agent 无法解决、需要人处理或确认的未闭合项；
- plan 必须缺省；
- 项目进入人工验收（H15），不是阻塞。

没有 issues = 全部自动验证通过；有 issues = 交付但带未闭合项。两者都进人工验收，区别只在报告内容和界面提示。

#### 2.2 execute

**含义：需要更多 Agent 工作。**

- issues 必填：为什么没通过、要补什么；
- plan 必填：重规划方案；
- report 必须缺省；
- 应用方案 → 执行 → 再次项目验收。

#### 2.3 判断规则

只有一条：

> **这件事能不能通过更多 Agent 工作解决？**

- 能 → execute；
- 不能（缺外部资源、只有人能确认、需要人做取舍）→ deliver。

不需要再区分“失败”“等待”“请求裁决”。三者在项目层没有不同的去向，都会到人工验收。

### 3. 字段规则

| 字段 | deliver | execute | 规则 |
|---|---|---|---|
| result | 必填 | 必填 | 只有两个值，互斥 |
| issues | 可选 | 必填 | title 必填 ≤30 字；detail 可选 ≤400 字；每轮是完整清单 |
| report | 必填 | 必须缺省 | Markdown；逐条对应契约标准 |
| plan | 必须缺省 | 必填 | 任务数组，结构同提案任务 |

issues 的语义随 result 变化：

- deliver：交给**人**处理或确认；
- execute：交给**规划者/执行者**处理。

### 4. 输入

项目验收拿到：

- 交付契约：目标、项目级验收标准、关键假设；
- 项目分支当前状态（普通工作区为当前目录）；
- 任务清单与状态（key、标题、验收标准、完成/取消），**不注入任务 summary 全文**；
- 已接受的项目记忆；
- 项目成果索引；
- 上一次项目验收报告与反馈（如有）。

不给：

- 任务级验收证据；
- 任务 summary 全文（需要时从项目分支和项目记忆获取事实）；
- 任务分支或提交区间。

理由见 H13：summary 是叙述，不是事实；项目验收按契约标准检查最终状态。

### 5. 报告要求

报告是项目验收的主要产物，也是人工验收唯一的判决依据。因此：

- **逐条对应契约的项目级验收标准**：每条写检查对象（文件、目录或分支版本）、检查范围（全量或抽样，抽样多少）、检查方法（命令、对比或人工核对）、实际结果、证据位置；只写“已检查/已满足”不合格；
- **验了什么必须可读**：报告固定包含一节「验收执行记录」，按标准顺序写上述五项；系统不做结构校验，但这是人工验收判断“是否真的检查过”的依据；
- 未闭合项单列一节：缺什么、为什么 Agent 解决不了、需要谁做什么；
- 不重复日志；细节指向文件或成果；
- 报告只能陈述已实际检查过的内容，不能把“应当满足”写成“已满足”。

项目验收**不设 criteria 字段**，也不机械校验报告是否覆盖全部标准。这是明确取舍：选择相信 Agent 的表述能力，把判断交给人工；代价是漏项只能靠人发现，因此撰写要求是唯一的结构约束。

### 6. 方案要求

plan 与提案方案结构相同：message、goal、constraints、assumptions、acceptance、tasks。

其中 goal 必须等于当前项目目标（重规划不能改目标）；acceptance、assumptions 可以调整，因为它们描述的是“怎么算完成”和“方案前提”。

应用规则：

- 校验 key 唯一、deps 合法、无环、不与现存/已取消任务冲突；
- **跳过 replan_review**：验收者本身就是规划者，自我审批没有意义；
- 项目开启“方案需确认”时，仍让用户确认一次；这是产品模式，不是角色审查；
- `execute` 的 plan 按项目重规划草稿处理：应用前可放弃并恢复旧计划，在途作业结算后应用，中断可恢复，每轮记录可审计；
- 应用后项目回到执行阶段，完成后再次项目验收。

风险：验收作业是独立会话，看到的是契约、分支和任务清单，没有完整规划上下文。它可能提出与已完成任务重复的方案，所以“与现存任务冲突”的校验不能省。

### 7. 场景推演

| 场景 | result | issues | report | plan | 之后 |
|---|---|---|---|---|---|
| 全部自动验证通过 | deliver | 无 | 有 | 无 | 人工验收 |
| 部分标准只有人能确认 | deliver | 待确认项 | 有，含待确认清单 | 无 | 人工验收 |
| 缺外部条件，Agent 无法推进 | deliver | 阻塞项 | 有，短报告说明为什么卡住 | 无 | 人工验收 |
| 有可修的缺口 | execute | 要修什么 | 无 | 有 | 应用方案 → 执行 |
| 契约外的集成问题 | execute | 集成缺口 | 无 | 有 | 应用方案 → 执行 |
| 自动重规划达到上限仍未通过 | deliver | 卡住的项 | 有，说明尝试过什么 | 无 | 人工验收 |
| 验收期间出现新任务 | — | — | — | — | 结论作废，回到执行 |
| 重规划进行中收到结论 | — | — | — | — | 只记录，不推进 |
| 项目暂停/归档中收到结论 | — | — | — | — | 记录结论，不改状态 |

“自动重规划达到上限”这一行是关键转换：修不动了就不该继续循环，转成 deliver + issues + 报告，把问题交给人。

### 8. 流转

- deliver → 项目进入人工验收（H15）；报告与未闭合项展示给用户；
- execute → 应用 plan → 执行 → 再次项目验收；
- 自动重规划有次数上限；超过后转 deliver，不再自动循环；
- 人工验收可以：接受（含带缺口接受）、驳回并要求重规划、要求补充说明；
- 人工驳回 → 回到 execute（由规划者重新出方案），这是唯一的回退通道。

### 9. 考虑过的方案

#### 9.1 结果结构

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 逐项 verdict（met/unmet/unverifiable/human_required）+ next_action（report/wait/replan/arbitrate） | 表达充分；能区分“待人工确认” | 两套维度交叉；同一条可能既 met 又要 replan；四值 verdict 与四值 action 组合复杂 | 未采用 |
| 三态（pass/execute/request）+ criteria | 保留证据账本 | criteria 与顶层结论仍可能矛盾；request 与“通过但待确认”边界模糊 | 未采用 |
| **两态（deliver/execute）+ issues/report/plan** | 只回答“要不要更多 Agent 工作”；无交叉维度 | 不再机械保证契约覆盖；通过/带缺口靠界面区分 | **采用** |

#### 9.2 是否保留 request

| 方案 | 结论 |
|---|---|
| 保留 request（请求人工裁定） | 未采用。项目层所有非 execute 结果都去人工验收，request 没有独立去向；它携带的信息就是 issues |
| 取消 request，用 issues 表达 | **采用**。是否需要人处理，由 issues 是否存在表达 |

注意：任务级（H10）仍保留 request，因为它的接收方不同（规划者/父任务，不是人）。两个层级的状态数不同是有意的，不是不一致。

#### 9.3 pass 的命名

| 方案 | 问题 | 结论 |
|---|---|---|
| pass | 暗示“全部验证通过”，与“交付但带未闭合项”矛盾 | 未采用 |
| submit | 与“提交验收结论”重名；两个结果都是“提交” | 未采用 |
| done | 暗示项目已完成，但完成要等人工验收 | 未采用 |
| **deliver** | 与已有“交付契约/交付物/交付记录”同词根；天然包含遗留项 | **采用** |

#### 9.4 是否保留逐项证据账本

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| criteria 数组 + verdict | 机械保证契约覆盖；可逐项展示 | 与顶层结论重复；四值 verdict 难维护 | 未采用 |
| 证据写进报告 | 结构简单；人工读报告即可 | 无法机械校验覆盖；漏项靠人发现 | **采用** |

#### 9.5 方案由谁出

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 验收只报缺口，另起重规划作业 | 职责单一 | 多一次作业；验收者最清楚缺口却不说方案 | 未采用 |
| **验收者直接出方案** | 少一次作业；方案贴合缺口 | 需校验与现存任务冲突 | **采用** |
| 验收者出方案并自我审批 | 流程完整 | 自我审批无意义 | 未采用 |

### 10. 决策依据

1. **只回答路由问题**：DOMO 只需要知道“要不要更多 Agent 工作”，其余都是给人看的内容；两态足够。
2. **项目层的接收方唯一**：所有非 execute 结果都到人工验收，request 因此冗余。
3. **人工是最终判决**：报告是判决依据，系统不重复做一遍机械校验；这符合“相信 Agent 智能”的一贯原则。
4. **验收者就是规划者**：同一角色池执行，出方案不是越权，也省掉一次转交。
5. **修不动就交人**：自动重规划有上限，达到后转 deliver + 报告，避免无限循环。
6. **失败轮不产报告**：execute 意味着还要继续做，此时出报告会让人误以为已交付。

### 11. 移交 H15

- 人工验收如何展示“无 issues 的 deliver”和“带 issues 的 deliver”；
- 人工验收的三种决定：接受（含带缺口）、驳回重规划、要求补充；
- 驳回后如何转成 execute；
- 报告被接受后项目如何完成、是否记一条最终交付记录。

### 12. 风险

- 不设 criteria 也不机械校验契约覆盖：漏项只能靠人工发现；缓解是报告必须有「验收执行记录」，逐条写清对象、范围、方法、结果、证据。
- deliver 带 issues 容易被误读为“全部通过”：界面和事件措辞必须区分“通过”与“交付，有 N 项待处理”。
- 验收者出方案可能重复已完成任务：应用时必须校验与现存任务冲突。
- 报告可能写成散文而不逐条对应：提示词约束，不做机械校验。
- 人工驳回是唯一回退通道：H15 必须提供，否则 deliver 带 issues 无法回到执行。
- 两态与任务级三态并存：需要在文档和提示词里说明“层级不同，不是不一致”。


### H15 项目验收 → 报告 / 人工

> 2026-11-07 定稿。本文定义项目报告生成之后，人工如何判断、如何回退、项目如何完成。
> 上游：H14（项目验收两态 deliver / execute）。下游：H16（项目分支合入 base）。
> 不在范围：任务级里程碑人工验收（H11）、项目分支合入 base（H16）。

### 1. 定位

人判断的不是报告，而是**交付结果是否符合预期**。报告只是让人理解“达成了什么、怎么做的、还有什么要注意”。

因此人工关口不提供“报告写得对不对”这种选项，也不要求人区分“是报告问题还是交付问题”。人只表达接受或不接受，由规划者解释反馈。

### 2. 四个动作

| 动作 | 条件 | 结果 |
|---|---|---|
| **接受** | 报告存在 | 项目完成 |
| **接受（带缺口）** | 报告存在且带未闭合项 | 项目完成，必须填写接受理由 |
| **重新验收** | 报告存在 | 重跑项目验收，不改变状态之外的其他内容 |
| **驳回** | 报告存在 | 必须填写意见；项目回到调整流程 |
| **提问** | 报告存在 | 只问答，不改变状态、不修改报告；可多轮 |

“接受（带缺口）”不是独立动作，是接受的一个特例：有未闭合项时，接受必须附带理由。

### 3. 接受

#### 3.1 无未闭合项

直接接受，项目完成。理由可选。

#### 3.2 带未闭合项

必须填写理由，说明为什么可以带缺口结项。这条理由进入最终交付记录。

不做逐项确认：未闭合项可能有多条，逐条勾选会增加负担，也不能提高判断质量。一句理由足够留下“人知情并同意”的痕迹。

### 4. 重新验收

**用途**：人补齐了外部条件（提供设备、数据、授权、账号），希望 AI 重新检查，而不想重新规划。

规则：

- 不修改当前报告，只触发一次新的项目验收；
- 新结论如果仍是 deliver，生成新报告替换当前报告，旧报告转为只读历史；
- 新结论如果是 execute，项目进入执行，当前报告不再是有效交付；
- 重新验收本身不产生新任务。

区分：

| 动作 | 人的意思 |
|---|---|
| 重新验收 | “我补了东西，你再看看” |
| 提问 | “你给我解释一下” |
| 驳回 | “我不接受” |

三者语义不同，不合并。

### 5. 提问

**用途**：让人在决定前弄清楚情况。

规则：

- 报告存在、尚未接受或驳回时可提问，可多轮；
- 由撰写报告的会话回答（同一上下文最清楚）；
- **不改变项目状态，不修改报告**；
- 问答进入项目历史，与报告放在一起；
- 接受或驳回后关闭；
- 同一时间只允许一个问答在进行，不设轮次上限。

为什么不允许在提问中修改报告：如果问答能顺手改报告，人就会在一个不断变化的对象上做判断，而且会出现“问完发现有问题，但报告已经悄悄变了”。有实质问题就走驳回。

### 6. 驳回

驳回只表达“我不接受，因为……”，不区分报告问题与交付问题。意见必填。

意见交给规划者解释，规划者结合契约与项目现状判断属于哪一类：

| 判断 | 处理 |
|---|---|
| 交付未达到契约，需要补工作 | 出方案 → 执行 → 再次项目验收 |
| 交付达到契约，但人不满意（主观标准） | 调整契约或目标，再出方案 |
| 只是报告没写清楚 | 重写报告，不产生新任务 |

第三类不需要人指定，是规划者的判断结果。

**目标变更**属于正常路径：如果人的反馈意味着“我要的不是这个”，就是一次项目重规划，可能需要重新走方案确认（H2）。这不是异常，而是交付后常见的调整。

### 7. 最终交付记录

项目被接受时记录一条最终交付：

- 被接受的报告（固定，不再变化）；
- 项目最终分支版本；
- 接受时间；
- 接受理由（带缺口接受时必填，其他情况可选）；
- 未闭合项清单（如有）。

与任务级的最终交付记录（H11）对应：任务级回答“每个任务交付了什么”，项目级回答“这个项目最终以什么状态交付”。

### 8. 历史

- 被驳回、被替换的报告保留只读版本，不与当前报告混在一起；
- 每轮人工意见、问答都留在项目历史里；
- 目的：事后能回答“上一版为什么被驳回”“当时人问过什么”。

### 9. 场景推演

| 场景 | 动作 | 结果 |
|---|---|---|
| 报告无未闭合项，人认可 | 接受 | 项目完成，记录最终交付 |
| 报告有未闭合项，人认可 | 接受（带缺口）+ 理由 | 项目完成，理由与未闭合项入记录 |
| 人补了设备，想再确认 | 重新验收 | 重跑验收，出新报告或转 execute |
| 人觉得功能不符合预期 | 驳回 + 意见 | 规划者判断：补工作 / 调整目标 / 重写报告 |
| 人看不懂报告某处 | 提问 | 回答，状态不变；可继续问或再决定 |
| 人问完发现确实不对 | 提问 → 驳回 | 问答留痕，进入调整流程 |
| 报告带缺口，人不接受缺口 | 驳回 + 意见 | 规划者判断是否补工作或调整目标 |
| 项目已完成后想改 | — | 不属于 H15；当前规则是开新项目（H3），重开能力另议 |

### 10. 考虑过的方案

#### 10.1 人工动作的划分

| 方案 | 问题 | 结论 |
|---|---|---|
| 接受 / 重写报告 / 重新规划 / 评论 | 要求人判断“是报告错还是交付错”，但人无法判断报告是否正确；两类驳回实际是同一件事 | 未采用 |
| 接受 / 驳回 / 提问 | 少一个“补条件后重验”的轻量路径 | 未采用 |
| **接受 / 重新验收 / 驳回 / 提问** | 覆盖三种不同意图，且不要求人做技术判断 | **采用** |

#### 10.2 带缺口的接受

| 方案 | 问题 | 结论 |
|---|---|---|
| 直接接受，不记录 | 带缺口结项没有痕迹 | 未采用 |
| 逐项确认未闭合项 | 负担重，不提高判断质量 | 未采用 |
| **接受 + 一句理由** | 留痕且轻 | **采用** |

#### 10.3 提问是否允许修改报告

| 方案 | 问题 | 结论 |
|---|---|---|
| 允许边问边改 | 判断对象在变化；“问完发现问题但报告已变” | 未采用 |
| **只回答，不改报告** | 判断对象稳定；有实质问题走驳回 | **采用** |

#### 10.4 驳回是否分类型

| 方案 | 问题 | 结论 |
|---|---|---|
| 人选择“重写报告”或“重新规划” | 人无法做这个判断 | 未采用 |
| **人只表达不接受，规划者解释** | 判断留给有能力的一方 | **采用** |

#### 10.5 报告历史

| 方案 | 问题 | 结论 |
|---|---|---|
| 只保留当前报告 | 无法回答“上一版为什么不行” | 未采用 |
| **保留只读历史** | 成本低，可追溯 | **采用** |

### 11. 决策依据

1. **人判断交付，不判断报告**：报告是描述，不是对象；因此不提供“重写报告”这个人工选项。
2. **判断留给有能力的一方**：人能表达接受或不接受，规划者能判断是补工作、改目标还是改报告。
3. **判断对象必须稳定**：提问不改报告，避免人在变化的对象上做决定。
4. **三种意图分开**：重新验收、提问、驳回分别对应“再看看”“解释一下”“不接受”，合并会让人不知道自己在做什么。
5. **带缺口要留痕**：接受是承诺，缺口的接受需要一句理由。
6. **项目级与任务级对应**：任务有最终交付记录，项目也应有，否则完成后只剩一份可能被覆盖的报告。

### 12. 移交 H16

- 项目完成后是否自动合入 base 分支；
- 合入前是否还需要一次人工确认；
- 合入失败（冲突、权限、保护分支）如何处理；
- 最终交付记录是否需要记录合入版本。

### 13. 风险

- 提问占用 Agent 调用，可能被当作免费咨询反复使用；用并发限制而不是轮次限制来约束。
- 驳回统一交给规划者，可能出现“人只是嫌报告啰嗦，却触发一轮规划”的过度反应；由规划者判断为“重写报告”即可，代价是一次规划作业。
- 带缺口接受只写一句理由，可能过于简略；但逐项确认的收益不足以抵消负担。
- 报告历史保留会增加存储与界面复杂度；但丢失历史的代价更大。
- 重新验收与驳回边界可能被混淆：前者不改方案，后者可能改方案；界面文案必须写清。


### H19 人工 → 任务

> 2026-11-07 定稿。本文定义人对单个任务可以做什么、每件事的边界，以及阻塞时人看到什么。
> 上游：H10（验收退回）、H17（续写与暂停）。
> 不在范围：项目级操作（暂停、重规划、报告验收）、规划者对任务的变更（H3）。

### 1. 定位

人工介入只在两种时刻发生：

- 任务停下来等人（阻塞、等待、失败）；
- 任务需要人做最终确认（里程碑）。

除此之外，人工不参与任务的日常推进。

### 2. 人工动作

| 动作 | 语义 | 影响 |
|---|---|---|
| 重试 | 新会话重跑当前任务 | 清空运行时失败计数、错误与冷却；**不重置验收拒绝次数**，不计入任务自动尝试上限；历史保留在事件 |
| 更换 Agent | 指定下一次作业使用某个 Agent | 只影响下一次；不改计数；需要确认风险 |
| 补充指导 | 写入当前指导并重新排队 | 覆盖旧指导；清运行时失败，保留验收拒绝次数 |
| 暂停 | 不再派发该任务的新作业 | 运行中的作业继续；结算纠正仍允许（H17） |
| 恢复 | 重新进入调度 | 从队列恢复 |
| 标记里程碑 | 把任意未完成任务设为里程碑 | 只改变验收方式，不改计划；任务完成前可设置 |
| 里程碑通过 / 拒绝 | 人工二次验收 | 通过则完成并合入；拒绝则退回执行并计入失败次数 |

#### 2.1 动作的边界

- **重试是新的开始，但不是清账**：新会话，不带上次上下文；只清运行时失败与冷却，验收拒绝次数保留（DESIGN §5.1），历史留在事件里；
- **换 Agent 不是重试**：它只改变下一次由谁做，不重置计数，也不保证换人就能成功；
- **补充指导是覆盖，不是追加**：指导只有一份，最新写入生效；旧指导留在事件里，避免过期内容干扰；
- **暂停不等于终止**：暂停管的是新工作，不管结算；已经跑完的结果仍可纠正与结算。

#### 2.2 重试的计数口径

重试不是把所有数字归零，而是换一个新会话继续同一件事。计数与历史分开处理：

| 计数 | 重试是否影响 | 说明 |
|---|---|---|
| 运行时失败计数、冷却、避开标记 | 清零 | 旧会话的进程问题不该跟到新会话 |
| 验收拒绝次数 | 保留 | 交付质量没有因为重试而改变，H10 的三次升级继续有效 |
| 任务自动尝试上限 | 不消耗、不清零 | 该项只统计自动派发；人工重试受项目费用预算约束 |
| 事件与历史 | 保留 | 重试记录追加，不覆盖旧记录 |

已被升级到规划者/父任务或人工裁决的任务，重试不改变已有的拒绝次数，系统继续按升级规则处理。

### 3. 指导

- 任务只有一个“当前指导”字段；
- 人工指导与上级决策给出的指导写进同一个字段，不区分来源；
- 新指导覆盖旧指导；
- 指导随下一次执行进入 prompt，位置在任务描述之后、验收标准之前。

理由：Agent 需要的是“现在该怎么做”，不是一份来源分明的会议记录；来源对它的行动没有影响。

### 4. 阻塞与用户说明

任务阻塞时，人看到的不是原始错误，而是一份说明：

| 字段 | 内容 |
|---|---|
| summary | 一行说明缺什么或需要决定什么 |
| why | 为什么影响交付 |
| owner | 谁来处理 |
| steps | 1–8 个具体操作 |
| after | 处理完后从哪里继续 |
| source | 来源：Agent 或系统 |

规则：

- **Agent 主动等待**时，说明由 Agent 填写；
- **系统级阻塞**（协议纠正失败、配置错误、合入失败、工作区不干净）由 DOMO 生成说明，标注来源为“系统”；
- 系统说明只陈述状态与可选动作，不假装是 Agent 的判断；
- 没有说明的阻塞不允许出现在界面上：宁可生成一份最短说明，也不显示裸错误。

### 5. 里程碑人工验收

- 验收者通过后，任务不立即完成，进入“等待人工验收”；
- 等待期间不派发新作业，也不合入；
- 人工通过：任务完成，按 H11 合入目标分支；
- 人工拒绝：填写原因，任务退回执行，计入验收失败次数；
- 人工验收不做部分通过：要么通过，要么退回。

### 6. 人不能做的事

- **不能直接改任务描述或验收标准**：要改走项目重规划（H3）；
- **不能取消任务**：任务集合由规划者决定；
- **不能跳过验收直接合入**；
- **不能修改已经完成的验收结论**：只能重开任务或重跑。

这些限制保证“任务的来源只有一个”——规划者；人的介入是纠偏，不是改计划。

### 7. 场景推演

| 场景 | 处理 |
|---|---|
| 任务因缺环境阻塞 | 用户看到说明（缺什么、怎么装、装完从哪继续），处理后点继续 |
| 任务连续失败被阻塞 | 说明建议重试或换 Agent；用户选择后任务重新排队 |
| 协议错误一次纠正后仍失败 | 系统生成说明：错误内容 + 建议换 Agent |
| 合入失败 | 系统生成说明：冲突/保护分支/权限，建议处理方式 |
| 用户想改验收标准 | 不允许；提示走重规划 |
| 任务被暂停 | 不再派发；结算纠正仍可进行 |
| 里程碑任务等人 | 显示通过/拒绝两个选择；拒绝需填原因 |
| 用户补了一条指导 | 覆盖旧指导，任务重新排队，只清运行时失败 |

### 8. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| 动作集合 | 保持现状 / 收敛 | **七种**：重试、换 Agent、指导、暂停、恢复、标记里程碑、里程碑验收 |
| 重试是否重置计数 | 全部重置 / 只重置运行时失败 | **只重置运行时失败**：验收拒绝次数是验收侧的判断，人工重试不能把它清零，否则三次升级失效 |
| 指导是否区分来源 | 区分 / 不区分 | **不区分**；Agent 需要“现在怎么做”，不需要来源 |
| 指导追加还是覆盖 | 追加 / 覆盖 | **覆盖**，最新指导生效，避免过期内容干扰 |
| 系统阻塞 | 显示原始错误 / 生成说明 | **生成说明**，标注“系统”，不显示裸错误 |
| 里程碑是否允许部分通过 | 允许 / 不允许 | **不允许**，要么通过要么退回 |

### 9. 决策依据

1. **人工介入是纠偏，不是改计划**：计划只有一个作者（规划者），人工的动作是让任务继续或停下。
2. **指导只需一份**：多份来源不同、时间不同的指导会让 Agent 难以判断哪条优先；最新覆盖最简单。
3. **阻塞必须可行动**：用户不该看到“产物未被 Git 跟踪”这种只有工程师能翻译的错误。
4. **重试只清运行时账**：重试可以让任务重新排队，但不能清零验收拒绝次数；否则人工只要点一次重试就能绕过 H10 的三次升级。

### 10. 影响

- 系统级阻塞需要生成用户说明（新增能力）；
- 指导字段保持单一，不加来源标记；
- 重试沿用“新会话”语义，不复用 H17 的续写；
- 里程碑人工验收的流转补全了 H11 留下的口子。

### 11. 风险

- 系统生成的说明可能过于笼统；要求至少包含“缺什么”和“下一步动作”。
- 覆盖指导会丢失旧内容；旧内容仍在事件里，但不会自动进入 prompt。
- 保留验收拒绝次数后，人工重试可能立刻再次触发升级；这是有意的——升级交给规划者/父任务判断，而不是靠重试绕过。
- 换 Agent 需要确认风险，可能被用户忽略；界面必须说明它会绕过冷却与限额。


## 五、项目合入与版本（H16）

### H16 项目分支 → base 分支

> 2026-11-07 定稿。本文定义项目完成之后，如何把项目分支合入用户指定的 base 分支。
> 上游：H15（人工接受、项目完成）。下游：无（这是项目生命周期的最后一步）。
> 不在范围：项目内部的合入（H11/H12）、归档。

### 1. 定位

合入 base 是**项目之外的附加动作**，不是项目完成的条件：

- 项目在人工接受时就已完成（H15）；
- 合入是用户主动发起的一次发布动作；
- 合入失败不改变项目状态，只影响“是否落地到 base”。

普通工作区没有分支，不参与 H16。

### 2. 前置条件

- 项目已完成（人工已接受报告）；
- 项目工作区没有未提交改动；
- base 分支的工作区（如果被检出）没有未提交改动；
- 没有未恢复的历史合入操作。

任何一条不满足都拒绝合入，并说明原因。不做“自动清理后再合入”。

### 3. 合入流程

1. **用户手动触发**。不自动合入，也不在项目完成时提示“是否立即合入”。
2. **DOMO 执行**：把项目分支 rebase 到 base，然后快进 base。
3. **base 未前进**：等价于纯快进，base 直接指向项目分支 HEAD。
4. **base 已前进**：rebase 会把项目变更重放到最新 base 上。
   - 无冲突 → 继续快进；
   - 有冲突 → DOMO 停止并回滚两边到操作前，把冲突交给 Agent。
5. **Agent 解决冲突**：只在项目分支上工作，基于合入前的 base 产出一个线性提交（不含 merge commit）；不直接改 base。
6. **DOMO 校验 Agent 产物**：基于合入前 base、父链连续、无 merge commit；校验通过后快进 base。
7. **完成**：记录被验收版本、合入版本、base 分支、是否发生过 rebase、是否由 Agent 解决过冲突。

#### 3.1 冲突处理作业的结果

~~~json
{ "kind": "done" }
{ "reason": "无法解决时说明原因" }
~~~

- 不描述细节：解决结果由 DOMO 检查仓库（父链、提交、工作区）判断，不靠 Agent 自述；
- 不写成果、项目记忆或报告；
- 无法解决时给出原因即可，DOMO 取消合入并保留现场。

合入后**不重新验收**。这是明确取舍，见第 4 节。

### 4. 不重验的含义

项目验收验的是项目分支。如果 base 在项目期间前进了，合入的内容是“最新 base + 项目变更”，**和验收过的版本不是同一个东西**。

本方案接受这个差异，理由是：

- 重验代价高，且 base 可能持续变化，重验后仍可能再次前进；
- 合入由人手动触发，人已经知道 base 的状态；
- 真正需要重验的场景，可以走“重新验收”或重开项目，而不是把重验绑在合入上。

代价必须在记录里体现：

- 记录**被验收版本**和**合入版本**两个提交；
- 标注“合入基于更新的 base，未重新验收”；
- 标注“冲突由 Agent 解决”，并记录涉及的冲突文件。

这样事后能回答“上线的东西和验收过的东西差在哪”。

### 5. 失败处理

| 情况 | 处理 |
|---|---|
| base 工作区脏 | 拒绝，要求先清理 |
| 项目工作区脏 | 拒绝，避免回滚覆盖现场 |
| rebase 冲突 | 回滚两边，交给 Agent；Agent 失败则取消合入 |
| 合入期间 base 再次移动 | 取消合入，回滚项目分支，要求重新发起 |
| 快进失败 | 回滚两边 |
| 回滚无法确认 | 记为“恢复未完成”，保存操作前后的引用，阻止再次合入，等人工处理 |

原则：**任何一步失败都恢复到操作前**，不留半合入状态。恢复信息必须可查（操作前 base 与项目分支的提交）。

### 6. 最终交付记录

项目完成时已记录（H15）：被接受的报告、最终分支版本、接受时间、理由、未闭合项。

合入成功后补充：

- 合入版本（base 上的新提交）；
- base 分支名；
- 合入时间；
- 是否发生过 rebase（base 是否前进过）；
- 是否由 Agent 解决过冲突；
- 冲突文件清单（如有）。

项目保持“已完成”状态，合入只是给这条记录补充落地信息。

### 7. 边界

- **合入后 base 又变化**：DOMO 不跟踪。合入是一次性动作，之后 base 的演化不属于项目范围。
- **重复合入**：base 已包含项目分支时，记为“已是最新”，不产生新提交，也不覆盖已有的合入记录。
- **归档**：合入不是归档的前置条件。项目可以已完成但未合入，也可以合入后长期不归档。
- **保护分支 / 权限**：属于环境问题，失败时按第 5 节处理，不做绕过。

### 8. 考虑过的方案

#### 8.1 谁执行合入

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **DOMO 执行 rebase + 快进，Agent 只在冲突时介入** | 有完整的回滚与恢复；Agent 只做它最擅长的冲突判断 | 两段式流程 | **采用** |
| Agent 执行整个合入，DOMO 只校验 | 与“Agent 自己提交”一致 | 失败时可能留下半完成状态，难以回滚 | 未采用 |

#### 8.2 base 前进时是否重验

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 重验后再合入 | 上线的就是验过的 | 代价高；base 可能持续变化 | 未采用 |
| 分级：无冲突提示、有冲突重验 | 折中 | 仍要在合入流程里插入重验 | 未采用 |
| **不重验，只记录差异** | 流程简单；责任在发起合入的人 | 上线内容可能未被验收 | **采用** |

#### 8.3 合入形态

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **rebase + 快进** | base 历史线性；保留每个任务的 squash 提交 | 需要 rebase，可能冲突 | **采用** |
| merge commit | 不重写历史 | base 出现非线性历史 | 未采用 |
| 压成一个项目提交 | base 很干净 | 丢失任务粒度 | 未采用 |

#### 8.4 冲突处理

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 人工在本地解决 | 人可控 | 脱离开 DOMO 流程，状态不可追踪 | 未采用 |
| **Agent 解决，DOMO 校验产物** | 可追踪；有固定校验 | 解决结果未被验收 | **采用** |
| Agent 解决后重验 | 更安全 | 与“不重验”的决定矛盾 | 未采用 |

### 9. 决策依据

1. **合入是附加动作**：项目已完成，合入失败不应该把项目改回未完成。
2. **DOMO 负责机械操作，Agent 负责判断**：rebase/快进有明确的失败点和回滚要求，适合 DOMO；冲突是语义判断，适合 Agent。
3. **不重验是明确取舍**：把成本压在一次人工触发的合入上，而不是每次 base 变化都重跑项目验收。
4. **记录必须诚实**：验收版本与合入版本不同、冲突由 Agent 解决，这两件事必须在记录里可见，否则记录会误导人。
5. **失败必须可恢复**：合入是唯一会改用户 base 的动作，任何半完成状态都不可接受。

### 10. 风险

- 上线内容未重新验收：由发起合入的人承担；记录里标注差异，但不阻止。
- Agent 解决冲突可能引入错误：无重验，只能靠记录和事后发现；冲突文件清单至少让人知道改了哪里。
- base 在合入期间被他人改动：会被检测并取消，但需要用户重新发起。
- 回滚无法确认时会阻止后续合入：这是有意的保守策略，需要人工介入。
- 合入与项目状态解耦：可能出现“项目已完成但从未合入”的长期状态，需要界面能看出来。

### 11. 与前面环节的关系

- H15：项目完成与最终交付记录；H16 只补充合入信息。
- H11/H12：任务级合入是另一层，任务是 squash 到项目/父任务分支，与 base 无关。
- H14：项目验收验的是项目分支，不是 base；H16 的 rebase 不改变这一点，差异由记录表达。


## 六、续写、失败与资源（H17、H18、H20）

### H17 作业会话 → 续写 / 恢复

> 2026-11-07 定稿。本文定义作业被中断或结果不可用时，如何继续：用同一会话还是新会话、预算多少、提示说什么。
> 上游：H7（结果契约）、H8（结算与一次纠正）。
> 不在范围：失败后的换 Agent 与调度重试（H20）。

### 1. 定位

续写是"接着干活"，不是"重新开始"。它要解决四类情况：

- 进程被中断（超时、崩溃、被杀）；
- 结果文件缺失或无法解析；
- 结果内容不符合协议（H8 只给一次纠正）；
- 会话不可用（供应商不支持恢复或会话丢失）。

### 2. 现状与问题

| 场景 | 现在怎么做 | 问题 |
|---|---|---|
| 运行中断 | 同会话续写 | 预算与其他场景混用 |
| 结果缺失/不可解析 | 继续提示，最多 5 轮 | 与内容纠正共用预算，且属于适配层问题 |
| 内容不合规 | 继续提示，最多 5 轮 | 与 H8 的"只纠正一次"冲突 |
| 项目暂停 | 禁止续写 | 把"暂停"误当成"不许结算"，T31 因此作废 |
| 会话不可用 | 按失败处理 | 重建作业、重跑任务，成本高 |
| 进程正常退出但结果无效 | 不认为可续写 | 内容错误往往就是正常退出，导致无法纠正 |

### 3. 预算：三类分开

| 场景 | 会话 | 预算 | 说明 |
|---|---|---|---|
| 运行中断 | 同一会话 | 2 次 | 保留上下文；提示先检查现场 |
| 结果缺失或无法解析 | 同一会话 | 2 次 | 适配层问题，只要求写结果 |
| 内容不合规 | 同一会话 | 1 次 | H8 的一次纠正 |
| 会话不可用 | 新会话 | 1 次 | 完整 prompt + 检查现场 |

预算按作业累计，不因重启重置；换新作业才重新计算。三类互不占用。

### 4. 能否续写不再看"进程是否异常"

现在的规则是"只有进程异常退出才算可续写"。但内容不合规通常发生在进程正常退出之后，于是最需要纠正的情况反而不能续写。

新规则：**能否续写只看该类预算是否还有剩余**，与进程是否异常退出无关。

### 5. 暂停与结算

暂停表示"不要再开新工作"，不表示"不许结算"。

- 暂停中仍允许**一次结算纠正**：补写结果、修正协议字段；
- 但不再开始新的执行轮次或新任务；
- 纠正完成后正常结算，项目保持暂停状态。

理由：已经跑完的工作不应该因为人工按了暂停而作废。

### 6. 续写提示说什么

原则：**同会话只补它不知道的事；新会话才补它没看过的事。**

| 场景 | 提示内容 |
|---|---|
| 运行中断 | 上次被中断；先检查工作区现场；继续未完成部分；写结果 |
| 结果缺失/不可解析 | 具体缺什么（文件不存在、非法 JSON、缺字段）；只修结果 |
| 内容不合规 | 具体错误（字段、期望、实际）；只修结果与工作区，不重做任务 |
| 会话不可用 | 完整任务与验收标准；上次被中断；先检查现场；结果协议 |

不说的东西：

- 中断的**分类**（超时、崩溃、被杀、限流）——对 Agent 没有行动价值，只记入日志与事件；
- 重复的任务描述——同会话里已经有了；
- 历史轮次与次数——除非它是本次要修的问题。

### 7. 恢复后的事实来源

- 工作区是唯一事实：分支、提交、未提交改动、已生成的文件；
- 不假设"上次做到哪一步"可以从会话记忆推断；
- 提示必须要求先检查现场，再决定继续什么；
- 结果文件每次重新写入，旧内容不保留为可用结果。

### 8. 会话不可用

两种原因：供应商不支持恢复、会话过期或丢失。

处理：用原 prompt 起一个新会话，明确"上次被中断，先检查现场"，预算 1 次。仍失败则按失败处理，走调度重试（H20）。

不直接失败的理由：工作区、提交和任务说明都在，多数情况能接上；重建作业重跑整任务是更贵的选择。

### 9. 与 H8 的关系

- H8 的"内容协议错误只纠正一次"由本文的预算执行；
- H8 的"结果缺失属于适配层"由本文的 2 次预算执行，不占任务层额度；
- 纠正成功后正常进入 H8 的结算流程；
- 纠正失败后按 H8 的分类处理：内容错误阻塞并建议换 Agent，适配失败按失败处理。

### 10. 场景推演

| 场景 | 结果 |
|---|---|
| 跑到一半超时 | 同会话续写，检查现场，继续 |
| 进程崩溃、无结果 | 同会话续写，要求补写结果 |
| 正常结束但结果 JSON 非法 | 同会话纠正，指出具体错误 |
| 正常结束但结果字段不合规 | 同会话纠正一次；仍错则阻塞并建议换 Agent |
| 项目暂停中结果不合规 | 允许一次结算纠正，之后保持暂停 |
| 会话过期 | 新会话，完整 prompt，检查现场 |
| 新会话也失败 | 按失败处理，走调度重试 |

### 11. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| 预算 | 统一 5 轮 / 按场景分开 | **分开**：中断 2、结果缺失 2、内容不合规 1 |
| 续写资格 | 看进程是否异常 / 看预算 | **看预算**，否则正常退出的内容错误无法纠正 |
| 暂停时 | 一律禁止 / 允许结算纠正 | **允许一次**，避免作废已完成工作 |
| 会话不可用 | 直接失败 / 新会话接续 | **新会话接续**，成本更低 |
| 提示内容 | 完整重述任务 / 只补不知道的 | **只补不知道的**；新会话才给完整任务 |
| 中断原因 | 写进提示 / 只记日志 | **只记日志**，对 Agent 无行动价值 |

### 12. 决策依据

1. **续写是接着干**：重复任务描述只会浪费上下文，甚至让它重做已完成部分。
2. **错误要具体**：纠正的前提是知道错在哪，含糊提示等于浪费唯一一次机会。
3. **中断分类对 Agent 无用**：超时和崩溃的处理方式相同，都是"检查现场继续"。
4. **暂停不是终止**：暂停管的是新工作，不管结算。
5. **新会话是最后手段**：成本高于续写，但低于重跑整任务。

### 13. 影响

- 续写资格不再依赖"进程异常退出"；
- 预算从统一的 5 轮拆为 2 / 2 / 1；
- 暂停中允许一次结算纠正；
- 会话不可用时改为新会话接续，而不是直接失败；
- 结果校验中与 failed 相关的判断需要删除（H4 已移除该类型）。

### 14. 风险

- 续写提示过短，Agent 可能误以为任务已完成；提示必须明确"继续未完成部分并写结果"。
- 新会话接续可能重复已完成工作；提示必须要求先检查现场。
- 暂停中允许纠正，可能被理解为"暂停无效"；界面需说明这是结算不是新工作。
- 预算按作业累计，长时间作业可能用完预算；这是有意限制，避免无限纠正。


### H18 项目 / 任务资源 → 作业

> 2026-11-07 定稿。本文定义执行所需的工具、依赖、缓存与输入放在哪里、如何交接、何时可以删除。
> 上游：H6（执行上下文）。下游：所有执行与验收作业。
> 不在范围：成果发布（H11）、共享记录（H8）。

### 1. 原始设计目标

资源目录最初要解决三件事：

1. **把运行条件从交付物里分出来**：工具链、依赖、数据输入、缓存不能进仓库，但每次重做成本很高；
2. **按复用范围分层**：一次性输出、任务内复用、跨任务复用，各自有位置；
3. **让后来者知道有什么可复用**：准备资源的人要说明用途、路径、版本、用法与限制。

前两条仍然成立；第三条因为共享记录被压缩（H7：≤5 条 ×120 字）而失效，需要换载体。

### 2. 三层空间

| 位置 | 生命周期 | 典型内容 |
|---|---|---|
| 作业目录 | 只此一轮 | 日志、临时输出、构建产物、截图 |
| 任务资源 | 同一任务内跨作业（执行 → 验收 → 返工） | 测试夹具、任务专用输入 |
| 项目资源 | 跨任务 | 工具链、共享依赖、公共语料 |

三者的边界不是按内容类型，而是按**复用范围**：只此一轮的绝不放进资源，能跨任务的不要只放任务资源。

资源目录独立于源码工作树，不随任务提交或合入；普通工作区与 Git 工作区都一样。任务资源与项目资源放在工作区外或 DOMO 管理目录，普通工作区不写入用户目录。

### 3. 资源不是成果

| 维度 | 资源 | 成果 |
|---|---|---|
| 本质 | 运行条件 | 交付内容 |
| 能否重建 | 多数可以 | 不可替代 |
| 位置 | 工作区外或 DOMO 管理目录，不进仓库 | 仓库内，随任务提交 |
| 数量 | 无上限 | 每任务 ≤4 |
| 生命周期 | 可删除，项目归档时清理 | 任务通过后发布，长期保留 |
| 谁看 | Agent | 人 + 下游 Agent |
| 是否参与验收 | 否 | 要做一致性检查 |

一句话：**成果是“交付了什么”，资源是“用什么做的”。**

由此得到一条硬规则：**重建成本高的内容不能只放在资源目录**。如果一个工具或数据丢了就再也做不出来，它必须作为成果提交到仓库，或者写清来源与获取方式。

### 4. 交接方式

两件东西，各管一半：

| 载体 | 内容 | 谁维护 |
|---|---|---|
| 资源目录内的 README | 是什么、版本、来源、怎么用、有什么限制 | 放资源的人 |
| 项目记忆一行（≤120 字） | “有什么、在哪”，负责被看见 | 放资源的人 |

例如：

- 目录内 README 写清 ffmpeg 6.1 的来源、安装方式、路径与环境变量；
- 项目记忆写一句“ffmpeg 6.1 在项目资源 ffmpeg-6.1/，用法见目录内 README”。

不引入清单格式、不做校验、不要求每条资源都有 README：没有 README 的资源仍然可用，只是不容易被发现。

### 5. 版本与命名

- 新版本用新目录（ffmpeg-6.1/、ffmpeg-7.0/），便于并存；
- 不引入版本元数据，目录名就是版本；
- 并存不承诺永久保留，旧版本可以删除。

### 6. 可删除与生命周期

资源是**可重建的运行条件**，因此：

- 可以删除旧版本、过期缓存、不再使用的工具链；
- 删除前由操作者确认没有进行中的任务依赖它；不做引用计数；
- 不自动回收单个文件：没有引用关系时，自动删比不删更危险；
- 项目归档时，只清理 DOMO 管理的资源目录；普通工作区不删除用户目录中的文件。

### 7. 权限

- 执行者可以在项目资源与当前任务资源内准备、更新、删除；
- 验收者与其他角色只读；
- 跨任务共享的内容使用独立名称，避免覆盖其他任务正在使用的资源。

### 8. 场景推演

| 场景 | 处理 |
|---|---|
| 安装了一个工具链供后续任务用 | 放项目资源，新目录名带版本，写 README，发一行项目记忆 |
| 生成了只在本轮用的测试日志 | 放作业目录，不登记 |
| 生成了本任务验收要复核的夹具 | 放任务资源 |
| 同一工具需要两个版本 | 两个目录并存；确认无人使用后可删旧版 |
| 资源损坏或丢失 | 按 README 重建；重建不了说明它本不该只做资源 |
| 项目归档 | 只清理 DOMO 管理目录 |
| 资源没有 README | 仍可使用，但发现成本高；不是错误 |

### 9. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| 是否保留资源目录 | 保留 / 取消 | **保留**：工具与依赖不能进仓库，也不能每次重做 |
| 交接载体 | 共享记录写全 / README + 一行记录 / 不交接 | **README + 一行记录**；共享记录写不下，完全不交接则无法发现 |
| 版本 | 元数据 / 目录命名 | **目录命名**，不引入格式 |
| 生命周期 | 永不删除 / 可删可重建 | **可删可重建**，避免无限增长 |
| 自动回收 | 做 / 不做 | **不做**：没有引用计数，误删风险高于收益 |
| 高价值内容 | 放资源 / 进仓库 | **进仓库**：资源目录不承诺长期保留 |

### 10. 决策依据

1. **资源是可重建的运行条件**：它的价值在于省时间，不在于留痕；丢了可以再做。
2. **成果是不可替代的交付**：所以才要发布、留痕、做一致性检查。
3. **无人维护的清单等于没有清单**：README 由放资源的人顺手写，成本最低。
4. **不自动回收**：没有引用关系时，自动删除无法判断谁还在用。
5. **归档即清理**：项目的生命周期结束，运行条件没有保留价值。

### 11. 风险

- README 可能缺失或过期；资源仍可用，但发现成本上升。
- 旧版本被删时可能仍有任务依赖；由操作者判断，提示词要求删除前确认。
- 资源目录可能被误用为交付存放地；硬规则是“重建成本高的必须进仓库”。
- 项目进行中资源可能持续增长；由人清理，没有自动上限。
- 资源里不应存放凭据或密钥；需要凭据时由用户提供运行环境，不写入资源目录。


### H20 作业失败 → 换 Agent / 重试

> 2026-11-07 定稿。本文定义作业失败后系统自动做什么：如何分类、换不换 Agent、要不要停。
> 上游：H17（同作业续写）、H8（协议纠正）。下游：H19（人工介入）。
> 不在范围：人工点重试（H19）、业务质量（由验收判断，H10）。

### 1. 定位

作业失败分两种：

- **同一次作业内还能继续**：中断、结果缺失、内容不合规 → H17 续写，不新建作业；
- **作业已经结束**：运行时失败 → 本文处理，新建作业重试。

失败**不包含**“做得不好”：质量由验收判断（H10），执行者不报失败（H4）。

### 2. 失败分类

| 类型 | 典型情况 |
|---|---|
| 限流 | 429、配额用尽、请求过多 |
| 瞬时 | 超时、卡死、进程崩溃、5xx、网络中断 |
| 永久 | 认证失败、密钥无效、配置不可用 |
| 协议/适配 | 结果缺失、无法解析、结果不合规（预算见 H17） |
| 配置 | 角色池为空、全部禁用、角色不匹配 |
| 系统 | 数据库、Git、文件系统等 DOMO 自身错误 |

分类只看错误事实，不看 Agent 自述。

### 3. 每类的策略

| 类型 | Agent 侧 | 任务侧 | 是否停 |
|---|---|---|---|
| 限流 | 按 retry_after 冷却；避开该 Agent | 不计失败次数 | 不停，等冷却 |
| 瞬时 | 继续重试；连续 3 次后冷却 30 分钟并避开该 Agent | 不计失败次数 | 不停 |
| 永久 | 立即避开该 Agent | 不计失败次数 | 同角色池没有其他可用 Agent 时停 |
| 协议/适配 | 不惩罚 Agent | 按 H17 的预算处理 | 预算用尽后停 |
| 配置 | — | — | 立即停；配置变化后自动恢复 |
| 系统 | — | — | 立即停，交人工 |

#### 3.1 为什么没有“失败次数上限”

停止任务只有一个条件：**没有可用 Agent**。

- 限流、永久错误：立即排除该 Agent；
- 瞬时错误：连续 3 次后排除该 Agent，前两次原 Agent 重试；
- 同池被排除到没有可用 Agent 时，任务停在“没有可用 Agent”，由人换池或加 Agent；
- 基础设施问题等待比失败更合理，加硬上限只会把可恢复的问题变成需要人工重开的任务。

因此“连续失败次数”只用于决定**是否换 Agent**，不用于决定**是否停止任务**。人工重试不消耗任务自动尝试上限，也不重置验收拒绝次数（H19）；它的成本由项目费用预算约束。

#### 3.2 为什么限流不计数

限流是资源约束，不是 Agent 或任务的问题。冷却后重试是对的；如果计入上限，一次供应商抽风就会把任务打死。

#### 3.3 为什么系统错误立即停

数据库、Git、文件系统出错不是 Agent 能解决的，重试只会重复同样的错误。停住并让人看到具体错误，比循环重试更快恢复。

### 4. Agent 选择

- 同角色池内选择，不跨角色；
- 避开最近一次失败的 Agent；
- 遵守冷却、可用时段、周期限额、并发上限；
- 人工指定的 Agent 只影响下一次作业（H19）。

### 5. 现场与提交

- 失败作业已经产生的提交保留在任务分支上（H7 append-only），重试继续叠加，不回滚；
- 工作区的未提交改动保留；
- 重试的提示要求先检查现场，避免重复已完成的工作（H6/H17）。

### 6. 与相邻环节的边界

| 情况 | 归属 |
|---|---|
| 同作业内中断、结果缺失、内容不合规 | H17 |
| 作业结束后运行时失败 | H20 |
| 协议预算用尽 | H8 → H19（人工） |
| 用户手动重试 | H19（新会话、重置计数） |
| 质量不达标 | H10（验收退回） |

### 7. 用户看到什么

- 失败分类与摘要，而不是原始日志；
- 已避开哪些 Agent、当前在等什么（冷却、无可用 Agent、预算）；
- 需要人工时给出可选动作：重试、换 Agent、调整池或预算（H19）。

### 8. 场景推演

| 场景 | 处理 |
|---|---|
| 429 限流 | 冷却该 Agent，换下一个；任务继续排队 |
| 作业超时 | 原 Agent 重试；连续 3 次后冷却并换人 |
| 进程崩溃、无结果 | 按瞬时处理 |
| 密钥失效 | 避开该 Agent；同池没有其他 Agent 则阻塞；用户修配置后自动恢复 |
| 角色池为空 | 立即阻塞，配置变化后自动恢复 |
| 数据库写入失败 | 立即阻塞，展示具体错误 |
| 协议错误纠正失败 | 阻塞，建议换 Agent（H8/H19） |
| 重试后又失败 | 继续避开失败的 Agent；没有可用 Agent 时停 |

### 9. 考虑过的方案

| 问题 | 方案 | 结论 |
|---|---|---|
| 是否设次数上限 | 设 / 不设 | **不设**：避开 Agent 已构成上限；基础设施问题等待优于失败 |
| 限流是否计数 | 计数 / 不计数 | **不计数**，冷却即可 |
| 瞬时失败是否换人 | 立即 / 连续 3 次后 | **连续 3 次后**，避免一次抖动就换掉最合适的 Agent |
| 永久失败 | 重试 / 避开 | **避开**；无可用则停 |
| 协议失败 | 自动重试 / 预算后停 | **预算后停** |
| 系统错误 | 重试 / 立即停 | **立即停** |
| 业务失败 | 保留 failed / 删除 | **删除**（H4），质量由验收判断 |

### 10. 决策依据

1. **失败要分类处理**：限流该等，配置该停，系统错误该报；一刀切重试会放大问题。
2. **避开 Agent 就是上限**：不需要额外计数，池子用尽自然会停。
3. **等待优于失败**：基础设施问题多数会自愈，把任务打死反而需要人工重开。
4. **协议错误已有独立预算**：再叠一层计数会让两套规则互相干扰。
5. **系统错误不重试**：重复执行同一个坏操作不会变好。

### 11. 影响

- 删除“任务失败”类型（H4 已删除 failed）；
- 连续失败次数只用于决定是否换 Agent，不用于停止任务；
- 项目仍可配置执行尝试上限与费用预算，但它们属于成本控制，不属于失败策略；
- 系统错误成为独立分类，需要生成用户说明（H19）。

### 12. 风险

- 没有次数上限，持续的瞬时失败可能消耗大量调用；由冷却、避开与费用预算兜底。
- 避开 Agent 的逻辑依赖池的大小；池里只有一个 Agent 时，瞬时失败会一直重试它。
- 系统错误若被误分类为瞬时，会进入重试循环；分类必须保守，拿不准就按系统错误停。
- 失败摘要可能掩盖细节；原始错误仍保留在作业记录中。

#### 2026-11-07：H15 人工验收

- **发现**：人无法判断“报告写得对不对”，报告是描述，不是判断对象；人判断的是交付结果是否符合预期。
- **决策**：取消“重写报告 / 重新规划”两种人工驳回，人只表达接受或不接受，由规划者解释反馈。
- **决策**：人工动作四个：接受、重新验收、驳回、提问；带缺口接受是接受的特例（必填理由）。
- **决策**：提问窗口只回答、不改状态、不改报告，多轮；接受或驳回后关闭。
- **决策**：被驳回/被替换的报告保留只读历史；每轮意见与问答进入项目历史。
- **决策**：项目完成时记录最终交付（报告、最终分支版本、接受时间、理由、未闭合项）。

- **决策**：合入由用户手动触发，不自动执行；合入失败不改变项目完成状态。

- **决策**：冲突处理只走 Agent，不由人工在本地解决；冲突文件与处理情况进入记录。
- **决策**：合入形态为 rebase + 快进，保留任务级 squash 提交，不产生 merge commit。

- **发现**：现有契约把只读目录等约束写进了 assumptions，说明缺少约束的独立位置。

#### 2026-11-07：H3 任务记录

- **决策**：key 在项目内终身唯一，取消任务不释放；新任务从最大编号之后继续；派生任务用父 key 加点号。
- **决策**：取消现状的“静默重编号”。编号规则写进提示词；真冲突视为规划者失误，自动纠正一次，仍冲突则阻塞并建议更换规划者（同 H8 的一次纠正思路）。
- **决策**：验收标准为空不再填默认值，直接拒绝。
- **决策**：移除人工添加任务；项目计划只有一个作者——规划者。执行者的 derive 属于任务内部拆分，不算计划变更。
- **决策**：项目完成后不能加任务，新需求开新项目；“重开项目”另议。
- **影响**：删除人工加任务入口；分析提示词给出已用 key 列表；落库校验增加 key 全局唯一与验收非空。

#### 2026-11-07：H4 上级决策

- **决策**：删除 failed。执行者只有 done / derive / replan 三种结果；质量由验收判断，执行者不做自我判决。
- **决策**：replan 只带原因与任务 key/标题；上级额外看到上一轮的请求、决策与指导，不注入完整历史与尝试次数。
- **决策**：子任务必须先给父任务，不允许跳过；顶层任务给规划者。
- **决策**：三种决策保留：继续（给指导）/ 等待（等人提供条件或决定）/ 替换方案。
- **决策**：父任务方案直接应用；项目方案按项目确认方式（自动直接、人工等待）。
- **决策**：不设请求次数阈值；是否重复上报、是否交人，由上级判断。
- **影响**：H7 删除 failed 类型；H8 删除业务失败分支；运行时失败仍由系统观测与调度重试。

#### 2026-11-07：H17 续写与恢复

- **决策**：预算按场景分开：运行中断 2 次、结果缺失/不可解析 2 次、内容不合规 1 次；互不占用、按作业累计。
- **决策**：能否续写不再看“进程是否异常退出”，只看该类预算是否还有剩余——否则正常退出的内容错误反而无法纠正。
- **决策**：暂停中允许一次结算纠正（补写结果、修正字段），但不开新工作。
- **决策**：会话不可用时用原 prompt 起新会话接续一次，而不是直接失败。
- **决策**：续写提示只补“它不知道的事”：中断只说事实与“先检查现场”，协议错误说具体字段；中断分类只记日志，对 Agent 没有行动价值。
- **影响**：结果校验中与 failed 相关的判断需删除（H4 已移除该类型）。

#### 2026-11-07：H18 资源

- **发现**：资源最初的设计目标是把运行条件从交付物中分出、按复用范围分层、由准备者交接；第三条因共享记录被压缩（H7）而失效。
- **决策**：三层空间不变：作业目录（一次性）、任务资源（同任务复用）、项目资源（跨任务复用）。
- **决策**：资源是可重建的运行条件，可以删除与覆盖；不承诺长期保留；项目归档时随工作区清理。
- **决策**：交接用目录内 README（内容）+ 共享记录一行（发现）；不做清单格式与校验。
- **决策**：版本靠目录命名，不引入元数据；不自动回收，删除前由操作者确认无任务依赖。
- **决策**：重建成本高的内容必须进仓库作为成果，不能只放资源目录。

#### 2026-11-07：H19 人工介入

- **决策**：人工动作收敛为六种：重试、换 Agent、补充指导、暂停、恢复、里程碑验收。
- **决策**：重试是新会话，重置尝试与拒绝次数，历史保留在事件。
- **决策**：指导只有一份，人工与上级写同一字段，不区分来源；新指导覆盖旧指导。
- **决策**：所有阻塞都要有用户说明（缺什么、影响、谁处理、步骤、如何继续）；系统级阻塞由 DOMO 生成并标注来源为“系统”，不显示裸错误。
- **决策**：里程碑人工验收不允许部分通过；通过则完成并入分支，拒绝则退回执行并计入失败次数。
- **决策**：人不能直接改任务描述或验收标准、不能取消任务、不能跳过验收合入。

#### 2026-11-07：H20 失败重试

- **决策**：失败分为六类：限流、瞬时、永久、协议、配置、系统错误。
- **决策**：不设次数上限——“避开的 Agent 不再被选中”本身构成上限；池子用尽自然停。
- **决策**：限流不计数，只按 retry_after 冷却并换人；瞬时连续 3 次后冷却 30 分钟并换人。
- **决策**：永久错误立即避开该 Agent；同池无可用 Agent 时停。
- **决策**：协议错误沿用 H8/H17 预算，不另设计数；系统错误立即阻塞交人工。
- **决策**：连续失败次数只用于展示，不驱动策略。
- **影响**：删除“任务失败”类型（H4 已删 failed）；项目仍可配置执行尝试上限与费用预算，但属于成本控制。

#### 2026-11-07：H11 发布与合入

- **决策**：落地后发布；记忆先、成果后；子任务知识先走，成果等父任务落地；缺失成果不能跳过，父任务显式退役或验收失败；任务一条最终交付记录；落地后不做集成验证；普通工作区同样等父任务完成。
- **待定**：里程碑人工验收的细节。


## 八、2026-11-08 实现修订与最终结论

> 本章不是讨论原文，而是按当前代码、DESIGN 与 TECH 回填的最终口径。前七章与本章冲突时，以本章为准。

### 8.1 最终方案相对 2026-11-07 定稿的变化

| 主题 | 2026-11-07 定稿 | 2026-11-08 最终口径 | 原因 |
|---|---|---|---|
| 人工阻塞说明 | H19 要求独立 `user_action`（summary/why/owner/steps/after） | 删除独立字段；用阻塞摘要、`reason`、`issues`、`guidance` 表达 | 一套字段跨任务/项目/审批三种场景，投影和校验成本高；人工在页面上需要的是“哪里卡住、要做什么”，不是固定五段式 |
| 人工动作数量 | 六种：重试、换 Agent、指导、暂停、恢复、里程碑验收 | 七种：增加“标记里程碑” | 标记是任务属性调整，不是验收；与“里程碑验收”分开 |
| 重试是否清账 | 原文一处写“重置尝试与拒绝次数” | 只清运行时失败、错误与冷却；不重置验收拒绝次数 | 拒绝次数是验收侧判断，重试不应让人绕过 3 次升级阈值 |
| 成果顺序 | “≤4 条，顺序即优先级” | ≤4 条，接口按路径稳定排序；顺序不承载产品语义 | 用户从未能控制顺序，前端也不允许拖拽；承诺优先级却无法执行，是假承诺 |
| 成果类型 | input/intermediate/delivery 三类 | 只有一种成果；参考输入不登记 | 实际数据几乎全是 intermediate，类型无分类价值 |
| 项目记忆 | 5k 全量，超限目录；目录含主题/范围 | 5k 全量；超限只给编号、来源任务、`records/<id>.json` 索引 | 主题/范围是 Agent 猜的；编号和路径是确定事实 |
| 协议纠错 | H17 已定 2/2/1；旧 TECH 仍写 5 轮 | 中断 2、缺失/不可解析 2、内容不合规 1，互不占用 | 统一“5 轮”会把不同失败的纠正空间混在一起 |
| 项目验收 | H14 两态 deliver/execute；旧实现仍有 criteria/next_action | deliver 可带 issues + report；execute 必带 issues + plan；无 criteria | criteria 与人工最终判断重复，且会产生“met 但 replan”的矛盾 |
| 人工驳回 | 旧 UI 提供“重新撰写 / 要求重新规划” | 只表达接受/不接受；驳回后规划者返回报告或完整方案 | 人判断交付，不判断报告；报告怎么改是规划者的职责 |
| 带缺口接受 | 原文已定必填理由，实现未落地 | 服务端强制理由；理由和 issues 进入最终交付记录 | 留痕，但不要求逐项确认 |
| 人工加任务 | H3 已定移除，代码/UI 仍有入口 | 删除接口、表单、草稿、测试；完成项目不能追加任务 | 计划唯一作者；完成后加任务会破坏已验收的交付边界 |
| 任务 key | 终身唯一，取消不释放 | 数据库唯一约束改为 `(project_id, key)` 全量唯一；不再只约束活跃任务 | 取消后复用会让历史引用指错任务 |
| 合入记录 | 目标分支、时间、项目提交 | 增加被验收版本、合入版本、是否 rebase、是否 Agent 解决冲突、冲突文件 | 合入后不重验，必须能看出“验的版本”和“上线的版本”差异 |
| 用量维度 | 项目/Agent/角色 | 增加按任务、按模型 | 任务成本和模型选择是实际排障入口 |
| Agent 命名 | WorkBuddy | CodeBuddy（类型、文件、UI、测试统一） | 外部产品名统一，避免两套标识 |
| 数据库 | 文档写 rusqlite | SQLite（通过 sqlx） | 实现栈与文档一致 |

### 8.3 机械校验、提示词与人工的分工

**机械校验（代码/数据库/API）**

- 方案：DAG 无环、依赖存在、任务验收非空、key 全量唯一；确认方案必须与当前草稿一致。
- 结果：角色—结果类型匹配；executor 无 failed；verifier 的 pass 不得带 issues，execute/request 至少一条 issues；项目验收 deliver/execute 互斥，deliver 必带 report，execute 必带 plan。
- Git：作业前后 ref 快照；除当前任务分支外其他 ref/config/hooks/worktree 元数据不得变；提交只追加；只允许冲突解决 merge commit；提交身份固定；工作区干净；diff 范围排除忽略路径与越界文件。
- 合入：目标分支干净；任务分支 squash；冲突额度；失败恢复操作前引用；恢复失败阻止再次合入。
- 发布：任务完成才发布；记忆先、成果后；子任务成果等父任务；发布失败任务不完成。
- 续写：三类预算独立计数；暂停结算纠正只一次；会话不可用只起一次新会话。
- 人工：报告带未闭合项接受必须填理由；里程碑验收只能通过/拒绝；重试不清拒绝次数。

**提示词（Agent 判断）**

- 全量复核验收标准，而不是只查上一轮 issues。
- 项目验收报告必须包含「验收执行记录」，逐条写检查对象、范围、方法、实际结果与证据位置。
- 共享记录提交前问三个问题：下游需要吗、是否只对本任务成立、是否已有记录可替代。
- 资源目录交接写 README，项目记忆只写一行发现。
- 合入冲突解决只修冲突，不扩大范围，不借机重构。

**人工（产品兜底）**

- 报告是否真的检查过、证据是否可信。
- 子任务成果退役理由是否成立。
- 接受带缺口时的理由是否可接受。
- 重规划草稿是否值得确认。

### 8.4 仍需注意的取舍

1. **项目验收没有 criteria 账本**：系统不核对报告是否覆盖每条验收标准；漏项只能靠报告撰写要求和人工阅读。这是为了提高交付速度、避免第二套评审协议而接受的代价。
2. **任务 evidence 仍是硬约束**：任务级验收需要逐条证据；项目级没有同等账本。两者不对称是有意的：任务验收是自动闸门，项目验收是人工判决。
3. **合入后不重新验收**：base 前进后只记录版本差异；如果 base 的变化与项目改动冲突，由合入时的 rebase 和人工发起合入的人承担。
4. **冲突额度用尽交上级，不自动换人**：上级可能判断继续补工作，也可能再冲突；系统不设无限自动循环，但也不保证一次就能解决。
5. **资源目录不自动回收**：长期项目需要人工清理；重建成本高的内容必须作为成果提交。
6. **提示词依赖模型能力**：报告质量、共享记录取舍、冲突范围控制都无法完全机械化；机械校验只能保证边界，不能保证判断质量。
