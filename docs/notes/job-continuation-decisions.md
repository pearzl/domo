# 作业继续、错误分类与会话恢复：设计取舍与决策依据

> 性质：设计决策记录，保存方案演进、已确认边界与后续实现依据，不是运行日志或发布记录。
>
> 状态：最终决策已确认。本文保留被否决方案的分析依据；当前实现与接口以 `DESIGN.md`、`TECH.md` 及适配层说明为准。理想分类精度与诊断字段的扩展方向不代表供应商总能提供足够证据。

## 1. 讨论范围与背景

DOMO 的作业可能因为进程、网络、供应商、会话、结果协议或任务本身的问题结束。把这些情况都称为“重试”，会混合三种不同操作：恢复原会话、创建新会话重新执行，以及解除暂停或派发限制。

本文集中回答：

- 哪些结束原因适合原会话继续，哪些应进入新会话或业务处理流程；
- 自动继续与人工继续为什么不能使用同样严格的错误分类门槛；
- Git 与普通工作区为什么不应采用不同的会话继续语义；
- Agent 适配层如何统一各 CLI 的结构化错误，以及统一抽象仍无法消除的识别局限；
- 如何避免错误分类、恢复尝试和费用统计中的误判。

本文仅记录作业继续、错误分类与会话恢复的设计取舍。相关业务规则参见 [DESIGN.md](../DESIGN.md)，实现说明参见 [TECH.md](../TECH.md)。

讨论对象是 DOMO 自身行为。具体项目的 SDK、路径、环境缺项、业务失败和运行数据不能直接上升为系统规则；测试使用隔离夹具，不以修改实际项目数据验证设计。

## 2. 操作语义

| 操作 | 含义 | 会话语义 |
| --- | --- | --- |
| 继续 | 上次工作结束后，尝试接续原会话完成原工作 | 明确恢复原会话，不静默另开会话 |
| 新会话执行 | 创建新的执行上下文，检查现有现场后开展工作 | 新会话；可以仍使用同一个 Agent |
| 指导后执行 | 人工补充工作指导后重新开展执行 | 按独立指导入口使用新会话 |
| 更换 Agent | 交由另一个执行主体处理 | 新会话，不冒充原会话继续 |
| 恢复项目或任务 | 解除暂停等派发限制 | 不单独决定复用还是新建会话 |
| 自动协议修正 | 作业内要求补齐或修正角色结果协议 | 有限纠错流程，不是人工解除阻塞的“继续” |
| 恢复结果结算 | 收集并应用已经有效产出的结果 | 不要求模型重复执行已经完成的工作 |

新会话不等于新工作区，也不等于重置文件或提交。已有文件、提交和最新反馈应作为现场交给执行者检查。反过来，继续原会话也不承诺所有命令都从精确断点恢复；Agent 需要判断上一轮已完成哪些操作。

人工修复凭据、余额、配额或配置后点击“继续”，与通过独立入口提交新的工作指导是不同意图。不能因为两者都有人介入，就统一强制使用新会话。

## 3. 方案演进与否决理由

### 3.1 保留的初始设计理念

最初的目标是把通用“重试”拆开：临时中断接续原会话，业务失败或返工重新开展工作；页面不展示语义不成立的操作，后端也不能只靠按钮隐藏约束状态机。

这些理念仍有效：

1. 不把模型报告的失败、验收拒绝和供应商故障混成同一类。
2. 不把工具命令失败等同于 Agent 作业失败。
3. 不把会话 ID 的存在等同于会话一定有效。
4. 不允许人工操作重置累计消耗或借继续绕过派发限制。
5. 不把自动协议纠错额度变成人工无限续轮入口。
6. 保留原始输入、输出、错误和费用，能够解释每次处置。

### 3.2 严格检查点方案的问题

被否决的严格方案要求会话已确认、明确临时中断，且 Agent 配置、任务输入、指导、依赖、共享版本和文件指纹均不变。现场指纹依赖 Git HEAD、差异、暂存区及未跟踪文件内容，因此排除了普通工作区。

这把“继续工作”误建模成“恢复完全相同的快照”：

- 原会话能够读取当前文件，不必依靠 Git 历史才能接着工作。
- 中断留下未完成修改正是继续需要处理的现场，不是禁止继续的证据。
- 配置变化可能是在修复上一次错误；一律要求配置不变会阻止合理恢复。
- 文件、依赖或共享信息的变化本身不能证明原会话不适合继续。
- 为普通目录再实现一套完整快照，只是在延续这个不必要的前提。

**决策：不再以工作区、输入或配置完全不变作为继续资格；不以是否使用 Git 区分能否继续。** 文件保护、角色写权限、契约有效性与正常业务状态机仍有各自职责，但不能借会话资格重新引入整套快照一致性检查。

### 3.3 从精确允许名单转向分层处置

只允许少量已识别的临时异常，会使卡死、未知退出和修复后的认证问题都被迫换会话。但“没有识别出临时异常”不等于“原会话有问题”，创建新会话也不保证更能解决这些错误。

**决策：详细错误分类作为理想诊断能力保留；实际处置允许未知。自动操作依赖可靠证据，人工继续不依赖精准命中临时错误允许名单。**

## 4. 最终决策：资格与派发分离

### 4.1 继续是否适合，主要看上次结束原因

工作区类型、是否留下未提交改动、文件指纹变化、配置是否与上次相同，不作为禁止原会话继续的原因。

在原任务仍有效的前提下，允许原会话检查当前现场并接着做。若用户改变的是工作目标或业务契约，则由正常的目标修改、重规划和作业有效性规则处理，不通过文件或提示词逐字比较推断。

### 4.2 基本状态约束仍有效

“主要看结束原因”不表示任何历史作业都可以被复活：

- 已完成、取消、归档或被替代的工作不能通过继续重新进入执行。
- 已有后续尝试的历史作业不能覆盖当前执行意图。
- 旧进程必须停止，不能让两个进程同时编辑同一现场。
- 项目或任务暂停时不启动；解除暂停不等于自动发起原会话继续。
- 冷却、用量、预算、队列、并发与权限按适用规则执行。人工指定 Agent 的独立风险确认规则不由继续隐式触发。
- 适配器必须能表达恢复原会话；不支持恢复时提供新会话执行，不能用完整提示词另起进程却标为原会话继续。

这些是生命周期、执行能力和派发授权检查，不是恢复现场快照的检查。页面由后端提供适用操作，接口和实际派发遵守同样语义，排队不代表无条件获得执行许可。

### 4.3 自动与人工继续分开

- **自动继续**：只有可靠证据支持适合自动接续时才执行，采用明确、有限的策略。某类错误适合继续，不等于它必须自动继续。
- **人工继续**：在没有明确业务终态或已知会话不可恢复的情况下，允许用户结合诊断选择；未知错误不自动剥夺这个选择。
- **外部条件恢复**：认证、余额、配额、模型或命令配置等由人修复并决定何时继续，DOMO 不声称已验证外部条件全部恢复，也不自动清除原有限制。

次数和消耗仍应有界，不能因改名为继续而重置。当前自动接续与人工继续共享最多两轮额外执行，协议纠错单独限制为五轮；放宽快照条件不扩大这些额度。参数与实现细节以设计文档和技术说明为准。

## 5. 理想情况下的详细结束原因与处置

下表描述有足够证据时希望达到的分类精度。“自动”列描述边界，不代表现有实现已支持所有类型的自动恢复。

| 上次结束原因或业务状态 | 人工继续 | 自动处置边界 | 决策依据 |
| --- | --- | --- | --- |
| 网络断连、连接重置、请求超时 | 允许 | 可靠识别时可按有限策略接续 | 执行通道中断，不否定工作本身 |
| 模型供应商临时错误，如 500、502、503、504 | 允许 | 必须确认是作业级供应商错误，不能仅扫描数字 | 供应商异常不代表会话损坏 |
| 短期请求频率或并发限制 | 允许，派发等待限制解除 | 遵守冷却或明确重试时间，不立即循环 | 适合接续不等于可以马上调用 |
| DOMO 单轮时长上限 | 允许 | 可按明确、有界策略自动接续 | 计时终止不等于任务失败 |
| DOMO 服务退出、重启或崩溃导致中断 | 允许 | 不因服务恢复就无条件自动执行，遵守恢复与暂停策略 | 基础设施中断本身不要求新会话 |
| Agent CLI 临时崩溃 | 允许尝试 | 原因不可靠时不自动继续 | CLI 异常不等于会话不可用 |
| 长时间无输出，被看门狗判定卡死 | 允许 | 不自动继续；重复发生时提示考虑新会话 | 无输出可能是长命令、通道问题或真正卡死，第一次不能断言 |
| 未知原因、普通非零退出、信号终止 | 允许尝试 | 不自动继续，诊断保持未知 | 退出码不能证明换会话更合适 |
| 用户强制暂停或主动停止在途进程 | 解除暂停后允许选择 | 不自动恢复原会话 | 主动中断不必等同于要求换会话 |
| 认证失败、权限缺失、余额不足、长期配额耗尽 | 人工恢复外部条件后允许 | 不根据错误文本认定已恢复，不自动接续 | 最终是否恢复以及是否继续由人决定 |
| 模型、命令参数、端点或其他配置错误 | 修复后允许尝试 | 不因配置被修改就自动启动 | 配置变化可能正是解除错误的必要操作；仍须实际支持恢复原会话 |
| 会话明确不存在、过期、损坏或恢复被拒绝 | 原会话无法继续，提供新会话 | 不静默新建会话 | 这是恢复能力失败，不是普通临时中断 |
| 上下文达到硬限制，且 Agent 无法自行压缩恢复 | 新会话 | 不重复调用同一已确认不可恢复的上下文 | 区分可自行压缩与真正硬失败 |
| 模型明确提交任务失败或请求重规划 | 按业务流程处理，后续执行使用新会话 | 不作为供应商异常续跑 | 有效业务结果不同于执行通道中断 |
| 验收拒绝、合入冲突返工 | 新执行会话 | 走返工与重新验收流程 | 不是恢复失败作业 |
| 缺失或不合法结果，自动协议修正尚有额度 | 作业内做有限纠错 | 由协议修正策略控制 | 与人工继续分开表达 |
| 自动协议修正耗尽 | 人工处理后使用新会话 | 不通过人工继续无限延长纠错 | 保留明确纠错边界 |
| 完整有效结果已经产出，DOMO 收集或结算失败 | 优先恢复收集与结算，不重复模型执行 | 按持久化结果和结算阶段恢复 | 避免重复写入、发布或其他外部副作用 |
| 工作已取消、归档、完成或被替代 | 不允许借原作业继续复活 | 按业务终态处理 | 历史存在不代表当前仍有效 |

### 5.1 环境缺项按发生层次区分

“缺少 SDK、文件、依赖或授权”不能只凭关键词决定处置：

1. 模型运行中某条工具命令失败，但 Agent 仍在处理：这是执行过程，不是作业结束原因，由模型自行判断与修复。
2. Agent 正常提交“无法完成”的有效任务失败结果：这是业务结论，进入人工处理或重规划，后续按新会话执行。
3. 外部服务或凭据问题使整个 Agent 执行异常结束：按作业级基础设施错误诊断，允许人修复后继续原会话。

同样的词出现在不同层次，不能产生同样的自动动作。模型对事实前提、资源缺项和修复方案的判断仍属于产品预期能力，DOMO 不为每种业务缺项建立专门状态机。

### 5.2 有效结果与进程错误并存

进程报错并不证明没有结果，存在结果文件也不证明业务已完成。应检查结果是否完整、符合角色协议、属于当前有效作业，以及结算处于什么阶段。

不能仅凭“看到错误事件就继续”，也不能仅凭 JSON 中有 `kind` 就认定无需恢复。合法业务失败按业务流程处理；完整成功结果优先结算；残缺结果再结合结束原因处理。具体优先级应有测试覆盖，不从一段日志猜测。

## 6. 错误分类的可靠性边界

### 6.1 能可靠知道的事实

DOMO 可以直接记录自己发起的超时终止、无输出终止、用户强停和正常服务关闭；恢复时可以识别未结算的在途作业被服务中断。它知道的是终止经过，不一定知道此前 Agent 是否已经遇到其他问题。

结构化协议明确报告的供应商错误、会话拒绝、上下文超限等可以归一化；结果文件是否缺失、是否合法、协议纠错是否耗尽，也可机械判断。

模型报告任务失败的事实可以确定，但模型对失败根因的分析不因此变成经过 DOMO 独立证明的事实。

### 6.2 不能承诺准确识别的内容

- HTTP 429 可能是短期限流，也可能是余额或长期配额问题。
- HTTP 403 可能是权限、账户策略或临时风控。
- 同一个退出码可能表示启动错误、网络问题、CLI 缺陷或工具链故障。
- stdout 中的错误可能是模型引用、工具输出、测试夹具或历史信息。
- 一次网络请求失败可能已经被 CLI 自行恢复，后续正常完成；中间事件不能覆盖最终正常结果。
- Agent、CLI 或供应商升级可能改变字段、嵌套结构和错误码含义。
- 会话上次可用不表示恢复时仍存在，外部凭据和服务状态也会随时改变。

因此统一分类必须保留 `unknown`，不能通过任意关键词把低可信推断提升为确定事实。stderr 也不天然等于可信供应商错误，需要结合适配器协议判断。

## 7. Agent 适配层的统一错误抽象

### 7.1 责任划分

各适配器格式不同是可以通过架构解决的问题，不应长期作为无法统一识别错误的理由。目标分层如下：

| 层次 | 责任 |
| --- | --- |
| 进程运行层 | 退出码、信号、启动失败、超时、无输出、终止经过等客观事实 |
| Agent 适配层 | 解析本类型事件，区分供应商、CLI、会话与工具错误，输出统一诊断和会话恢复能力 |
| 角色结果协议层 | 解析任务失败、重规划、验收拒绝、有效成功结果以及协议错误 |
| 作业与恢复策略层 | 合并结束经过和诊断证据，决定自动接续、人工选择、业务流转或恢复结算 |
| 调度层 | 队列、并发、冷却、角色池、费用与尝试授权等派发约束 |
| 展示层 | 展示归一化原因、依据、未知状态和后端提供的操作，不独立解析原始错误控制按钮 |

适配层负责“报告什么错误、依据是什么”，不持有数据库执行人工裁决，也不直接决定重规划或清除冷却。runner 和 scheduler 不应各自维护按 Agent 类型解析错误的分支。

适配结构与统一诊断契约参见 [Agent 适配层架构](agent-adapter-architecture.md)，协议核对依据参见 [CLI 协议核对](agent-cli-protocols.md)。统一抽象并不承诺所有供应商事件都具有同样的分类精度。

### 7.2 抽象需要表达的语义

以下是目标语义，不是已定稿字段名、Rust 类型或数据库 schema：

| 信息 | 作用 |
| --- | --- |
| 停止原因 | 单独表示超时、无输出、用户终止、服务中断、进程退出、正常结束，避免和诊断混淆 |
| 归一化错误类别 | 网络、供应商临时错误、限流、认证、余额/配额、配置、会话、上下文限制、CLI 内部错误或未知 |
| 作用层次 | 作业级故障、工具级错误或信息事件，避免工具失败升级为作业失败 |
| 证据来源 | DOMO 自有事件、适配器结构化事件、CLI 文本推断或未知 |
| 原始码与诊断引用 | 保留 HTTP 状态、供应商错误码、原始事件或受控日志引用，方便追溯 |
| 重试时间与恢复提示 | 提供供应商明确上报的时间或建议，不把建议等同于 DOMO 已获执行授权 |
| 会话恢复状态 | 区分支持恢复、标识可用、明确不可恢复以及实际恢复失败，不用一个布尔值冒充所有事实 |

一个作业可以同时记录“被 DOMO 超时终止”和“此前收到供应商限流事件”。不必强行丢掉其他证据，只保留单一标签。策略应考虑事件层次、顺序和最终结果，而不是取日志里第一个或最后一个包含关键字的句子。

### 7.3 降级原则

1. 优先使用 DOMO 已知的终止事实，以及适配器理解的作业级结构化事件。
2. 缺少结构化协议的自定义 CLI 可以输出未知，文本解析只作有来源标记的辅助诊断。
3. 工具输出、推理文本和模型引用不能单独授权自动继续。
4. 无法区分短期限流与长期配额时，不自动假定会自行恢复；人工继续仍可用。
5. 无法确定会话失效时，不因模糊文本提前断言绝对不可恢复；实际恢复时验证。
6. 明确的有效业务结果不能被较低可信的文本推断覆盖。

统一适配层能够消除格式差异，不能凭空补足供应商未提供的信息。理想分类越细，越需要真实协议样本和未知分支，而不是越多全局正则表达式。

## 8. 实际恢复与人工决策

继续请求表达的是“尝试恢复这个会话”，不是事前证明它一定成功：

1. 用户查看上次结束原因，必要时在 DOMO 之外恢复条件，选择继续。
2. 后端核验作业仍有效且可以派发，等待适用的冷却、预算和并发条件。
3. 适配器明确发起原会话恢复，Agent 检查当前现场后接着工作。
4. 如果恢复返回会话不存在、上下文不可恢复等确定错误，保存原始诊断并说明无法继续，提供新会话执行。
5. 若恢复再次因未知或外部错误失败，仍如实记录，不把失败包装为新会话成功启动。

修复配置后还需满足目标 CLI 实际支持的恢复方式。不能把“不要求配置不变”解释为可以跨不兼容的 Agent 会话存储迁移；当配置使原会话不可访问时，应明确说明恢复能力不满足，而不是重新引入完整配置相等校验。

继续提示应提醒检查上一轮执行到哪里、现有文件和可能的残留操作。重复执行命令可能造成外部副作用；终止进程、恢复会话和重新发送提示词都不提供业务操作恰好一次保证。DOMO 不能因此宣称自动回滚，也不能用文件指纹假装解决外部副作用。

## 9. 普通工作区的专门边界

普通工作区与 Git 工作区采用同样的会话继续原则，不要求为继续引入全目录快照。

现有普通目录保护包含输入/产物指纹、覆盖授权和未完成写入标记。它们服务于文件保护和交接检查，不能把“原写作业中断留下现场”误判成“必须先换新会话”：

- 原会话继续需要能够处理自己的未完成修改，不能仅因未完成写入标记而在启动前被阻断。
- 未完成写入标记不能为使继续通过而直接当成成功清除；继续失败仍须保留真实现场状态。
- 模型接手时检查当前文件，既有写权限及用户约束仍有效，继续不授予越界写权限。
- 是否还需要某类独立人工检查，应按该保护机制的实际职责确定，不能将全部外部变化重新变成原会话继续的通用禁止条件。

具体如何表达“同一工作接续”与“另一个作业接手”，属于保护机制与恢复路径的集成设计；不能以这项集成尚未完成为由，将普通目录不支持继续当成产品必然限制。

## 10. 审计、费用与验证依据

### 10.1 审计与用量不因继续消失

保留每轮输入、输出、结束原因、归一化诊断、证据来源、人工选择、恢复结果与用量。修复外部条件不等于 DOMO 已验证成功，未知字段保持未知，不写入凭据等敏感信息。

继续不清零累计费用与执行投入，也不清零原任务的失败、验收拒绝记录。适配器提供累计会话账本时，结算要避免与此前已入账运行重复计算。自动协议修正、人工继续和新会话执行应能够在历史中区分。

### 10.2 行为与契约验证依据

- Git 和普通目录都能接续原会话；中断残留文件不是禁止条件。
- 修改文件或修复配置后，不因快照不一致被继续资格拒绝。
- 卡死、未知退出和强制暂停可由人决定继续，不自动循环。
- 认证、余额、配额和配置错误可在人修复后继续，未恢复时再次失败仍如实呈现。
- 同一归一化错误在不同适配器上得到一致策略；未知字段、未知事件和协议升级不会误触发自动操作。
- 工具输出中的 429、503、认证或会话字样不会被当成作业级故障；已被 CLI 恢复的中间错误不会覆盖最终成功。
- 原会话恢复失败不静默新建；不支持恢复的适配器不会伪装成继续。
- 有效成功结果与结算异常并存时优先恢复结算，业务失败和协议纠错耗尽仍走独立流程。
- 暂停、取消、替代、已有在途进程、排队和预算约束不能被继续绕过。
- 历史输出、费用和错误证据保留；恢复失败、服务中断与重复恢复不会重置或重复计算消耗。

这些是长期维护的行为与契约测试依据，不是一次性执行清单或对现有测试覆盖率的声明。

--------

**核心取舍：保留细致、统一、可追溯的错误分类目标，但不要求分类永远准确；自动行为依据可靠证据，人工继续允许处理不确定性，真实恢复结果决定原会话是否还能使用。**
