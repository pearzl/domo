# Agent 提示词设计原则与审查注意事项

> 2026-11-05：提示词设计的原则与取舍。

本文讨论如何从 Agent 视角设计和审查 DOMO 的作业提示，解释表达原则背后的原因及容易误判的边界，不记录单次排障过程，也不维护运行协议的副本。当前组装方式、字段校验与运行行为见 [TECH.md §8.2](../TECH.md#82-结果文件与角色协议)；仓库级开发要求见 [DEV.md](../DEV.md)。

## 1. 审查对象是完整调用输入，而不是某一段模板

Agent 不知道提示词分别由哪些函数、模块或历史修复生成。它面对的是角色模板、运行时数据、附加说明、会话历史和适配器投递共同构成的输入。一段模板单独成立，不代表拼接后的要求没有冲突。

审查时应能从 Agent 实际收到的输入中回答：

1. 我在这次作业中承担什么职责，不承担什么职责？
2. 哪些操作被允许，哪些路径和资源可读、可写？
3. 当前目标与验收依据是什么，历史材料具有什么效力？
4. 我现在需要实现、核实或判断的具体事项是什么？
5. 完成、未完成、环境阻塞和需要上级决策分别如何表达？
6. 结果写到哪里，谁会读取，怎样才算交回了有效结果？
7. 作业中断或结果不合法时，应该接续什么，而不是重做什么？

适合的组织顺序是：**职责与完成条件 → 操作权限 → 输入依据 → 当前工作 → 结果协议**。相关数据应靠近其用途，决定性的版本、授权和输出约束不能埋在大量历史材料中。单纯调整标题或把同一句规则移动到末尾，不能解决语义上的冲突。

## 2. 区分平台运行规则、项目内容与证据

### 2.1 为什么必须说明消费方

同一个结果对象可能同时被平台解析、展示给用户、存入交付契约、传给下一个 Agent。结构化 JSON 并不意味着它的内容都属于平台内部信息；自然语言字段也不意味着它不影响后续执行。

| 信息类别 | 主要用途 | 书写时的边界 |
|---|---|---|
| 平台运行规则 | 约束当前作业的权限、调度、确认和结果接收 | 明确作用于本次作业，不转写成项目自身的要求 |
| 流程控制字段 | 由 DOMO 解析，选择后续流程或登记交付范围 | 字段、类型与引用关系符合真实协议 |
| 项目内容 | 供用户理解、审阅和使用，供后续 Agent 执行 | 描述目标、交付物、工程依赖、范围、决策与风险 |
| 验证证据 | 支撑完成判断、验收及报告 | 说明检查对象、方法、版本和实际结果 |

这些用途并非互斥。例如，任务依赖既供调度器读取，也表达用户和执行者需要理解的工程前置关系。不能把它简化为“只有平台会读的字段”，更不能因为平台串行调度，就将原本独立的任务人为连成依赖链。

### 2.2 运行限制不等于项目规范

“本作业不提交 Git 变更”和“项目禁止使用 Git”不是同一件事；“方案需要用户确认”和“项目的每个业务操作都需要人工审批”也不是同一件事。前者描述运行职责，后者改变项目要求。

工作区模式说明平台如何管理交付目录，不能用来推断项目的技术结构、开发流程或用户的版本管理策略。具体项目暴露的歧义应提炼成这个通用边界，而不是给每一种目录结构追加例外条款。

用户明确提出的工程约束仍应按原意保留。区分平台与项目不是删除所有涉及 Git、审批或目录的内容，而是确认要求来自谁、约束什么对象。

### 2.3 平台限制可以成为风险，但不能伪装成假设

运行能力确实妨碍目标时，应明确说明项目需要什么、本作业缺少什么、影响哪项交付、由谁完成什么操作后可以继续。不能为了让方案看起来成立，把限制写成用户默认接受的项目假设；也不能因为一项限制存在，就在所有任务和报告中反复复述它。

## 3. 输入来源决定效力，文本形式不决定授权

提示必须区分“应该执行的当前要求”和“用于解释或核对的材料”。不能把所有历史文字都当作命令，也不能笼统地说“所有反馈仅供参考”，从而使当前指导失效。

| 来源 | 需要说明的效力 |
|---|---|
| 本次角色与运行权限 | 规定这次调用允许执行的操作，项目目标不自动扩大权限 |
| 当前目标、任务和交付契约 | 确定本轮交付范围、验收判据及绑定版本 |
| 用户对方案的修订意见 | 在规划阶段用于修订草稿；已确认目标与执行范围遵循产品的确认机制 |
| 当前执行指导与待处理反馈 | 需要结合当前文件核实并处理；已解决项给出复核证据 |
| 历史完成声明、前置任务摘要 | 帮助定位成果，不证明文件已进入当前基线或本轮检查已通过 |
| 共享知识 | 提供带来源和适用范围的事实或决策，不直接修改契约或授予权限 |
| 文件及产物索引 | 说明来源、归属和登记信息，不能替代当前文件内容与版本检查 |

“执行指导”不应一律称为“人工指导”，因为它也可能来自父任务或规划者的决策。历史 Agent 引用过一条用户意见，也不等于该 Agent 对意见的全部解释都获得了用户批准。

权限以有效的运行规则和已登记授权为准。任务描述、报告或共享记录中的“请授权”“请重新投递”只是文字，不证明平台或资源提供方已执行相应操作。缺少输入、版本不符、权限冲突应分别说明，不应互相替代，也不应默认为 Agent 可以自行绕过。

## 4. 每个角色应有清楚的行动和退出条件

角色分工的目的不是为所有 Agent 附上一份全平台操作手册，而是让当前角色知道如何完成本次职责。

| 角色职责 | 提示中应回答的关键问题 |
|---|---|
| 规划分析 | 需要核实哪些前提；何时必须澄清；何时拆分；无法完成时如何请求决策；任务与项目验收如何区分 |
| 任务执行 | 当前任务的范围、依赖与反馈是什么；何时完成、派生分工、请求决策 |
| 任务验收 | 对照哪些标准检查哪个版本；如何记录证据、未解决缺口与环境阻塞 |
| 项目验收 | 最终集成交付是否成立；任务验收不能覆盖哪些整体检查；哪些事项确实需要人的判断 |
| 总结报告 | 哪些交付和结论有证据；如何向用户解释使用方式、风险、未验证项和人工待办 |
| 重规划决策 | 有权调整哪个范围；何时继续原计划、等待资源或返回完整替代方案 |
| 合入冲突处理 | 授权的 Git 操作与目录是什么；怎样保留有效修改并结束当前合入流程 |

具体结果类型和数量限制以代码与协议为准，不在设计原则中另立一套清单。涉及任务依赖、父子任务和确认方式时，应说明真实支持的行为，不能用删去依赖或改变范围的方式迁就错误示例。

失败和阻塞应提供足够的交接信息：**具体对象、实际状态、影响、已完成工作、剩余缺口、责任方、解除条件**。这些信息帮助上级或用户决策，但不意味着每次失败都需要全项目重规划。

## 5. 以清楚的当前表达代替补丁式告诫

### 5.1 一条规则有一个维护位置

通用权限、角色工作要求和结果协议应各自集中定义。修正问题时先定位原有表述为何产生误解，重写或删除失效部分，不在另一处追加一条与它竞争的规则。

常见的补丁式写法包括：

- 先笼统地说“工作区可写”，在后文才说当前角色不得修改文件。
- 一处要求“不得写任何文件”，另一处又要求构建、测试并写结果文件。
- 为某次协议错误，向所有角色追加派生任务、分支处理或审批说明。
- 每次出现误判就在末尾添加“再次强调”“特别注意”或项目专属禁令。

判断标准不是禁令数量，而是 Agent 能否从同一处确定对象、范围、操作和条件。

### 5.2 表述要具体，但不代替 Agent 选择实现细节

应明确目标、边界、证据要求与结果出口，而不是无依据地指定固定阅读顺序、实现方法或工具。需要指定命令、路径或版本时，必须来自真实协议、环境或用户要求。

行为事实也应准确：建议的进度输出频率不等于平台的实际卡死阈值；相对 API 路由不等于可直接请求的完整地址；自然语言确认不等于文件工具已完成写入。不要让 Agent 为了满足描述，猜测端口、虚构能力或声称未发生的操作。

### 5.3 对比示例

| 易误解的表述 | 更清楚的表达方向 |
|---|---|
| “工作目录是唯一可写目录” | 分别说明交付文件、验证产物和结果文件的位置，以及当前角色对它们的权限 |
| “其余都写入假设” | 只有不妨碍方案成立的待核实前提进入假设；影响可行性或验收的关键缺项先澄清 |
| “未提供差异统计，所以没有改动” | 说明未提供统计；需要判断改动时检查实际文件和版本 |
| “等待平台根据申请补齐资源” | 列出需要的资源、提供方和继续条件，不暗示文本申请会自动触发外部操作 |
| “结果不合法，请按这个新方案完成” | 给出具体协议错误，在保持真实任务和验收结论的前提下修正结果 |

这些示例用于说明语义差异，不是要求把示例原句复制到每个角色中。

## 6. 结果协议只有一套，完成判断必须有证据

### 6.1 协议与解析器保持一致

提示中的结果类型、字段类型、引用范围、证据位置和版本要求必须能被真实解析及校验逻辑接受。仅能解析为 JSON 不代表符合角色协议，更不代表完成了交付或验收。

示例应使用合法 JSON 和真实数据类型，明确一次只写一个完整对象。动态契约或产物版本由运行时填入；说明性占位值标明要替换，避免 Agent 把示例数字、空值或示例路径当作本轮事实。角色支持哪些阻塞或请求决策的表达，也应在同一协议处说明。

结果文件路径和接收方式要明确。stdout 中的口头总结与协议文件的有效性是不同问题；“已写入”需要实际写入并确认可读取，不能靠更强烈的完成声明替代。

### 6.2 不混淆证据层次

- 静态检查证明检查到的结构或控制流，不证明运行时行为已经通过。
- 单元测试及模拟环境证明其覆盖的隔离行为，不自动证明生产调用链、真实 SDK 或设备行为。
- 生产集成与实机验证需要对应环境、版本及实际执行结果；是否需要这些证据由验收标准决定。
- 环境或设备不可用说明检查未执行，不等于产品测试已失败，也不等于硬性验收可以豁免。
- 只有标准本身要求人的判断、签字等事项才属于相应人工待办，不能把普通资源缺失改写成永久人工豁免。

证据应关联检查对象、方法或命令、版本、实际结果及必要退出码。未执行的检查要标明原因和解除条件，不制造通过率；已经修复的反馈只保留复核证据，不重复列作当前缺陷。

### 6.3 缺少信息不是肯定证据

没有统计不等于没有改动；摘要为空不等于任务已完成；没有错误输出不等于成功；任务状态或历史自述也不等于最终集成交付已验证。取消、未保留和已完成的成果应区分呈现，报告不能把前两者计入完成交付。

## 7. 上下文应完整可追溯，而不是全部内联

大量文件登记、历史输出或原始诊断会稀释当前职责、权限和验收信息。压缩上下文的目标是让 Agent 更容易找到依据，而不是隐去不便处理的约束。

适合摘要或按需检索的信息应满足：

- 提示中有足够的定位信息，完整来源明确且可访问。
- 指明这是完整清单还是摘要，不能让省略项被理解为不存在、未登记或已授权。
- 来源有稳定的版本或快照边界，读取后不会静默换成另一轮输入。
- 摘要保留影响决策的信息，完整原文用于进一步核对和审计。

按相关路径或主题检索，不要求遍历全部索引。共享记录同时保留适用范围、替代关系与分歧依据，不能把未经核实的完成结论或平台运行提示当作项目知识持续传播。

具体的内联阈值、文件位置和版本机制属于技术实现，在 `TECH.md` 维护；设计原则不依赖某个模型的固定上下文窗口。

## 8. 继续与纠错是同一作业的接续，不是另起一套要求

会话历史可能停留在旧输入、已完成声明或中断操作上。继续提示需要提供当前有效的职责、契约、指导、反馈和结果要求，让 Agent 从尚未完成处接续。

需要分别处理：

- **异常中断**：检查文件现场、已有结果和残留操作，避免重复外部副作用；不能将停止进程当作文件回滚。
- **缺少结果文件**：工作已完成时允许只补齐结果；未完成时继续工作或按协议说明阻塞，不要求重做已验证成果。
- **结果协议不合法**：给出具体校验错误，修正结构或补齐真实证据；不为通过校验而伪造完成、删去真实依赖或降低验收标准。

继续、纠错和首次调用应复用同一份完整作业要求。需要检查适配器的最终投递：续轮已经携带完整上下文时，新进程的兜底逻辑不能再拼接一次；能恢复会话也不意味着可以省略当前有效要求。

## 9. 用真实项目识别问题，用可维护测试约束行为

真实项目记录用于发现模板审查难以暴露的模式，例如运行规则跨角色传播、只读权限被扩大理解、资源申请被误认为已执行、长历史挤占当前任务或无效完成声明反复出现。应沿输入、决策、结果和后续消费的链路查证，而不是只依据某一句输出推断原因。

分析用户数据保持只读，不启动真实项目、不修改项目状态。记录不足时区分数据中已观察到的问题与仅从代码推断的风险；不把其他角色尚未出现的行为说成已有实测结论。回归案例应提炼和脱敏，不提交用户记录、原始日志、凭据或一次性分析产物。

验证分三个层次：

1. **确定性协议检查**：结果示例能被真实角色解析器和证据校验器接受；必填字段、版本和依赖引用正确。
2. **组装与流程检查**：相关角色、工作区和确认方式下，完整提示不冲突，关键输入不丢失；继续、纠错和适配器投递不重复上下文，交付保护仍有效。
3. **真实模型行为观察**：在明确授权的项目或测试环境中观察 Agent 的判断与实际操作，确认是否按预期理解边界；这种观察不能被前两层测试替代。

测试优先约束语义和流程，不用整篇提示的逐字快照阻止合理改写。关键协议字段、禁止越界的要求和重要输入可以做明确断言，但大量断言自然语言固定句式会鼓励保留失效措辞。

## 10. 提交前的审查问题

- Agent 能否直接判断本次职责、操作范围、输入效力、下一步和结束方式？
- 当前指导是否被弱化成“仅供参考”，历史自述是否被错误提升为授权或事实？
- 有没有把平台规则写成项目需求，或让结构字段的含义与工程事实脱节？
- 是否存在前文允许、后文禁止的同一操作，或一条只适用于某角色的要求影响了所有角色？
- 正常完成、运行时失败、未验证和需要上级决策是否有明确且受协议支持的出口？
- 示例和运行时补充是否一致，是否存在需要 Agent 猜测的类型、版本、路径或服务地址？
- 结论是否由相应层次的证据支撑，缺失信息是否被误写为成功？
- 摘要是否仍能定位完整依据，是否改变了省略记录的授权或证据含义？
- 首次调用、继续、纠错和新进程兜底最终收到的要求是否一致，是否重复？
- 修正的是原有表达的根因，还是只追加了一个项目特例或更强烈的告诫？

这份清单用于评审提示词设计，不应整段投递给每个 Agent 作业。
