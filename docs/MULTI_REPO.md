# 多仓工作区模型：设计讨论与决策记录

## 1. 结论摘要

- **多仓共享目录下的串行不是设计保守，而是本质约束。** worktree 只能解决文件隔离，解决不了跨仓一致性、胶水文件和运行时隔离。
- **逐仓 worktree 不可行**：worktree 建在工程目录之外，且只覆盖任务 scope 内的仓库，任务会看到残缺工程。
- **全仓镜像 worktree 能补目录完整性**，但绕不开胶水文件、ignored 文件、submodule、绝对路径、跨仓合入事务和运行时资源冲突。
- **胶水文件全量复制只对“静态、只读、体积小”成立**；可变胶水会分叉，缺少写回/合并就会产生“任务验收通过但真实工程没变”的假验收。
- 真正的产品抉择是：**DOMO 要不要继续管理多仓的 git 迭代边界**。
  - 要 → 保留现状（A）或保守收敛（D）。
  - 不要 → 两类 + 直接改 + 串行（B），把 git 生命周期交还用户。
- **“两类 + 自动识别”本身值得做**：`multi` / `plain` 不是用户语义，只是“锚点是否为 git 仓库、包含几个仓库”的事实；让用户手选容易误配，也让并发规则变成类型特例。
- 多仓并行如果成为刚需，**优先引导 monorepo**；否则不要用 worktree 去模拟，那会把调度问题变成分布式事务问题。

## 2. 现行设计（方案 A）

### 2.1 工作方式

工程分三类：

| 类型 | 工作方式 | 并发 | 隔离 |
|---|---|---|---|
| 单仓（git） | DOMO 工作区内每任务开 git worktree | 允许：多项目、同项目多任务并行 | worktree 天然隔离；合入前同步基线 |
| 多仓（git 父目录） | 直接在工程目录操作；每仓一个项目分支 | **不允许**：同一时刻一个项目、一个任务 | 项目分支隔离；切换时逐仓切分支；要求工作区干净 |
| 普通目录（非 git） | 直接在工程目录（或默认目录）操作；任务可用子目录 | 允许（无版本控制保护） | 目录级，弱隔离 |

多仓的完整流程：

1. **确认项目**：逐仓检查（存在、可写、目标分支未被其他 worktree 占用）→ 全部通过才逐仓确保 `domo/iter-<项目short>` 分支存在并 checkout → 写基线 `{repos: {rel: branch}}`；任一失败不切换任何仓库。
2. **切换项目**：暂停当前项目 → 逐仓检查工作区干净（有脏文件则阻止并列出仓库与文件）→ 停止工程目录宿主 → 逐仓 checkout 目标项目分支（不存在则按当前 HEAD 创建，失败回滚已切换仓库）→ 恢复目标项目；同工程仍有运行中项目则拒绝。
3. **任务验收**：逐仓确认位于目标项目分支，再 `git add -A && git commit`；无改动跳过并记录；任一仓提交失败 → 任务转 `escalated` 并进收件箱，不静默通过。
4. **项目完成**：默认不合回主干，保留分支；报告展示 `repo → branch`，并注明“分支已保留，未合回主干”。

### 2.3 现存问题

1. **三类不是用户语义**：用户很难判断该选单仓、多仓还是普通目录；选错会直接导致并发策略和隔离方式错误。
2. **并发规则不一致**：设计说普通目录“允许并行、弱隔离”，但显式指定的非 git 目录在实现里是零隔离、直接共用同一目录（`sandbox.rs` 的 `direct_non_git` 分支），并行会互相覆盖文件。
3. **多仓维护成本高**：脏工作区 409、全有或全无 checkout、失败回滚、切分支前停宿主、`domo/iter-*` 分支污染、自动提交侵入用户仓库。
4. **多仓与非代码的异同**：
   - 共同点：都没有每任务隔离，都是“共享可变工作目录”。
   - 不同点：多仓还有分支/提交/基线这些**并发下会被破坏的 VCS 不变量**，所以多仓串行是硬要求；普通目录并行只是文件冲突风险。方案 B 会把这两者统一成串行，这个区别随之消失。
5. **迁移压力低**：当前仓库里没有 `data/domo.db` 运行库，历史 `multi` 数据兼容成本很小；代码里保留 legacy 读取即可。

## 3. 讨论确立的技术事实

1. **逐仓 worktree 会破坏工程完整性。** worktree 建在 `~/.domo/workspace/.../wt/<task>/<repo>`，不在工程父目录下；而且只建任务 scope 内的仓库（`sandbox.rs` 的 `task_scope`），目录名还被压平（`rel.replace('/', "_")`），任务看不到其他仓，相对路径和跨仓脚本失效。
2. **全仓镜像 worktree 可以补目录完整性**：每任务一个根目录，所有仓库按原始相对路径建进去。但 worktree 只含 tracked 文件，缺 ignored 文件、submodule、父目录胶水文件和绝对路径假设。
3. **全仓 worktree 不能解决跨仓一致性。** 两个任务各自从同一快照出发、独立推进分支后，可能产生语义不兼容；git 合并干净 ≠ 产品可用。并行编码必然带来串行集成。
4. **跨仓合入需要事务。** 逐仓合入时任一仓冲突，必须回滚已合入的仓或进入人工不一致状态；否则工程处于半合入的坏状态。
5. **胶水文件全量复制不是通用解。** 只对“静态、只读、体积小”的胶水成立；可变胶水会分叉，必须定义写回/合并，否则会出现假验收；生成物、密钥、大数据、DB/volume 不适用。真正的解法是 meta-repo / manifest。
6. **文件隔离 ≠ 运行时隔离。** 端口、本地 DB、Docker network/volume、缓存、本地 socket 仍会冲突；两个全栈任务并行跑测试很可能互相打架。
7. **并行收益与仓库重叠度成反比。** 多仓工程耦合越强，任务越会落在同一批仓上，并行收益越低、冲突越高。
8. **monorepo 是并行的正规解法。** 一个 worktree 天然包含全部代码，不需要镜像、胶水策略和跨仓合入事务。
9. **多仓并行本质是“工作区物化 + 分布式事务”问题**，不是 worktree 问题；完整复制整个目录（含 `.git`、ignored 文件）能解决环境完整性，但磁盘/时间成本高，仍需跨仓集成。

## 4. 候选方案

### A. 现状：三类，多仓串行 + 分支/提交

- **做法**：见 §2。
- **优点**：有明确的迭代边界；可回滚、可追溯；每任务一次提交；切换项目有脏检查保护；报告有 `repo → branch`。
- **缺点**：多仓最复杂的部分都在这里；切换/确认/提交的失败路径多；自动建分支和提交对用户仓库有侵入性；三类配置易选错。
- **复杂度**：**高**（状态机 + git 操作 + 失败回滚 + 宿主生命周期）。
- **性价比**：**中**。如果“项目 = 可回滚的仓库迭代”是核心承诺，这套成本是值得的；否则是纯负担。

### B. 两类，多仓当普通目录

- **做法**：只剩“git 仓库 / 普通目录”两类；多仓目录按普通目录处理：**串行 + 直接在工程目录改**；去掉项目分支、基线、逐仓提交、切换流程。
- **优点**：
  - 删掉多仓最易错的管理层，估算净减 **1.0–1.3k 行**；
  - 并发规则统一为“有 worktree 隔离就并行，没有就串行”；
  - 不再污染用户仓库；
  - 类型可自动识别，去掉误配；
  - 实现与文档一致（顺带修掉普通目录并行不安全的问题）。
- **缺点**：
  - 失去“项目 = 仓库迭代边界”：失败迭代不能一键回滚；
  - 失去逐任务提交和 `repo → branch` 报告，任务改动归属变弱；
  - 脏工作区不再被系统拦截，agent 改动会和用户未提交改动混合；
  - 项目切换概念消失；
  - 非代码任务也串行，损失并行。
- **复杂度**：**低–中**。删代码为主；新增普通目录的项目级 + 任务级串行门、类型识别、legacy 兼容。
- **性价比**：**高**，前提是接受“git 生命周期交还用户”。

#### B+ 建议配套的安全网

1. 项目开始时记录每仓 HEAD；
2. 验收时把 `git diff <基线>` 只读快照进证据包；
3. 确认项目时对脏仓库警告（不阻塞）；
4. UI 只读显示各仓当前分支；
5. 新项目开始时提示“建议先提交/建分支”。

这些约 50–100 行，能保住审计和可复现性，但**不恢复自动回滚**。

### C. 两类 + 能力判定：有 repo 就 worktree（已否决）

- **做法**：不按类型，按“是否发现 git 仓库”决定 worktree 或直接改。
- **否决原因**：最初认为可以复用现成的多仓 worktree/merge 代码，但忽略了 **worktree 在工程目录之外、且只覆盖 scope 内的仓**。逐仓 worktree 会让任务看到残缺工程，跨仓相对路径和脚本失效。
- **结论**：**不成立。**

### C2. 全仓镜像 worktree（C 的修正版）

- **做法**：每任务创建一个根目录，**所有仓库**按原始相对路径建 worktree；胶水文件复制或只读挂载；验收后逐仓合回项目分支。
- **优点**：目录完整性成立；任务间文件隔离；工程目录保持干净；不需要用户切分支。
- **缺点**：
  - 胶水文件仍需策略（只读快照或 meta-repo + 合并）；
  - worktree 缺 ignored 文件/submodule，依赖要逐任务安装/构建；
  - 绝对路径、IDE、Docker bind mount 仍可能失效；
  - 运行时资源仍冲突；
  - 跨仓语义兼容和原子合入仍需额外机制；
  - 每任务 N 套工作树，磁盘/构建时间上升；
  - 项目级并行还要每项目每仓分支 + 临时 worktree/`update-ref` + 合入队列。
- **复杂度**：**高–很高**。需要 workspace materializer + 跨仓合入事务 + 运行时隔离 + 生命周期治理，代码量大概率超过 B 删掉的部分。
- **性价比**：**低–中**。只在“任务基本 repo-local、胶水小且静态、构建轻、几乎不跨仓”时成立。

### D. 保守收敛：两类 + 自动识别，但保留多仓行为

- **做法**：用户只选目录，系统识别三种内部模式；多仓仍是“串行 + 项目分支 + 逐仓提交”，普通目录改为串行 + 直接改。
- **优点**：去掉类型误配；修掉普通目录并行不安全；保留 VCS 语义；风险低。
- **缺点**：`baseline.rs` 的多仓状态机仍在，代码省得少；切换项目的复杂度不变。
- **复杂度**：**中**（保留 A 的大部分复杂度，去掉 UI/配置复杂度）。
- **性价比**：**中–高**。适合“产品语义先不动，只简化入口”的阶段。

### E. 产品边界：并行只支持 monorepo

- **做法**：多仓目录明确串行；需要并行的用户使用单仓（monorepo）。
- **优点**：实现最干净，复用单仓 worktree；不引入跨仓编排；规则容易解释。
- **缺点**：要求用户改变仓库结构；对“必须多仓”的用户不友好；无法支持独立仓库的发布节奏/权限。
- **复杂度**：**低**。
- **性价比**：**高**，作为产品定位规则，而不是独立实现。可以和 A/B/D 叠加。

### F. meta-repo / manifest（完整的多仓并行方案）

- **做法**：父目录建 meta-repo 管理胶水；各仓用 submodule / `repo` / `west` / manifest 固定 commit；每任务按 manifest materialize 完整工作区；胶水有 diff/merge/rollback；跨仓合入走事务。
- **优点**：可复现、可回滚、胶水有版本、多仓并行在工程上成立。
- **缺点**：manifest 维护、同步/初始化、submodule 状态、跨仓合入事务、运行时隔离；产品复杂度显著上升；仍然不解决语义兼容。
- **复杂度**：**很高**。
- **性价比**：**低**，除非“多仓并行 + 可复现构建”是核心卖点。业界已有工具，不必自造。

### G. 整目录复制 / 克隆 / overlay / 容器

- **做法**：每个任务复制整个工程（含 `.git`、ignored 文件），或用 reflink / overlayfs / 容器做隔离。
- **优点**：环境完整，ignored 文件、运行时依赖都能带上（容器尤其）。
- **缺点**：磁盘/时间成本高；reflink/overlayfs 平台相关（WSL/ext4、macOS 行为不同）；合回仍需逐仓 patch/事务；容器化与“本地优先、简单部署”冲突。
- **复杂度**：**很高**。
- **性价比**：**低**，除特定重型场景。

## 5. 对比矩阵

| 方案 | 用户配置 | 多仓并发 | 多仓 git 语义 | 代码改动 | 主要风险 | 复杂度 | 性价比 |
|---|---|---|---|---|---|---|---|
| **A 现状** | 3 类手选 | 串行 | 分支 + 逐任务提交 | — | 状态机复杂、侵入仓库 | 高 | 中 |
| **B 多仓当普通目录** | 2 类（可自动） | 串行 | 无 | 净减 ~1.0–1.3k | 失去回滚/归属/脏保护 | 低–中 | **高**（若接受语义变化） |
| **C 逐仓 worktree** | 2 类 | 名义并行 | 无 | — | 工程残缺，**不可行** | — | **否决** |
| **C2 全仓镜像** | 2 类 | 任务可并行 | 可保留分支 | 新增物化 + 事务 | 胶水/运行时/跨仓集成 | 高–很高 | 低–中 |
| **D 保守收敛** | 2 类（自动） | 串行 | 分支 + 提交（保留） | 小 | 保留 A 的复杂度 | 中 | 中–高 |
| **E monorepo 边界** | 单仓 / 目录 | 单仓并行、目录串行 | 单仓 worktree | 小 | 要求用户改结构 | 低 | 高（作为规则） |
| **F manifest** | 自动 | 可并行 | 完整可复现 | 很大 | 工程复杂度 | 很高 | 低（除非核心需求） |
| **G 整目录复制** | 自动 | 可并行 | 视实现 | 很大 | 磁盘/平台/合入 | 很高 | 低 |

## 6. 决策轴

按顺序回答四个问题，基本就能落方案：

1. **多仓代码是不是主场景？**
   - 否 → 直接 B（+ 安全网）。
   - 是 → 继续。
2. **是否承诺“项目 = 可回滚的仓库迭代”？**
   - 是 → A 或 D。
   - 否 → B。
3. **多仓并行是不是必须能力？**
   - 否 → A / B / D 都可，按 1、2 选。
   - 是 → 继续。
4. **能否要求用户用 monorepo？**
   - 能 → E（推荐）。
   - 不能 → F 或 C2/G，且先做数据验证；不要直接上 C。

## 7. 推荐路径

### 7.1 近期（低风险，无论选哪条都值得做）

- **类型收敛为两类 + 自动识别**：单仓（锚点是 git 仓库根）→ worktree；其余 → 共享目录。
- **普通目录改为串行 + 直接改**，修掉“文档说弱隔离、实现零隔离却允许并行”的不一致。
- 保留 `multi` 作为内部/legacy 值，映射到对应行为；当前无 DB，迁移成本低。

### 7.2 如果选 B（推荐给“通用任务工作台”定位）

- 删除多仓基线/切换/提交路径，`project_is_multi` 换成“是否需要直接串行”的判定；
- 串行门同时覆盖**项目级**和**任务级**（现在只有 multi 有，plain 完全不拦）；
- 加 B+ 安全网：每仓 HEAD、任务 diff 快照、脏警告、只读分支显示；
- 在 DESIGN 明确写：多仓/普通目录项目**不对应 git 分支边界**，git 生命周期由用户管理；
- 同步改 DESIGN §2/§4/§10/§14、ARCH §5.3/§6.2/§14/§15、README、前端和 smoke。

### 7.3 如果选 A/D（推荐给“coding-first、项目=迭代”定位）

- 保留多仓分支/提交；
- 至少做类型自动识别 + 普通目录串行；
- 继续维护 `baseline.rs` 的切换状态机。

### 7.4 如果要做多仓并行

- **优先 E（monorepo）**；
- 只有数据证明“多仓并行是刚需”时，才考虑 C2 或 F；
- 无论 C2 还是 F，都必须同时解决：全仓物化、胶水策略、跨仓合入事务、运行时隔离；
- 先做 spike，量四个指标：多仓工程占比、任务跨仓比例、胶水大小/变更频率、并行测试资源冲突率。

## 8. 未决问题

1. **B 下是否保留“任务一次提交”作为 opt-in？** 默认不建议：`git add -A` 会把用户未提交改动卷进去；只读 diff 快照更安全。
2. **胶水文件是只读还是可写？** 第一版建议只读 + hash 快照 + 修改即拒绝/升级；确认“任务经常改胶水”后再考虑 meta-repo。
3. **项目级并行是否要？** 会引入每项目每仓分支和跨仓合入队列，成本远高于任务级并行。
4. **报告和证据是否保留 diff？** 建议保留：HEAD 基线 + 任务 diff 快照，成本低、对代码评审价值高。
5. **是否保留 `multi` 类型值？** 建议保留读取兼容，但用户界面不再暴露。
6. **普通目录的默认工作区**是否还保留每任务子目录？串行后不是安全必需，可作为清理便利保留，不影响类型模型。

## 9. 一句话回顾

> 多仓靠 worktree 并行不成立：逐仓 worktree 会让工程残缺，全仓镜像又绕不开胶水文件、ignored 文件、跨仓一致性和运行时隔离。多仓串行是共享目录模型的本质约束。真正的产品抉择只有一条：**DOMO 要不要继续管理多仓的 git 迭代边界**。要 → A/D，保留分支、提交、切换，接受维护成本；不要 → B，删掉这套管理层，串行 + 直接改，把 git 交还用户，并用 HEAD/diff 快照保住审计。两类 + 自动识别是共同收益，先做。多仓并行如果哪天成为刚需，优先引导 monorepo；否则不要用 worktree 去模拟它，那是把调度问题变成分布式事务问题。
